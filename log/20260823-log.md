## 3: สร้าง Data Model และ API Spec (data-api-designer)

- **06-data-model.md:** สร้างใหม่ (ไม่มีไฟล์นี้มาก่อน) — [06-data-model.md](../01-requirements/06-data-model.md) ต่อยอดจาก 11 entity เชิงแนวคิดใน [05-architecture.md](../01-requirements/05-architecture.md) หัวข้อ 5 แตกเพิ่มอีก 6 entity ที่มีหลักฐานรองรับชัดเจนจาก backlog/spec/acceptance-criteria (Unit, DrugItem, RequisitionLineItem, ManualForecastAdjustment, HistoricalUsageRecord, GoodsReceiptRecord) รวมเป็น 17 entity พร้อม ER Diagram (Mermaid) และตารางฟิลด์ครบทุกตาราง — ไม่มีการเอ่ยชื่อ database engine/ORM/SQL type ใดๆ (ใช้ชนิดข้อมูลเชิงแนวคิดทั้งหมด)
- **07-api-spec.md:** สร้างใหม่ (ไม่มีไฟล์นี้มาก่อน) — [07-api-spec.md](../01-requirements/07-api-spec.md) จัดกลุ่ม operation เป็น 11 กลุ่มตาม "องค์ประกอบเชิงตรรกะ/บริการ" ใน 05-architecture.md หัวข้อ 3 พร้อมตาราง RBAC สรุป (หัวข้อ 2) และ cross-reference operation↔entity ครบทั้ง 17 entity (หัวข้อ 4) — ไม่มีการเอ่ยชื่อ API protocol/style หรือกลไก authentication ใดๆ
- **การตัดสินใจที่ต้องถามและคำตอบ:** เครื่องมือถามยืนยันแบบโต้ตอบ (AskUserQuestion) **ไม่พร้อมใช้งานในเซสชันนี้เช่นเดียวกับตอนสร้าง 05-architecture.md** จึงไม่ได้สัมภาษณ์ผู้ใช้แบบ interactive สำหรับประเด็น load-bearing ที่ agent instructions กำหนดให้ต้องถามเสมอในการสร้างเอกสารครั้งแรก เลือกแนวทางที่มีหลักฐานสนับสนุนชัดเจนที่สุดจากเอกสารที่มีอยู่แทนการเดาแบบเปิดกว้าง แล้วบันทึกไว้อย่างโปร่งใสในหัวข้อ 6 ของ data-model และหัวข้อ 5 ของ api-spec:
  1. **ระดับความละเอียดของ data model** = ระดับกลาง (header/detail split) — อ้างอิงหลักฐานจาก AC ของ BL-001 Scenario 3 ที่ยืนยันว่าคำขอเบิกหนึ่งใบมีหลายรายการยา
  2. **การจัดการข้อมูลอ้างอิง/รายการคงที่** = แบบผสม (Mixed) — Unit เป็น entity แยก (จำนวนอาจเปลี่ยนแปลง), ส่วนที่เหลือ (Role, สถานะคำขอ ฯลฯ) เป็น prose enum
  3. **รูปแบบชื่อฟิลด์** = ป้ายไทยหลัก + คำศัพท์อังกฤษกำกับ ไม่มีคอลัมน์ "รหัส" แยก (เพื่อคงความเป็นแนวคิดล้วนๆ)
  4. **หลักการจัดกลุ่ม operation ของ API spec** = Hybrid (resource-oriented สำหรับข้อมูลอ้างอิง + journey-oriented สำหรับ workflow ธุรกิจ) จัดกลุ่มตามองค์ประกอบเชิงตรรกะ/บริการใน 05-architecture.md เพื่อความสอดคล้องข้ามเอกสาร
  5. **การนำเสนอ RBAC ใน API spec** = ตารางสรุปย่อ (หัวข้อ 2) + คอลัมน์ role ต่อ operation พร้อมกันทั้งสองระดับ
- **สิ่งที่ยังค้าง (ต้องตัดสินใจเพิ่ม):** ทั้ง 5 ประเด็นข้างต้นเป็นค่าที่ agent เลือกเองโดยไม่มีการยืนยันจากเจ้าของข้อกำหนด — ต้องให้เจ้าของข้อกำหนดตรวจสอบ/ยืนยัน/ขอเปลี่ยนในรอบเรียกใช้ `/build-data-api-spec` ครั้งต่อไป นอกจากนี้ open items ที่สืบทอดมาจาก spec/backlog/architecture (โครงสร้างคอลัมน์ไฟล์ INVC — บล็อก Epic 4, ฟิลด์เพิ่มเติมของรายการยาที่ต้องเภสัชกรยืนยัน, เกณฑ์กระทบยอด BL-032, จำนวนวันแจ้งเตือนล่วงหน้า BL-009b, รูปแบบไฟล์รายงานผู้บริหาร BL-019, role ที่มีสิทธิ์จัดการรายการยา) ยังคงค้างเช่นเดิมและถูกสะท้อนไว้ในหัวข้อสุดท้ายของทั้งสองเอกสาร

**ต่อเนื่องในรอบเดียวกัน — ยืนยันประเด็นค้างผ่าน `AskUserQuestion` (เครื่องมือพร้อมใช้งานแล้วในฝั่งการสนทนาหลัก):**

- ถามผู้ใช้ยืนยัน 4 ประเด็น: (1) ระดับความละเอียดของ data model, (2) การจัดการข้อมูลอ้างอิง/รายการคงที่, (3) หลักการจัดกลุ่ม operation ของ API spec, (4) role ที่มีสิทธิ์เพิ่ม/แก้ไขรายการยา (Drug/Item Master)
- ผู้ใช้ตอบ: (1)-(3) **คงค่าเริ่มต้นตามที่ agent เลือกไว้ทั้งหมด**; (4) **ผู้ดูแลระบบ (Admin) เท่านั้น** เป็นผู้มีสิทธิ์เพิ่ม/แก้ไขรายการยา
- อัปเดต [06-data-model.md](../01-requirements/06-data-model.md) หัวข้อ 6 และ [07-api-spec.md](../01-requirements/07-api-spec.md) หัวข้อ 2, 3.1, 4, 5 ให้สะท้อนว่า granularity/reference-data/API grouping เป็นการ**ยืนยันแล้ว** และปิด open item เรื่อง role ผู้จัดการรายการยา (ลบออกจากรายการค้าง เปลี่ยนเป็นข้อสรุป Admin เท่านั้น) พร้อมเพิ่ม Changelog entry ในทั้งสองไฟล์
- **สิ่งที่ยังค้าง:** เฉพาะ open items ที่สืบทอดจาก spec/backlog (โครงสร้างคอลัมน์ไฟล์ INVC — บล็อก Epic 4, ฟิลด์เพิ่มเติมของรายการยาที่ต้องเภสัชกรยืนยัน, เกณฑ์กระทบยอด BL-032, จำนวนวันแจ้งเตือนล่วงหน้า BL-009b, รูปแบบไฟล์รายงานผู้บริหาร BL-019) — ไม่มีประเด็นเชิงโครงสร้างของเอกสารทั้งสองนี้เองที่ค้างแล้ว

- **สิ่งที่ยังค้าง (ต้องตัดสินใจเพิ่ม):** 3 Feature มี AC/backlog coverage บางเนื่องจาก open item ที่สืบทอดมาจากรอบก่อนหน้า (ไม่ใช่ปัญหาใหม่ของรอบนี้) — **FT-018** (`invc-file-format-compatibility.md`) บางที่สุด บล็อกโดยรูปแบบคอลัมน์ไฟล์ INVC ที่ยังไม่ยืนยันจากฝ่ายดูแล INVC, **FT-008** (`stock-reconciliation.md`) บล็อกโดยพฤติกรรมกระทบยอด BL-032 ที่ยัง `[รอยืนยัน]`, **FT-016** (`filtered-report-export.md`) บล็อกโดยรูปแบบไฟล์ส่งออกรายงาน BL-019 ที่ยัง `[รอยืนยัน]` — ทั้งสามรายการนี้ไดอะแกรมหยุดที่จุดที่ยืนยันแล้วเท่านั้น ไม่ได้สมมติขั้นตอนที่ยังไม่รู้ผล ควรยืนยันกับเภสัชกรเจ้าของระบบ (FT-008/FT-016) และฝ่ายดูแล INVC (FT-018) ก่อนขยายไดอะแกรมเหล่านี้เพิ่มเติม

## 5: สร้างทะเบียน Detailed Design ที่ขาดหายไป (detailed-design-writer, ขอบเขตจำกัดเฉพาะ README.md)

- **ขอบเขตที่ทำงาน:** ตามคำสั่งเจาะจง — สร้าง/อัปเดตเฉพาะ [01-requirements/08-detailed-design/README.md](../01-requirements/08-detailed-design/README.md) เป็นทะเบียนรวม **ห้ามสร้างไฟล์ detailed design ต่อ Feature ใหม่** ในรอบนี้
- **สิ่งที่พบก่อนเริ่ม:** ตรวจสอบดิสก์จริง (`Glob`) แทนการเชื่อถือรายการ 11 ไฟล์ที่ผู้เรียกให้มา — พบว่ามีไฟล์ detailed design ต่อ Feature อยู่แล้วจริง **21 ไฟล์** (ไม่ใช่ 11 ตามที่แจ้งมา) ครอบคลุม FT-001 ถึง FT-021 ทั้งหมด แต่ไม่มี README.md เป็นทะเบียนรวมมาก่อนเลย ทั้งที่ทุกไฟล์ per-feature มีลิงก์อ้างถึง "README.md" สำหรับนโยบาย granularity/exception/state-diagram ร่วม (ลิงก์ที่ตายอยู่ก่อนหน้านี้)
- **ไฟล์ที่สร้าง:** [01-requirements/08-detailed-design/README.md](../01-requirements/08-detailed-design/README.md) — list ไฟล์ทั้ง 21 ไฟล์ (FT-001–FT-021) พร้อม backlog อ้างอิงและ scenario ที่ครอบคลุมต่อไฟล์, สรุปนโยบายรวม (granularity ระดับกลาง = 1 diagram ต่อ BL-ID, กฎ inline `alt` เทียบกับแยกไดอะแกรม, state diagram เฉพาะ Feature เจ้าของสถานะจริง [FT-002, FT-017], การแทน participant ตาม 05-architecture.md §3) โดยสรุปจากเนื้อหาไฟล์ที่มีอยู่จริง ไม่ใช่การตัดสินใจใหม่ และ list Feature ที่ยังไม่มีไฟล์ (FT-022–FT-025 ทั้งหมดอยู่ใน Epic 5)
- **การตัดสินใจที่ถามและคำตอบ:** ไม่มีการถามผู้ใช้ในรอบนี้ — ขอบเขตถูกระบุไว้ชัดเจนแล้วว่าจำกัดเฉพาะ README.md เท่านั้น

- **สิ่งที่ยังค้าง (ต้องตัดสินใจเพิ่ม):** (1) FT-022–FT-025 (Epic 5: Responsive UI, PDPA, Access Log, Availability) ยังไม่มีไฟล์ detailed design — ต้องรอคำร้องขอเจาะจงผ่าน `/build-detailed-design {FT-ID}`; สังเกตว่า FT-022 และ FT-025 อาจไม่เหมาะกับรูปแบบ sequence diagram แบบเดียวกับ Feature เชิงธุรกิจอื่น (เป็น NFR ล้วนๆ) ควรหารือรูปแบบที่เหมาะสมก่อนสร้างจริง (2) open items เดิมที่สืบทอดจาก backlog/spec (INVC column format, BL-032 เกณฑ์กระทบยอด, BL-019 รูปแบบไฟล์รายงาน, BL-009b จำนวนวันแจ้งเตือน) ยังคงค้างเช่นเดิมและถูกสะท้อนไว้ใน README.md ใหม่แล้ว

## 6: ตรวจสอบ/ยืนยัน Detailed Design ของ FT-022 (detailed-design-writer, ขอบเขตเจาะจง FT-022)

- **ขอบเขตที่ทำงาน:** เฉพาะ FT-022 (BL-026 — ออกแบบ UI แบบ Responsive เต็มรูปแบบ) ตามคำสั่งเจาะจงจากผู้ประสาน ซึ่งอ้างอิงสถานะของ README.md ที่เคยระบุว่า FT-022 "ยังไม่มี Detailed Design" (สแนปช็อตจากรายการที่ 5)
- **สิ่งที่พบก่อนเริ่ม:** ตรวจสอบดิสก์จริงด้วย `Glob`/`Read` แทนการเชื่อสถานะที่ได้รับมา — พบว่า **`responsive-ui-all-devices.md` มีอยู่แล้วจริงบนดิสก์** พร้อมเนื้อหาสมบูรณ์ (ลงวันที่ 20260823 เช่นกัน) และ **README.md ก็ถูกแก้ไขให้ตรงกับความจริงแล้ว** (25/25 ไฟล์ รวม FT-022) — README.md มี Changelog ของตัวเองระบุว่าเคยเกิด "race condition" ระหว่างสองรอบการรันคู่ขนานที่เขียนทับกัน และถูกแก้ไขให้ตรงกับดิสก์จริงไปแล้วก่อนรอบนี้จะเริ่ม จึงไม่มีการแก้ไขไฟล์ README.md เพิ่มเติมในรอบนี้ (สถานะที่ผู้ประสานได้รับมาเป็นข้อมูลเก่ากว่าความจริงบนดิสก์)
- **การตรวจสอบเนื้อหา `responsive-ui-all-devices.md`:** เทียบกับ `backlog.md` (BL-026), `02-feature-list.md` (FT-022), และ `04-test-design/acceptance-criteria.md` (BL-026 Scenario 1-4: desktop/tablet/mobile/boundary) แล้ว **สอดคล้องครบถ้วน ไม่พบ drift** — breakpoint ตรงกัน (mobile 320-767px/tablet 768-1023px/desktop 1024px+), grid column ต่อ breakpoint อ้างอิง DESIGN.md ตรงกับ AC, มี boundary case (รอยต่อ 767/768px และ 1023/1024px) ครบ ไม่มีการเอ่ยชื่อ technology/protocol ใดๆ participant ใช้ role/องค์ประกอบเชิงตรรกะทั่วไปเท่านั้น
- **การตัดสินใจที่ต้องถามผู้ใช้ (ยังไม่เคยถามมาก่อนสำหรับ FT-022 นี้โดยเฉพาะ):** เครื่องมือ `AskUserQuestion` ไม่พร้อมใช้งานสำหรับ subagent นี้ในเซสชันนี้ ("Error: No such tool available: AskUserQuestion") จึงไม่สามารถถามผู้ใช้แบบ interactive ได้โดยตรง — ไฟล์ปัจจุบันเลือกแนวทาง **"hybrid": หนึ่งไดอะแกรมตัวแทนครอบคลุมทั้ง 3 breakpoint + หมายเหตุอธิบายเหตุผล** โดยเป็นการตัดสินใจของผู้เขียนไฟล์เองในรอบก่อนหน้า (รอบที่ 4) ไม่เคยถูกยืนยันจากผู้ใช้จริง จึงคงแนวทางนี้ไว้เป็นค่าเริ่มต้นที่สมเหตุสมผลที่สุด (ตาม Auto Mode) แต่เสนอ 3 ทางเลือกพร้อมข้อดี/ข้อเสียให้ผู้ประสานส่งต่อผู้ใช้ยืนยันหรือเปลี่ยน: **(ก) คงแนวทาง hybrid ปัจจุบัน** (ไดอะแกรมตัวแทนเดียว + note) — ข้อดี: มีอยู่แล้ว มีเหตุผลรองรับ ตรงตามเทมเพลตขั้นต่ำ 1 diagram/Feature และคงความสม่ำเสมอกับอีก 24 ไฟล์; ข้อเสีย: ไดอะแกรมค่อนข้างเป็นแนวคิดกว้างๆ ไม่อ้างอิงหน้าจอ/operation ที่เป็นรูปธรรม **(ข) เอา sequence diagram ออกทั้งหมด เปลี่ยนเป็น checklist/constraint เชิงข้าม Feature** ที่ไฟล์อื่นอ้างอิงกลับมาแทน — ข้อดี: ตรงกับธรรมชาติของ NFR ที่ไม่มี "ใคร→ใคร" จริงมากกว่า; ข้อเสีย: ขัดกับเทมเพลต/นโยบายที่ต้องมี sequence diagram อย่างน้อย 1 อัน และต้องแก้ไขจุดอ้างอิงในไฟล์อื่นถ้านำไปใช้เป็นแนวทางมาตรฐาน **(ค) แยกไดอะแกรมต่อ breakpoint (3 ไดอะแกรม)** เพื่อ map ตรงกับ AC 4 scenario/prototype 1:1 — ข้อดี: traceability ละเอียดที่สุด; ข้อเสีย: ไดอะแกรมซ้ำกันเกือบทั้งหมดต่างแค่ note เพิ่มภาระดูแลโดยไม่ได้ข้อมูลใหม่
- **ไฟล์ที่แก้ไข:** ไม่มี — ทั้ง `responsive-ui-all-devices.md` และ `README.md` อยู่ในสถานะถูกต้องอยู่แล้วก่อนรอบนี้เริ่ม (ตรวจสอบแล้วไม่มี drift ที่ต้องแก้)
- **สิ่งที่ยังค้าง (ต้องตัดสินใจเพิ่ม):** รอผู้ใช้ยืนยัน/เลือกทางเลือกการนำเสนอ FT-022 ข้างต้น (ก/ข/ค) — ปัจจุบันคงแนวทาง (ก) ไว้เป็นค่าเริ่มต้น; นอกจากนี้สังเกตว่ามีรอบการรัน `/build-detailed-design` คู่ขนานกันเกิดขึ้นในโปรเจกต์นี้ (ตามที่ README.md เองบันทึกไว้เรื่อง race condition) ควรแจ้งผู้ใช้ให้ระวังการเรียกใช้ subagent นี้ซ้อนกันหลายรอบพร้อมกัน เพื่อป้องกันการเขียนทับไฟล์กันเองในอนาคต

## 7: ปรองดอง race condition ระหว่างรายการที่ 4 และ 5 (detailed-design-writer)

- **สิ่งที่พบ:** รายการที่ 4 (สร้างครบ 25 Feature ในรอบเดียว ตามคำตอบ AskUserQuestion ของผู้ใช้) และรายการที่ 5 (รันแยกต่างหากด้วยขอบเขตจำกัดเฉพาะ README.md โดยเห็นดิสก์มีเพียง 21 ไฟล์) เกิดขึ้น**พร้อมกันแบบ race condition** — รายการที่ 5 อ่านสถานะดิสก์ก่อนที่รายการที่ 4 จะเขียนไฟล์ FT-022–FT-025 เสร็จ แล้วรายการที่ 5 เขียนทับ `README.md` ที่รายการที่ 4 สร้างไว้แล้วด้วยเวอร์ชันที่รายงานผิดว่ามีไฟล์ครบเพียง 21/25 และ FT-022–FT-025 ยังไม่มี detailed design (ทั้งที่ไฟล์ทั้ง 4 นี้มีอยู่จริงบนดิสก์พร้อมเนื้อหาครบถ้วนจากรายการที่ 4)
- **การแก้ไข:** ตรวจสอบดิสก์จริงด้วย `Glob` อีกครั้ง ยืนยันว่าไฟล์ per-feature ทั้ง 25 ไฟล์ไม่ได้รับผลกระทบจาก race condition นี้ (มีแต่ `README.md` เท่านั้นที่ถูกเขียนทับ) จึงเขียน `README.md` ใหม่อีกครั้งให้สะท้อนสถานะที่ถูกต้อง (25/25 ไฟล์) โดยรวมโครงสร้างตารางที่ดีกว่าจากเวอร์ชันของรายการที่ 5 (คอลัมน์ "Backlog อ้างอิง" และคำอธิบาย scenario ที่ละเอียดกว่า) เข้ากับเนื้อหาที่ถูกต้องครบถ้วน ไม่มีไฟล์ per-feature ใดถูกแก้ไขเพิ่มเติม
- **สิ่งที่ยังค้าง:** เหมือนเดิมตามที่ระบุไว้ในรายการที่ 4 (FT-008/FT-016/FT-018 มี AC/backlog coverage บางเนื่องจาก open item ที่สืบทอดมา ไม่ใช่ปัญหาใหม่) — ไม่มี Feature ใดขาดหายไปอีกต่อไป

## 8: ยืนยันรูปแบบการนำเสนอ FT-022 กับเจ้าของข้อกำหนด (ถามผ่าน AskUserQuestion ในการสนทนาหลัก)

- **สิ่งที่ค้าง:** รายการที่ 6 พบว่า [responsive-ui-all-devices.md](../01-requirements/08-detailed-design/responsive-ui-all-devices.md) (FT-022) เลือกแนวทาง "hybrid" (1 ไดอะแกรมตัวแทนครอบคลุมทั้ง 3 breakpoint แทนการแยกตามนโยบาย "3+ branch แยกไดอะแกรม") โดย agent เลือกเองในรายการที่ 4 โดยไม่เคยถามผู้ใช้ เนื่องจาก `AskUserQuestion` ไม่พร้อมใช้งานสำหรับ subagent ในตอนนั้น
- **คำถามที่ถาม:** เสนอ 3 ทางเลือกพร้อมข้อดี/ข้อเสีย — (ก) คงแนวทาง hybrid ปัจจุบัน (ข) เปลี่ยนเป็น checklist/constraint แทน sequence diagram (ค) แยก 3 ไดอะแกรมต่อ breakpoint
- **คำตอบ:** ผู้ใช้ยืนยัน **คงแนวทาง hybrid ปัจจุบัน** ไม่มีการเปลี่ยนแปลง
- **การอัปเดต:** แก้ [responsive-ui-all-devices.md](../01-requirements/08-detailed-design/responsive-ui-all-devices.md) หัวข้อ 5 และ Changelog ให้สะท้อนว่าเป็นการยืนยันแล้ว (ไม่ใช่การตัดสินใจเองที่รอยืนยันอีกต่อไป) และเพิ่มหมายเหตุยืนยันใน [README.md](../01-requirements/08-detailed-design/README.md) ที่ข้อ "ข้อยกเว้นที่ตั้งใจ"

- **การตัดสินใจที่ต้องถามและคำตอบ:** ประเด็น "รูปแบบข้อมูลของหมวดบัญชีแพทย์" (Boolean เดี่ยวบน DrugItem vs. entity หมวดยาแยก vs. join กับ Unit) เป็นการตัดสินใจเชิงออกแบบจริงที่ไม่ถูกกำหนดไว้ชัดเจนจากข้อเท็จจริงที่ยืนยันแล้วเพียงอย่างเดียว — เครื่องมือ `AskUserQuestion` ไม่อยู่ใน toolset ของ agent นี้ในเซสชันนี้ (เช่นเดียวกับ agent อื่นที่เคยพบมาก่อนในวันเดียวกัน — รายการที่ 1, 3, 6, 12) จึงไม่สามารถถามแบบโต้ตอบได้ เขียนการวิเคราะห์ 3 แนวทางพร้อมข้อดี/ข้อเสียครบไว้ใน [06-data-model.md](../01-requirements/06-data-model.md) หัวข้อ 6 แล้ว**เลือกแนวทาง Boolean เดี่ยวบน DrugItem เป็นค่าเริ่มต้น** ด้วยเหตุผลว่ามีหลักฐานรองรับมากที่สุดและเสี่ยงน้อยที่สุดที่จะสมมติโครงสร้างเกินข้อเท็จจริงที่ยืนยันแล้ว (ไม่มีหลักฐานว่ายาตัวเดียวกันจัดหมวดต่างกันตามหน่วย) — บันทึกเป็น `[ถือว่า — รอเภสัชกรเจ้าของระบบยืนยัน]` ให้ผู้ประสาน/ผู้ใช้ยิงคำถามนี้ผ่าน `AskUserQuestion` ในรอบสนทนาหลักได้ถ้าต้องการเปลี่ยน
- **การปิด open item เพิ่มเติม (ไม่ได้ถูกขอตรงๆ แต่พบระหว่างแก้ไข):** ข้อกังวลเดิมใน AC ของ BL-022 Scenario 3 / TC-102 เรื่อง "กลไกป้องกันที่ต้นทางให้รายการยาทุกตัวมี WORKING_CODE ก่อนใช้เบิกได้" ได้รับคำตอบเชิงแนวคิดแล้วจากการกำหนดให้ WORKING_CODE เป็นฟิลด์จำเป็น+unique ที่ระดับ entity ของ DrugItem (บังคับที่ operation "เพิ่ม/แก้ไขรายการยา") — บันทึกหมายเหตุไว้ในหัวข้อ 3.13 ของ data-model.md แล้ว แต่**ไม่ได้แก้ไข** acceptance-criteria.md/test-case โดยตรง (ไฟล์เหล่านั้นดูแลโดย `/build-test-design` เท่านั้น) — ส่งต่อให้รอบ `/check-backlog-sync` หรือ `/build-test-design` ถัดไปอัปเดต `[รอยืนยัน]` นี้ให้ตรงกัน
- **สิ่งที่ยังค้าง (ต้องตัดสินใจเพิ่ม):**
  1. ยืนยันแนวทางโมเดล "หมวดบัญชีแพทย์" (Boolean เดี่ยว — ค่าเริ่มต้นที่เลือกไว้ — เทียบกับ 2 ทางเลือกอื่นที่วิเคราะห์ไว้ใน data-model.md หัวข้อ 6)
  2. ส่งต่อให้ `/check-backlog-sync` หรือ `/build-test-design` อัปเดต acceptance-criteria.md/test-case ของ BL-022 (ปิด `[รอยืนยัน]` เรื่องกลไกป้องกันที่ต้นทาง) และของ BL-034 (เปลี่ยนจาก mock flag เป็นฟิลด์จริง TC-103/TC-104) ให้ตรงกับฟิลด์ที่เพิ่มในรอบนี้
  3. ส่งต่อให้ `/build-detailed-design FT-018` อัปเดต [08-detailed-design/invc-file-format-compatibility.md](../01-requirements/08-detailed-design/invc-file-format-compatibility.md) ให้สะท้อนฟิลด์/ตรรกะแยกไฟล์ที่ยืนยันแล้ว (นอกขอบเขตของ agent นี้)
  4. open item อื่นที่ไม่เกี่ยวข้องกับรอบนี้ไม่เปลี่ยนแปลง: การเชื่อมต่อ JHCIS/myPCU โดยตรง [BL-023/FR-4.4], เกณฑ์กระทบยอด [BL-032], จำนวนวันแจ้งเตือนล่วงหน้า [BL-009b], รูปแบบไฟล์ส่งออกรายงานผู้บริหาร [BL-019], ฟิลด์คลินิกเพิ่มเติมของรายการยา (dosage form/หน่วยนับ/กลุ่มยา)

## 17: ยืนยันแนวทางโมเดล "หมวดบัญชีแพทย์" กับเจ้าของข้อกำหนด (ถามผ่าน AskUserQuestion ในการสนทนาหลัก)

- **การอัปเดต:** แก้ [06-data-model.md](../01-requirements/06-data-model.md) หัวข้อ 3.3 (หมายเหตุฟิลด์ "หมวดบัญชีแพทย์") และหัวข้อ 6 ให้สะท้อนว่าเป็นการยืนยันแล้ว ไม่ใช่ `[ถือว่า]` ที่รออีกต่อไป พร้อมเพิ่ม Changelog entry

## 19: Sync Check ของ High-Level Architecture หลังยืนยันรูปแบบไฟล์ INVC (architecture-writer)

- **ขอบเขตที่ตรวจ:** ตรวจสอบ [05-architecture.md](../01-requirements/05-architecture.md) ทั้งฉบับเทียบกับ `backlog.md`, `02-feature-list.md`, `03-user-journey/*.md` (4 ไฟล์), และ `01-spec/*.md` (6 ไฟล์) เวอร์ชันล่าสุดบนดิสก์ — ไม่จำกัดเฉพาะจุดที่ผู้เรียกงานระบุมา (INVC) แต่ตรวจทั้งฉบับตามที่ได้รับมอบหมาย
- **สิ่งที่พบ:** เอกสารยังค้างสถานะเดิมของรูปแบบไฟล์ INVC ("ยังไม่ยืนยันรูปแบบคอลัมน์" / "บล็อกการพัฒนา Epic 4 ทั้งหมด") ใน 5 จุด ทั้งที่ [spec 005](../01-requirements/01-spec/20260816-005-legacy-system-integration.md) ยืนยันแล้วตั้งแต่ 20260823 (FR-4.3/FR-4.3a/FR-4.3b จากไฟล์ตัวอย่างจริง 46 ไฟล์ที่เจ้าของข้อกำหนดตรวจสอบเอง) และ `backlog.md`/`02-feature-list.md`/`08-detailed-design/invc-file-format-compatibility.md` ถูกอัปเดตให้สะท้อนสถานะนี้ไปแล้วก่อนหน้า (รายการที่ 12-18 ของ log วันนี้) — ไม่พบจุด drift อื่นนอกเหนือจากเรื่อง INVC นี้ (ตรวจครบ: องค์ประกอบเชิงตรรกะ 11 รายการ, data flow ทั้ง 4 role, entity เชิงแนวคิด 11 รายการ, จุดเชื่อมต่อภายนอกอื่น (JHCIS/myPCU, อีเมล, LINE OA), NFR 8 หัวข้อ, open items ที่เหลือ (BL-023/BL-032/BL-009b/BL-019) — ทั้งหมดยังคง sync กับสถานะปัจจุบันของ backlog/spec/feature-list/journey ไม่มีจุดต้องแก้เพิ่ม
- **การแก้ไข (auto-fixed ทั้งหมด — ไม่มีจุดกำกวมที่ต้องถามผู้ใช้ เนื่องจากมีหลักฐานยืนยันชัดเจนตรงตัวจาก spec 005/backlog.md/06-data-model.md อยู่แล้ว):**
  1. หัวข้อ 3 — แถว "บริการส่งออกไฟล์เชื่อมต่อระบบเดิม": เปลี่ยนจาก "(ยังไม่ยืนยันรูปแบบคอลัมน์)" เป็นยืนยันแล้ว พร้อมเพิ่มตรรกะแยก 1-2 ไฟล์ต่อหน่วยต่อรอบ (FR-4.3a)
  2. หัวข้อ 5 — entity "ไฟล์ส่งออก (Export File)": เพิ่มคำอธิบายกรณี 1 หรือ 2 ไฟล์ตามรายการยาหมวด "บัญชีแพทย์" และเพิ่มการอ้างอิง BL-034
  3. หัวข้อ 6 (จุดเชื่อมต่อระบบภายนอก) — แถว INVC: เปลี่ยนสถานะจาก `[ต้องยืนยัน — รูปแบบคอลัมน์ไฟล์]`/"บล็อกการพัฒนา Epic 4 ทั้งหมด" เป็น resolved (20260823) พร้อมเพิ่มการอ้างอิง FR-4.3a/FR-4.3b และ BL-034

## 27: ยืนยันบางส่วน — ผู้รับผิดชอบตรวจสอบ/คอนเฟิร์มยอดไม่ตรงกัน BL-032 (requirement-writer)

(แม่ข่าย) เสมอไป (การปรึกษา รพศ.ชร. เป็นทางเลือกเสริมเมื่อไม่แน่ใจเท่านั้น) พร้อมตั้งข้อสังเกตว่าขั้นตอนนี้ **น่าจะ** เกิดขึ้นระหว่างขั้นตอนอนุมัติคำขอเบิกระดับ 1 ที่เภสัชกรตรวจสอบคำขออยู่แล้ว (FT-002/BL-004) แต่ขอไม่ให้ agent สมมติจุดผูกนี้เองโดยไม่ถามยืนยันถ้ายังกำกวม — เดิม open item นี้ (ค้างมาจากรอบที่ 16/23/26) ยังไม่มี BL-ID รองรับโดยตรง
