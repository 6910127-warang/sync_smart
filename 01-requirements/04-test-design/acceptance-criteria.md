## รายละเอียดต่อ Backlog Item

### Epic 1: เบิก-จ่ายยา NCD (Core)

### BL-001 | เจ้าหน้าที่ รพ.สต. เห็นยอดแนะนำเบิกอัตโนมัติ

- **Feature:** [FT-001](../02-feature-list.md) — สร้างคำขอเบิกยาประจำเดือน
- **อ้างอิง:** FR-1.1, US-1.0 ([002](../01-spec/20260816-002-ncd-drug-requisition-core.md))

**Scenario 1: แสดงยอดแนะนำเบิกอัตโนมัติ (happy path)**
- Given มีเกณฑ์ safety stock ที่คำนวณแล้วและยอดคงเหลือล่าสุดของหน่วย
- When เจ้าหน้าที่ รพ.สต. เปิดหน้าสร้างคำขอเบิกของเดือนนั้น
- Then ระบบแสดงยอดแนะนำเบิกต่อรายการยาโดยอัตโนมัติ

**Scenario 2: หน่วยยังไม่มีเกณฑ์ safety stock ที่คำนวณเสร็จ (edge)**
- Given หน่วยยังไม่มีเกณฑ์ safety stock ที่คำนวณเสร็จ (เช่น BL-011 ยังไม่เสร็จ หรือหน่วยเพิ่งเข้าร่วมเครือข่าย)
- When เจ้าหน้าที่เปิดหน้าสร้างคำขอเบิก
- Then **[ถือว่า]** ระบบต้องแจ้งให้ทราบว่ายังไม่มีค่ายอดแนะนำ ไม่ใช่แสดงค่า 0 ที่ทำให้เข้าใจผิดว่าไม่ต้องเบิก

**Scenario 3: หน่วยมีหลายรายการยาที่ต้องเบิกในเดือนนั้น**
- Given หน่วยมีรายการยาหลายรายการที่ต้องเบิกในรอบเดือนนั้น
- When เปิดหน้าสร้างคำขอ
- Then ระบบแสดงยอดแนะนำแยกต่อรายการยาทุกรายการ ไม่ใช่ยอดรวมเดียว

### BL-002 | เจ้าหน้าที่ รพ.สต. กรอกยอดคงเหลือ + ยืนยันคำขอเบิก

- **Feature:** [FT-001](../02-feature-list.md)
- **อ้างอิง:** FR-1.1a, US-1.1 ([002](../01-spec/20260816-002-ncd-drug-requisition-core.md))

**Scenario 1: กรอกยอดคงเหลือและยืนยันคำขอ (happy path)**
- Given เจ้าหน้าที่เห็นยอดแนะนำเบิกแล้ว
- When กรอกยอดคงเหลือปัจจุบันของแต่ละรายการและกดยืนยันคำขอ
- Then ระบบบันทึกคำขอสถานะ "รอการอนุมัติระดับ 1"

**Scenario 2: กรอกยอดคงเหลือเป็นค่าที่ไม่ถูกต้อง (validation error)**
- Given กำลังกรอกยอดคงเหลือของรายการยา
- When กรอกค่าที่ไม่ใช่ตัวเลข หรือค่าติดลบ
- Then **[ถือว่า]** ระบบต้องปฏิเสธการบันทึกและแจ้งให้แก้ไขก่อนยืนยันคำขอ (validation มาตรฐานของฟอร์มตัวเลข)

**Scenario 3: กรอกยอดคงเหลือไม่ครบทุกรายการ (edge)**
- Given มีรายการยาที่ยังไม่ได้กรอกยอดคงเหลือครบทุกรายการ
- When กดยืนยันคำขอ
- Then **[ถือว่า]** ระบบต้องไม่ยืนยันคำขอจนกว่าจะกรอกครบทุกรายการยา

### BL-003 | เจ้าหน้าที่ รพ.สต. กด "ขอปรึกษา"

- **Feature:** [FT-001](../02-feature-list.md)
- **อ้างอิง:** FR-1.1b, US-1.1b ([002](../01-spec/20260816-002-ncd-drug-requisition-core.md))

**Scenario 1: กด "ขอปรึกษา" แจ้งเภสัชกร (happy path)**
- Given เจ้าหน้าที่ไม่เห็นด้วยกับยอดแนะนำ
- When กดปุ่ม "ขอปรึกษา"
- Then ระบบส่ง alert ไปยังกลุ่มเภสัชกรผ่าน LINE OA ทันที และบันทึกเหตุการณ์นี้ลง audit trail (BL-008)

**Scenario 2: LINE OA ไม่พร้อมใช้งานชั่วคราว (error)**
- Given ช่องทาง LINE OA ไม่พร้อมใช้งานชั่วคราว (เช่น API ล่ม)
- When กดปุ่ม "ขอปรึกษา"
- Then **[ถือว่า]** ระบบต้องแจ้งผู้ใช้ว่าส่งแจ้งเตือนไม่สำเร็จ และยังคงบันทึกเหตุการณ์การกดขอปรึกษาไว้ใน audit trail (ไม่ปล่อยให้เงียบหายไปทั้งหมด)

**Scenario 3: กดขอปรึกษาแล้วยังแก้ไข/ยืนยันคำขอต่อได้**
- Given กดปุ่ม "ขอปรึกษา" แล้วแต่ยังไม่ได้ยืนยันคำขอ
- When เจ้าหน้าที่แก้ไขยอดคงเหลือ/ยอดแนะนำต่อ
- Then เจ้าหน้าที่ยังคงยืนยันคำขอในภายหลังได้ตามปกติ (ปุ่มขอปรึกษาไม่บล็อกการยืนยันคำขอ)

### BL-004 | เภสัชกรอนุมัติคำขอเบิกแบบสองระดับ

- **Feature:** [FT-002](../02-feature-list.md) — อนุมัติคำขอเบิกแบบสองระดับ
- **อ้างอิง:** FR-1.2, US-1.2, US-1.2b ([002](../01-spec/20260816-002-ncd-drug-requisition-core.md))

**Scenario 1: อนุมัติระดับ 1 (happy path)**
- Given คำขอสถานะ "รอการอนุมัติระดับ 1"
- When เภสัชกรระดับ 1 พิจารณาและอนุมัติ
- Then สถานะเปลี่ยนเป็น "รอการอนุมัติระดับ 2"

**Scenario 2: ปฏิเสธ/ปรับจำนวนที่ระดับ 1 (edge)**
- Given คำขอสถานะ "รอการอนุมัติระดับ 1"
- When เภสัชกรระดับ 1 ปฏิเสธคำขอ หรือปรับจำนวนก่อนอนุมัติ
- Then ระบบบันทึกจำนวนที่ปรับ (ถ้ามี) หรือสถานะ "ปฏิเสธ" พร้อมเหตุผล และบันทึกลง audit trail (BL-008)

**Scenario 3: อนุมัติระดับ 2 โดยคนละคน (happy path)**
- Given คำขอผ่านระดับ 1 แล้ว
- When เภสัชกรระดับ 2 (คนละคนกับระดับ 1) ยืนยัน
- Then สถานะเปลี่ยนเป็น "อนุมัติแล้ว"

**Scenario 4: เภสัชกรคนเดียวกันพยายามอนุมัติสองระดับ (error — RBAC)**
- Given เภสัชกรคนเดียวกันเป็นผู้อนุมัติระดับ 1
- When พยายามยืนยันระดับ 2 ของคำขอเดียวกัน
- Then ระบบต้องปฏิเสธการกระทำ (ดู DESIGN.md §4.3 — UI ควรซ่อน/disable ปุ่มระดับ 2 ด้วย ไม่พึ่ง backend validation อย่างเดียว)

**Scenario 5: เภสัชกรระดับ 1 คอนเฟิร์มยอดไม่ตรงกันเป็นส่วนหนึ่งของการอนุมัติระดับ 1 (happy path, เพิ่ม 20260824 — อ้างอิง FR-1.9b, BL-032)**
- Given คำขอที่กำลังพิจารณาอยู่ในขั้นตอนอนุมัติระดับ 1 มีข้อความแจ้งเตือนยอดไม่ตรงกันปรากฏอยู่ (ดู BL-032/FT-008 ด้านล่าง)
- When เภสัชกรผู้อนุมัติระดับ 1 กด "คอนเฟิร์ม" การกระทบยอดนี้ (เป็น interaction เดียวกับการพิจารณาอนุมัติระดับ 1 ไม่ใช่ขั้นตอนแยก)
- Then ระบบต้องให้เภสัชกรกรอกยอดคงเหลือที่ถูกต้องด้วยตนเอง และบันทึกค่านั้นเป็นยอดคงเหลือที่ถูกต้อง/มีผลผูกพันต่อ แทนยอดเดิมที่เจ้าหน้าที่ รพ.สต. รายงาน (FR-1.1a)

### BL-005 | ระบบเปลี่ยนสถานะ "พร้อมส่งออก" / "จ่ายแล้ว"

- **Feature:** [FT-002](../02-feature-list.md)
- **อ้างอิง:** FR-1.3 ([002](../01-spec/20260816-002-ncd-drug-requisition-core.md))

**Scenario 1: เปลี่ยนสถานะเป็น "พร้อมส่งออก" (happy path)**
- Given คำขอผ่านอนุมัติครบสองระดับ
- When ระบบประมวลผล
- Then สถานะเปลี่ยนเป็น "พร้อมส่งออก" โดยอัตโนมัติ

**Scenario 2: เปลี่ยนสถานะเป็น "จ่ายแล้ว" ทันทีที่คอนเฟิร์ม (happy path)**
- Given เภสัชกรผู้อนุมัติระดับ 2 กด "คอนเฟิร์ม" (BL-020)
- When ระบบประมวลผล
- Then สถานะเปลี่ยนเป็น "จ่ายแล้ว" ทันที โดยไม่ต้องรอการยืนยันย้อนกลับจากฝ่ายคลังยาว่านำเข้า INVC สำเร็จ

**Scenario 3: คำขอที่ยังอนุมัติไม่ครบสองระดับ (edge)**
- Given คำขอผ่านการอนุมัติเพียงระดับเดียว (ยังไม่ครบ 2 ระดับ)
- When ตรวจสอบสถานะคำขอ
- Then สถานะต้องไม่ใช่ "พร้อมส่งออก" (ยังคงเป็น "รอการอนุมัติระดับ 2")

### BL-006 | เจ้าหน้าที่ รพ.สต. ยืนยันการรับยา

- **Feature:** [FT-003](../02-feature-list.md) — ยืนยันรับยาเข้าคลัง
- **อ้างอิง:** FR-1.4, US-1.3 ([002](../01-spec/20260816-002-ncd-drug-requisition-core.md))

**Scenario 1: ยืนยันรับยา (happy path)**
- Given ยาถูกจ่ายจาก รพ.แม่ข่ายแล้ว (สถานะ "จ่ายแล้ว")
- When เจ้าหน้าที่ยืนยันรับยาเข้าคลัง
- Then ยอดคงคลังของหน่วยอัปเดตทันที

**Scenario 2: เจ้าหน้าที่หน่วยอื่นพยายามยืนยันรับยา (error — RBAC)**
- Given เจ้าหน้าที่ รพ.สต. อื่นที่ไม่ใช่เจ้าของคำขอนี้
- When พยายามยืนยันรับยาแทนหน่วยอื่น
- Then ระบบต้องปฏิเสธการกระทำ เนื่องจากสิทธิ์เข้าถึงเฉพาะหน่วยตนเอง (อ้างอิง BL-024 RBAC)

**Scenario 3: พยายามยืนยันรับยาก่อนสถานะ "จ่ายแล้ว" (edge — state)**
- Given คำขอยังไม่ได้เปลี่ยนเป็นสถานะ "จ่ายแล้ว" (เช่น เภสัชกรยังไม่กดคอนเฟิร์ม)
- When เจ้าหน้าที่พยายามยืนยันรับยา
- Then ระบบต้องไม่อนุญาตให้ยืนยันรับยาก่อนสถานะ "จ่ายแล้ว"

### BL-007 | แสดงยอดคงคลังแบบ Real-time

### BL-009b | แจ้งเตือนล่วงหน้าก่อนกำหนดส่งคำขอเบิกประจำเดือน

- **Feature:** [FT-007](../02-feature-list.md) — แจ้งเตือนล่วงหน้าก่อนกำหนดส่งคำขอเบิกประจำเดือน
- **อ้างอิง:** FR-1.8, US-1.5 ([002](../01-spec/20260816-002-ncd-drug-requisition-core.md)) — resolved 20260825 (จำนวนวันล่วงหน้า = 2 วัน)

**Scenario 1: แจ้งเตือนล่วงหน้า 2 วันก่อนกำหนด (happy path)**
- Given ใกล้ถึงกำหนดส่งคำขอเบิกประจำเดือนของหน่วย
- When ถึงจำนวนวันที่กำหนดไว้ล่วงหน้าตามค่าเริ่มต้นของระบบ = **2 วัน** ก่อนกำหนดส่ง
- Then ระบบส่งแจ้งเตือนไปยังเจ้าหน้าที่ รพ.สต. ของหน่วยนั้นผ่านช่องทางอีเมล + LINE OA (BL-014)

**Scenario 2: ยังไม่ถึงกำหนดแจ้งเตือน (boundary — ไม่ส่งก่อนเวลา)**
- Given หน่วยหนึ่งกำหนดส่งคำขอเบิกวันที่ 25 ของเดือน
- When วันปัจจุบันคือวันที่ 22 (3 วันก่อนกำหนด — ยังไม่ถึงเกณฑ์ 2 วัน)
- Then ระบบยังไม่ส่งแจ้งเตือนล่วงหน้าให้หน่วยนั้น (ต้องรอถึงวันที่ 23 ซึ่งคือ 2 วันก่อนกำหนดพอดี)

**Scenario 3: แจ้งเตือนเฉพาะหน่วยที่ถึงกำหนด (edge — RBAC scoping)**
- Given หลายหน่วย รพ.สต. มีกำหนดส่งคำขอเบิกในวันที่ต่างกัน
- When ถึงกำหนดแจ้งเตือนล่วงหน้า 2 วันของหน่วยหนึ่ง
- Then ระบบแจ้งเตือนเฉพาะเจ้าหน้าที่ของหน่วยนั้น ไม่ส่งแจ้งเตือนไปยังหน่วยอื่นที่ยังไม่ถึงกำหนด

- หมายเหตุ: จำนวนวันล่วงหน้า (2 วัน) เป็น**ค่าเริ่มต้นของระบบ**ที่ Admin ปรับเปลี่ยนได้เองภายหลังผ่านหน้าจอ "ตั้งค่าระบบ" (ดู BL-043/FT-034 ด้านล่าง) — เมื่อ Admin ปรับค่านี้ ต้องทดสอบซ้ำว่ารอบแจ้งเตือนถัดไปใช้ค่าใหม่แทนค่าเดิมทันที (ดู BL-043 Scenario 1)

### BL-032 | กระทบยอดคงเหลือที่แจ้งเองกับยอดคงคลังที่ระบบคำนวณ

- **Feature:** [FT-008](../02-feature-list.md) — กระทบยอดคงเหลือที่แจ้งเองกับยอดคงคลังที่ระบบคำนวณ
- **อ้างอิง:** FR-1.9, FR-1.9a, FR-1.9b, US-1.6, FR-1.1a, FR-1.5 ([002](../01-spec/20260816-002-ncd-drug-requisition-core.md)); ดูจุดผูกกับ BL-004 (FT-002) ด้านบน — resolved ครบ 20260823 (4 รอบ)

**Scenario 1: พบความคลาดเคลื่อน — แจ้งเตือนทันทีด้วยข้อความคำต่อคำ (happy path, exact-match/zero-tolerance)**
- Given มียอดคงเหลือที่แจ้งเองและยอดคงคลังที่ระบบคำนวณของหน่วยเดียวกันในช่วงเวลาเดียวกัน
- When ระบบเปรียบเทียบสองค่านี้และพบว่าไม่ตรงกัน (ไม่ว่าจะต่างกันเท่าใด แม้เพียง 1 หน่วย — เปรียบเทียบแบบ exact-match ไม่มี tolerance band)
- Then ระบบแสดงข้อความ "ยอดคงเหลือที่เจ้าหน้าที่แจ้งกับยอดคงคลังที่ระบบคำนวณอัตโนมัติ ไม่ตรงกัน โปรดตรวจสอบ หากไม่แน่ใจให้ปรึกษา รพศ.ชร. (แม่ข่าย)" ทันที

**Scenario 2: ยอดสองค่าตรงกัน (happy path — ไม่มีความคลาดเคลื่อน)**
- Given ยอดคงเหลือที่แจ้งเองตรงกับยอดคงคลังที่ระบบคำนวณของหน่วยเดียวกันในช่วงเวลาเดียวกัน
- When ระบบเปรียบเทียบสองค่านี้
- Then ระบบต้องไม่แจ้งเตือนหรือสร้างขั้นตอนกระทบยอดใดๆ (ไม่มีความคลาดเคลื่อน)

**Scenario 3: เภสัชกรกรอกยอดที่ถูกต้องเองเมื่อคอนเฟิร์ม ระหว่างขั้นตอนอนุมัติระดับ 1 (happy path, เพิ่ม 20260824 — อ้างอิง FR-1.9b, BL-004)**
- Given ระบบแสดงข้อความแจ้งเตือนยอดไม่ตรงกัน (Scenario 1) ของคำขอที่กำลังอยู่ระหว่างการพิจารณาอนุมัติระดับ 1 (ดู BL-004/FT-002)
- When เภสัชกรผู้อนุมัติระดับ 1 กด "คอนเฟิร์ม" การกระทบยอดนี้เป็นส่วนหนึ่งของการพิจารณาอนุมัติระดับ 1 (ไม่ใช่ขั้นตอนแยก)
- Then ระบบต้องให้เภสัชกรกรอกยอดคงเหลือที่ตนพิจารณาแล้วว่าถูกต้องด้วยตนเอง (ไม่ใช่ระบบยึดยอดคงคลังที่คำนวณอัตโนมัติ FR-1.5 เป็นค่าที่ถูกต้องเองโดยอัตโนมัติ และไม่ใช่การรับทราบเฉยๆ โดยไม่แก้ไขค่า) และค่านี้กลายเป็นยอดคงเหลือที่ถูกต้อง/มีผลผูกพันต่อ (authoritative) แทนยอดคงเหลือปัจจุบันเดิมที่เจ้าหน้าที่ รพ.สต. รายงาน (FR-1.1a)

**Scenario 4: เภสัชกรพยายามคอนเฟิร์มโดยไม่กรอกยอดใหม่ (edge — validation, `[ถือว่า]`)**
- Given เภสัชกรผู้อนุมัติระดับ 1 กำลังคอนเฟิร์มการกระทบยอดของคำขอที่มีข้อความแจ้งเตือนยอดไม่ตรงกัน
- When พยายามกด "คอนเฟิร์ม" โดยไม่ได้กรอกยอดคงเหลือที่ถูกต้องในช่องกรอกค่าใหม่
- Then **[ถือว่า]** ระบบต้องปฏิเสธการคอนเฟิร์มและบังคับให้กรอกค่าก่อน เนื่องจาก FR-1.9b ระบุชัดว่าเภสัชกร "ต้องกรอกยอดคงเหลือที่ถูกต้องด้วยตนเอง" เสมอ (ไม่ใช่ทางเลือก) — เป็นสมมติฐาน validation มาตรฐานที่ยังไม่ได้รับการยืนยันจากเจ้าของข้อกำหนดโดยตรงว่าพฤติกรรม error message ที่แน่นอนควรเป็นอย่างไร

- หมายเหตุ: resolved ครบ 20260823 (4 รอบ) — (1) ต้องแจ้งเตือนด้วยข้อความคำต่อคำ ตีความเป็น exact-match/zero-tolerance (รอบ 1, FR-1.9) (2) เภสัชกรเป็นผู้ตรวจสอบ/คอนเฟิร์ม ไม่ใช่เจ้าหน้าที่ รพ.สต. เอง และการปรึกษา รพศ.ชร. เป็นทางเลือกเสริมไม่ใช่ขั้นตอนบังคับ (รอบ 3, FR-1.9a) (3) เภสัชกรกรอกยอดที่ถูกต้องเองเมื่อคอนเฟิร์ม กลายเป็นค่าที่มีผลผูกพันต่อ และขั้นตอนนี้รวมอยู่ในการอนุมัติระดับ 1 เดิม (BL-004) ไม่ใช่ขั้นตอนแยกใหม่ (รอบ 4, FR-1.9b) — ดู [002](../01-spec/20260816-002-ncd-drug-requisition-core.md) FR-1.9/FR-1.9a/FR-1.9b — **Scenario 3-4 เพิ่มโดย test-design-writer เมื่อ 20260824** เพื่อปิดช่องว่างที่ backlog.md/02-feature-list.md/03-user-journey ปิด Open Item รอบ 4 ไปแล้วตั้งแต่ 20260823-20260824 แต่ acceptance-criteria.md/test-cases ยังไม่เคยสะท้อนตาม — **ยังเหลือ `[ส่งต่อ]` ด้าน data model เท่านั้น**: ฟิลด์เก็บ "ยอดคงเหลือที่เภสัชกรกรอกยืนยันแล้ว (authoritative value)" ตาม FR-1.9b ยังไม่ถูกออกแบบอย่างเป็นทางการ รอ `/build-data-api-spec` — ไม่บล็อกงานเอกสารเฟสปัจจุบัน (ดู backlog.md BL-032)

- **อ้างอิง:** FR-2.1, US-2.2 ([003](../01-spec/20260816-003-stock-forecast-alerts.md))

**Scenario 1: คำนวณแบบ year-over-year (happy path)**
- Given มีข้อมูลย้อนหลัง 3 ปีของหน่วย/รายการยา
- When ระบบคำนวณเกณฑ์ safety stock ของเดือน X
- Then ใช้ค่าเฉลี่ยของเดือน X ย้อนหลัง 3 ปี ไม่ใช่ rolling average ทั่วไป

**Scenario 2: ไม่ปนข้อมูลข้ามเดือน (edge)**
- Given มีข้อมูลย้อนหลังของเดือนมีนาคมและเดือนอื่นในปีเดียวกัน

**Scenario 3: ข้อมูลพอดีขั้นต่ำ 3 ปี (boundary)**
- Given มีข้อมูลย้อนหลังพอดี 3 ปีของเดือน X
- When ระบบคำนวณ safety stock
- Then คำนวณค่าเฉลี่ยจากทั้ง 3 ปีที่มีครบ (ไม่ปฏิเสธเพราะข้อมูลพอดีขั้นต่ำ)

### BL-012 | ปรับปรุง Safety Stock ต่อเนื่องอัตโนมัติ

- **Feature:** [FT-010](../02-feature-list.md)
- **อ้างอิง:** FR-2.1b ([003](../01-spec/20260816-003-stock-forecast-alerts.md))

**Scenario 1: คำนวณยอดใช้จริงตามสูตร stock-flow (happy path)**
- Given มียอดคงเหลือต้นเดือน/ปลายเดือนที่ รพ.สต. รายงานมาพร้อมคำขอเบิก และยอดรับเข้าระหว่างเดือน
- When ระบบประมวลผลสิ้นเดือน
- Then คำนวณยอดใช้จริง = ยอดคงเหลือต้นเดือน + ยอดรับเข้า − ยอดคงเหลือปลายเดือน และนำไปปรับปรุง safety stock อัตโนมัติ

**Scenario 2: ไม่มีการใช้ยาเลยในเดือนนั้น (boundary)**
- Given ยอดคงเหลือต้นเดือน + ยอดรับเข้า = ยอดคงเหลือปลายเดือน
- When ระบบคำนวณยอดใช้จริง
- Then ได้ค่ายอดใช้จริง = 0 และนำค่านี้ไปปรับปรุง safety stock ตามสูตรปกติ (ไม่ error)

**Scenario 3: ค่ายอดใช้จริงติดลบผิดปกติ (edge)**
- Given ยอดคงเหลือปลายเดือนที่รายงานมามากกว่าผลรวมของยอดคงเหลือต้นเดือน+ยอดรับเข้า (ยอดใช้จริงติดลบ)
- When ระบบคำนวณ
- Then **[ถือว่า]** ระบบต้องตรวจพบค่าที่ผิดปกตินี้และไม่นำไปปรับปรุง safety stock โดยไม่แจ้งเตือน — หมายเหตุ (แก้ไข 20260824): นี่เป็นความผิดปกติเชิงคำนวณคนละจุดกับ BL-032/FR-1.9 (ซึ่งตรวจจับเฉพาะยอดคงเหลือที่แจ้งเอง vs. ยอดคงคลังที่ระบบคำนวณ ณ ช่วงเวลาเดียวกัน ไม่ใช่ยอดใช้จริงที่คำนวณได้ตอนสิ้นเดือน) — BL-032 ยืนยันครบแล้ว 20260823 (FR-1.9/FR-1.9a/FR-1.9b, ดู BL-032 ด้านล่าง) แต่ไม่ครอบคลุมกรณีนี้โดยตรง เกณฑ์การจัดการค่าผิดปกติของยอดใช้จริงติดลบใน Scenario นี้ยังคงเป็นสมมติฐาน QA มาตรฐานที่ยังไม่ได้รับการยืนยันจากเจ้าของข้อกำหนด

### BL-035 | สำรองข้อมูลรายวัน (Backup, RPO ≤ 24 ชั่วโมง)

- **Feature:** [FT-026](../02-feature-list.md) — สำรองข้อมูลรายวัน (Backup, RPO ≤ 24 ชั่วโมง)
- **อ้างอิง:** NFR Reliability/Backup & Recovery ([006](../01-spec/20260816-006-rbac-and-security-nfr.md) หัวข้อ "เพิ่มเติม 20260824") — resolved 20260824 (หลักการ), resolved 20260825 (ช่องทางแจ้งเตือนเมื่อล้มเหลว)

**Scenario 1: สำรองข้อมูลสำเร็จตามรอบรายวัน (happy path)**
- Given ระบบทำงานตามปกติ
- When ถึงรอบเวลาสำรองข้อมูลประจำวันที่กำหนดไว้
- Then ระบบสร้างสำเนาสำรองข้อมูลล่าสุดสำเร็จ และบันทึกผลสำเร็จของรอบนั้นไว้ให้ตรวจสอบได้

**Scenario 2: กู้คืนข้อมูลได้ภายในเป้าหมาย RPO (happy path)**
- Given ระบบล่มและต้องกู้คืนข้อมูลจากสำเนาสำรองล่าสุด
- When กู้คืนข้อมูล
- Then ข้อมูลที่กู้คืนได้ต้องไม่เก่ากว่าการสำรองครั้งล่าสุดเกิน 24 ชั่วโมง (RPO ≤ 24 ชั่วโมง)

**Scenario 3: รอบสำรองข้อมูลล้มเหลว (edge, resolved 20260825)**
- Given ถึงรอบเวลาสำรองข้อมูลประจำวัน
- When กระบวนการสำรองข้อมูลล้มเหลว (เช่น พื้นที่จัดเก็บเต็ม)
- Then ระบบต้องแจ้งเตือนผู้ดูแลระบบทันทีผ่าน**อีเมล + LINE OA** (ช่องทางเดียวกับการแจ้งเตือนอื่นของระบบ) ว่าการสำรองข้อมูลรอบนั้นไม่สำเร็จ แทนที่จะล้มเหลวแบบ silent

- หมายเหตุ: เป็น NFR เชิงระบบ/infrastructure ล้วนๆ (backup อัตโนมัติเบื้องหลัง) ไม่มีหน้าจอ/ปฏิสัมพันธ์ที่ผู้ใช้คนใดต้องลงมือทำ (สอดคล้องกับ [Feature List](../02-feature-list.md) FT-026 ที่ไม่ปรากฏเป็น step ใน user-journey ใดๆ) — scenario ด้านบนมุ่งทดสอบผลลัพธ์เชิงระบบ (สำเร็จ/กู้คืนได้ตามเป้าหมาย RPO) แทน user flow — resolved (20260824) ดู [006](../01-spec/20260816-006-rbac-and-security-nfr.md) หัวข้อ "เพิ่มเติม 20260824"

### BL-036 | ตรวจสอบสถานะคำขอเบิกซ้ำก่อนบันทึกทุกครั้ง (Optimistic Concurrency Check)

- **Feature:** [FT-027](../02-feature-list.md) — ตรวจสอบสถานะคำขอซ้ำก่อนบันทึกทุกครั้ง (Optimistic Concurrency Check)
- **อ้างอิง:** FR-6.5 ([006](../01-spec/20260816-006-rbac-and-security-nfr.md)) — เกี่ยวพันโดยตรงกับ BL-004 (FT-002) — resolved 20260824

**Scenario 1: ผู้ใช้คนแรกบันทึกสำเร็จตามปกติ (happy path)**
- Given คำขอเบิกหนึ่งรายการถูกเปิดพิจารณาโดยผู้ใช้ 2 คนพร้อมกัน
- When ผู้ใช้คนแรกกดบันทึกการอนุมัติ/แก้ไข
- Then ระบบตรวจสอบสถานะล่าสุดของคำขอก่อนบันทึก พบว่ายังไม่มีใครแก้ไขคำขอนี้ไปก่อนหน้า จึงบันทึกสำเร็จตามปกติ

**Scenario 2: ผู้ใช้คนที่สองถูกปฏิเสธเมื่อข้อมูลไม่ตรงกับเวอร์ชันล่าสุด (edge/error)**
- Given ผู้ใช้คนแรกบันทึกการอนุมัติ/แก้ไขคำขอนี้สำเร็จไปแล้ว (Scenario 1)
- When ผู้ใช้คนที่สองพยายามกดบันทึกการอนุมัติ/แก้ไขคำขอเดียวกันโดยยังใช้ข้อมูลเวอร์ชันเก่าก่อนที่คนแรกจะบันทึก
- Then ระบบปฏิเสธการบันทึกและแสดง error แจ้งว่ามีผู้อื่นแก้ไขคำขอนี้ไปแล้ว พร้อมแนะนำให้โหลดข้อมูลล่าสุดก่อนดำเนินการต่อ

**Scenario 3: เชื่อมโยงกับกฎห้ามอนุมัติคนเดียวกันสองระดับ (integration กับ BL-004)**
- Given เภสัชกรคนเดียวกันเป็นผู้อนุมัติระดับ 1 ของคำขอหนึ่งไปแล้ว
- When เภสัชกรคนเดียวกันพยายามอนุมัติระดับ 2 ของคำขอเดียวกัน
- Then ระบบต้องปฏิเสธการกระทำ ทั้งจากกฎ RBAC ของการอนุมัติสองระดับ (BL-004) และจากกลไกตรวจสอบสถานะคำขอก่อนบันทึกทุกครั้ง (BL-036) ที่ทำงานร่วมกัน

**Scenario 4: โหลดข้อมูลล่าสุดแล้วบันทึกซ้ำได้ตามปกติ (edge, `[ถือว่า]`)**
- Given ผู้ใช้คนที่สองได้รับ error จาก Scenario 2 แล้ว
- When โหลดข้อมูลคำขอเวอร์ชันล่าสุดใหม่และดำเนินการต่อตามสถานะปัจจุบัน
- Then **[ถือว่า]** ระบบต้องอนุญาตให้บันทึกได้ตามปกติ (ไม่ใช่การล็อกคำขอนั้นถาวร) เนื่องจากกลไกนี้เป็น validation ป้องกันการเขียนทับข้อมูลเก่า ไม่ใช่การบล็อกการทำงานต่อเนื่อง — เป็นสมมติฐาน UX มาตรฐานที่ยังไม่ได้รับการยืนยันจากเจ้าของข้อกำหนดโดยตรงว่าพฤติกรรมหลัง error ควรเป็นอย่างไร

### BL-037 | บังคับเปลี่ยนรหัสผ่านครั้งแรก + Session Timeout อัตโนมัติ (ทุก Role)

- **Feature:** [FT-028](../02-feature-list.md) — บังคับเปลี่ยนรหัสผ่านครั้งแรก + Session Timeout อัตโนมัติ (ทุก Role)
- **อ้างอิง:** FR-6.6, FR-6.7 ([006](../01-spec/20260816-006-rbac-and-security-nfr.md)) — resolved 20260824 (หลักการ), resolved 20260825 (ความยาวรหัสผ่านขั้นต่ำ)

**Scenario 1: บังคับเปลี่ยนรหัสผ่านเมื่อ login ครั้งแรก (happy path)**
- Given ผู้ใช้ (ทุก role) login เข้าระบบครั้งแรกด้วยรหัสผ่านเริ่มต้น
- When login สำเร็จ
- Then ระบบบังคับให้ตั้งรหัสผ่านใหม่ก่อนเข้าใช้งานหน้าจออื่นใดของระบบ

**Scenario 2: กรอกรหัสผ่านใหม่สั้นกว่าเกณฑ์ขั้นต่ำ (edge — validation, boundary)**
- Given ผู้ใช้กำลังตั้งรหัสผ่านใหม่ตาม Scenario 1
- When กรอกรหัสผ่านใหม่ยาว **7 ตัวอักษร** (สั้นกว่าเกณฑ์ขั้นต่ำ 1 ตัวอักษร เช่น "abc1234")
- Then ระบบต้องปฏิเสธและแจ้งว่ารหัสผ่านต้องมีความยาวอย่างน้อย **8 ตัวอักษร** ก่อนเข้าใช้งานได้

**Scenario 3: กรอกรหัสผ่านใหม่ยาวพอดีเกณฑ์ขั้นต่ำ ไม่มีอักขระพิเศษ (happy path — boundary)**
- Given ผู้ใช้กำลังตั้งรหัสผ่านใหม่ตาม Scenario 1
- When กรอกรหัสผ่านใหม่ยาว **8 ตัวอักษร** พอดี ประกอบด้วยตัวอักษร/ตัวเลขทั่วไปเท่านั้น ไม่มีอักขระพิเศษ (เช่น "abcd1234")
- Then ระบบต้องยอมรับรหัสผ่านนี้ (ไม่บังคับอักขระพิเศษ/ตัวเลขเพิ่มเติมตามที่ยืนยันแล้ว 20260825) และให้เข้าใช้งานหน้าจออื่นต่อได้

**Scenario 4: ตัด Session อัตโนมัติเมื่อไม่มีการใช้งาน (happy path)**
- Given ผู้ใช้ (ทุก role) login เข้าระบบแล้วไม่มีการใช้งานต่อเนื่องประมาณ 30 นาที
- When ครบเวลาที่กำหนด
- Then ระบบตัด session อัตโนมัติและต้อง login ใหม่ก่อนใช้งานต่อ

**Scenario 5: มีการใช้งานต่อเนื่องไม่ถูกตัด Session (boundary)**
- Given ผู้ใช้ใช้งานระบบต่อเนื่อง (มีการโต้ตอบกับระบบ) ก่อนครบ 30 นาที
- When ตรวจสอบสถานะ session ณ เวลาที่ครบ 30 นาทีนับจากจุดเริ่มต้นเดิม
- Then session ยังคงอยู่ ไม่ถูกตัดออกโดยอัตโนมัติ (ตัวจับเวลาต้องนับใหม่ทุกครั้งที่มีการใช้งาน)

### BL-038 | ยืนยันตัวตนสองปัจจัย (2FA/OTP) เฉพาะเภสัชกรผู้อนุมัติระดับ 1/2

- **Feature:** [FT-029](../02-feature-list.md) — ยืนยันตัวตนสองปัจจัย (2FA/OTP) เฉพาะเภสัชกรผู้อนุมัติระดับ 1/2
- **อ้างอิง:** FR-6.8 ([006](../01-spec/20260816-006-rbac-and-security-nfr.md)) — resolved 20260824 (หลักการ), resolved 20260825 (จำนวนครั้ง/อายุ/ช่องทาง OTP)

**Scenario 1: บัญชีเภสัชกรผู้อนุมัติต้องยืนยัน OTP เพิ่มเติม (happy path)**
- Given บัญชีเภสัชกรผู้อนุมัติระดับ 1 หรือระดับ 2 login ด้วย username/password ถูกต้อง
- When ระบบตรวจสอบสิทธิ์
- Then ระบบส่งรหัส OTP ไปยัง**อีเมลที่มีอยู่แล้วในระบบ**ของบัญชีนั้น (ช่องทางเดียวกับการแจ้งเตือนเดิมของ FT-012) และเรียกให้ยืนยันตัวตนเพิ่มเติมด้วย OTP ก่อนเข้าใช้งานหน้าจออื่นได้

**Scenario 2: กรอก OTP ถูกต้องภายในเวลาที่กำหนด (happy path)**
- Given เภสัชกรผู้อนุมัติได้รับรหัส OTP ทางอีเมลแล้ว
- When กรอกรหัส OTP ที่ถูกต้องภายใน **5 นาที** นับจากที่ระบบส่งรหัส
- Then ระบบอนุญาตให้เข้าใช้งานระบบได้ตามสิทธิ์ปกติ

**Scenario 3: กรอก OTP ผิดภายในจำนวนครั้งที่อนุญาต (edge — boundary, ยังไม่ล็อก)**
- Given เภสัชกรผู้อนุมัติกำลังยืนยันตัวตนด้วย OTP
- When กรอกรหัส OTP ผิดเป็นครั้งที่ 1 หรือครั้งที่ 2 (ยังไม่ครบ 3 ครั้ง)
- Then ระบบปฏิเสธรหัสที่กรอกและอนุญาตให้กรอกใหม่ได้อีก (ยังไม่ล็อกบัญชี)

**Scenario 4: กรอก OTP ผิดครบ 3 ครั้ง — ระบบล็อกชั่วคราว (error — boundary, resolved 20260825)**
- Given เภสัชกรผู้อนุมัติกรอกรหัส OTP ผิดมาแล้ว 2 ครั้งติดต่อกัน
- When กรอกรหัส OTP ผิดเป็นครั้งที่ 3
- Then ระบบล็อกบัญชีนั้นชั่วคราวไม่ให้ขอ/กรอก OTP ต่อ แล้ว**อนุญาตให้ขอรหัส OTP ชุดใหม่ได้อัตโนมัติหลังผ่านไป 5 นาที** — ไม่ต้องรอ Admin ปลดล็อกให้

**Scenario 5: OTP หมดอายุเกิน 5 นาที (error — boundary)**
- Given เภสัชกรผู้อนุมัติได้รับรหัส OTP มาแล้วเกิน **5 นาที**
- When กรอกรหัส OTP นั้น (แม้จะเป็นรหัสที่ถูกต้องตอนออก)
- Then ระบบปฏิเสธเนื่องจากรหัสหมดอายุแล้ว และให้ขอรหัส OTP ชุดใหม่

**Scenario 6: Role อื่นไม่บังคับ 2FA (RBAC scoping)**
- Given ผู้ใช้ role อื่น (เจ้าหน้าที่ รพ.สต., ผู้บริหาร, Admin) login ด้วย username/password ถูกต้อง
- When ระบบตรวจสอบสิทธิ์
- Then ระบบไม่เรียกให้ยืนยัน OTP เพิ่มเติม เข้าใช้งานได้ทันทีหลัง login สำเร็จ (หลังผ่านขั้นตอนบังคับเปลี่ยนรหัสผ่านครั้งแรกถ้ามีตาม BL-037)

### BL-039 | เข้ารหัสข้อมูลระหว่างส่งผ่านเครือข่าย (Data Encryption in Transit)

- **Feature:** [FT-030](../02-feature-list.md) — เข้ารหัสข้อมูลระหว่างส่งผ่านเครือข่าย (Data Encryption in Transit)
- **อ้างอิง:** FR-6.9 ([006](../01-spec/20260816-006-rbac-and-security-nfr.md)) — resolved 20260824 (เข้ารหัส in transit เสมอ), resolved 20260825 (พฤติกรรมปฏิเสธช่องทางไม่เข้ารหัส)

**Scenario 1: ข้อมูลเข้ารหัสระหว่างส่งเสมอ (happy path)**
- Given ผู้ใช้เข้าถึงระบบผ่านเครือข่าย
- When มีการรับส่งข้อมูลใดๆ ระหว่าง client กับระบบ (เช่น login, บันทึกคำขอเบิก, ดาวน์โหลดไฟล์)
- Then ข้อมูลถูกเข้ารหัสระหว่างการส่งผ่านเสมอ ไม่มีช่องทางรับส่งข้อมูลจริงแบบไม่เข้ารหัส

**Scenario 2: พยายามเข้าถึงผ่านช่องทางไม่เข้ารหัส (edge, resolved 20260825)**
- Given มีการพยายามเชื่อมต่อกับระบบผ่านช่องทางที่ไม่เข้ารหัส
- When ระบบตรวจพบการเชื่อมต่อประเภทนี้
- Then ระบบต้อง**ปฏิเสธการเชื่อมต่อทันทีพร้อมแสดง error** — ไม่ redirect ไปยังช่องทางที่เข้ารหัสให้อัตโนมัติ และไม่อนุญาตให้รับส่งข้อมูลจริงผ่านช่องทางที่ไม่เข้ารหัส

- หมายเหตุ: ไม่ครอบคลุมการเข้ารหัสข้อมูลที่จัดเก็บ (at rest) เพิ่มเติมในเฟสนี้ (resolved 20260824, สอดคล้องกับ PDPA ระดับพื้นฐาน BL-027) — เป็น NFR เชิงระบบล้วนๆ ที่เกิดขึ้นเบื้องหลังทุกการสื่อสาร ไม่มีปฏิสัมพันธ์ที่ผู้ใช้ต้องลงมือทำ

### BL-040 | รองรับเบราว์เซอร์ Evergreen 2 เวอร์ชันล่าสุด

- **Feature:** [FT-031](../02-feature-list.md) — รองรับเบราว์เซอร์ Evergreen 2 เวอร์ชันล่าสุด
- **อ้างอิง:** NFR Compatibility — เบราว์เซอร์ ([006](../01-spec/20260816-006-rbac-and-security-nfr.md)) — resolved 20260824

**Scenario 1: ใช้งานได้ครบถ้วนบนเบราว์เซอร์ยี่ห้อหลัก 2 เวอร์ชันล่าสุด (happy path)**
- Given ผู้ใช้เปิดระบบด้วยเบราว์เซอร์ยี่ห้อหลัก (เช่น Chrome, Edge, Firefox, Safari) เวอร์ชันล่าสุดหรือเวอร์ชันก่อนหน้าล่าสุด (2 เวอร์ชันล่าสุด)
- When ใช้งานฟังก์ชันหลักของทุก role
- Then ระบบแสดงผลและทำงานได้ถูกต้องครบถ้วนบนทุกยี่ห้อ/เวอร์ชันที่ระบุ

**Scenario 2: เบราว์เซอร์รุ่นเก่ากว่าที่กำหนด (edge — scope-confirmation)**
- Given ผู้ใช้เปิดระบบด้วยเบราว์เซอร์รุ่นเก่ากว่า 2 เวอร์ชันล่าสุดของยี่ห้อนั้น
- When ใช้งานฟังก์ชันหลัก
- Then ระบบไม่จำเป็นต้องรับประกันการทำงานที่ถูกต้อง — พฤติกรรมผิดปกติบนเบราว์เซอร์รุ่นเก่ากว่าที่กำหนดไม่ถือเป็นข้อบกพร่อง (defect) ตามขอบเขตที่ยืนยันแล้ว

### BL-041 | ขอบเขตรองรับเฉพาะขนาดเครือข่ายปัจจุบัน (Scalability)

- **Feature:** [FT-032](../02-feature-list.md) — ขอบเขต Scalability เฉพาะขนาดเครือข่ายปัจจุบัน
- **อ้างอิง:** NFR Scalability ([006](../01-spec/20260816-006-rbac-and-security-nfr.md)) — resolved 20260824

**Scenario 1: รองรับขนาดเครือข่ายปัจจุบันได้ตาม NFR อื่นที่เกี่ยวข้อง (happy path)**
- Given จำนวนหน่วยงาน (29 รพ.สต. + 1 รพ.แม่ข่าย) และผู้ใช้งานพร้อมกันไม่เกินหลักสิบราย ตามขนาดเครือข่ายปัจจุบัน
- When ทดสอบภาระงาน (load test) ตามขนาดนี้
- Then ระบบทำงานได้ตาม NFR Performance (ยอดคงคลังอัปเดตภายใน 5 วินาที, ดู BL-007) และ NFR Availability (BL-033) ที่กำหนดไว้ครบถ้วน

**Scenario 2: ไม่ต้องรองรับการขยายเครือข่ายในอนาคต (scope-confirmation)**
- Given ขอบเขตที่ยืนยันแล้วคือรองรับเฉพาะขนาดเครือข่ายปัจจุบัน ไม่เผื่อขยายไปยังอำเภอ/พื้นที่อื่น
- When วางแผนการทดสอบ performance/load
- Then ไม่ต้องออกแบบ/ทดสอบสถานการณ์ที่เกินขนาดเครือข่ายปัจจุบัน — ไม่ถือเป็นข้อบกพร่องหากระบบไม่รองรับโหลดที่เกินขอบเขตนี้

### BL-042 | Disaster Recovery (RTO ≤ 4 ชั่วโมง + ขั้นตอนสำรองแบบ Manual)

- **Feature:** [FT-033](../02-feature-list.md) — Disaster Recovery (RTO ≤ 4 ชั่วโมง + ขั้นตอนสำรองแบบ Manual)
- **อ้างอิง:** NFR Disaster Recovery ([006](../01-spec/20260816-006-rbac-and-security-nfr.md)) — resolved 20260824 (RTO/manual fallback), resolved 20260825 (กลไกนำข้อมูลกลับเข้าระบบ)

**Scenario 1: กู้คืนระบบภายในเป้าหมาย RTO (happy path)**
- Given ระบบล่มในเวลาราชการ
- When ทีมผู้ดูแลระบบดำเนินการกู้คืน
- Then ระบบกลับมาใช้งานได้ภายใน 4 ชั่วโมง (RTO ≤ 4 ชั่วโมงในเวลาราชการ)

**Scenario 2: มีขั้นตอนสำรองแบบ Manual ระหว่างรอกู้คืน (happy path)**
- Given ระบบยังไม่สามารถใช้งานได้ระหว่างรอกู้คืน
- When เจ้าหน้าที่/เภสัชกรต้องดำเนินงานเบิก-จ่ายยาต่อ
- Then มีขั้นตอนสำรองแบบ manual (เช่น บันทึกด้วยมือ/Excel ชั่วคราว) ที่นำมาใช้งานได้ทันทีโดยไม่ต้องรอระบบกลับมา

**Scenario 3: นำข้อมูลที่บันทึกระหว่าง Manual Fallback กลับเข้าระบบผ่าน Bulk Import (edge, resolved 20260825)**
- Given ใช้ขั้นตอนสำรองแบบ manual ระหว่างระบบล่ม (Scenario 2) และระบบกลับมาใช้งานได้ตามปกติแล้ว
- When ผู้ดูแลระบบ (Admin) เข้าหน้าจอ/เครื่องมือ Bulk Import และอัปโหลดไฟล์ Excel ที่บันทึกไว้ระหว่างระบบล่ม (ยืนยันแล้ว 20260825 ว่าเป็น Admin ไม่ใช่เจ้าหน้าที่/เภสัชกรที่บันทึกข้อมูลด้วยมือ)
- Then ระบบนำข้อมูลเข้าสู่ระบบเป็นชุด (bulk) แทนการกรอกซ้ำทีละรายการผ่านหน้าจอปกติ เพื่อไม่ให้ข้อมูลตกหล่น

- หมายเหตุ: Scenario 1-2 เป็นการทดสอบเชิง infrastructure/operational process มากกว่าฟังก์ชันในตัวแอป SmartSync เอง (ทีมผู้ดูแลระบบดำเนินการกู้คืนเป็นงานภายนอกแอป และ manual fallback คือการออกจากระบบไปใช้วิธีเดิมชั่วคราว) — **แต่ Scenario 3 (ยืนยันแล้ว 20260825) มีปฏิสัมพันธ์ในแอปจริง** (หน้าจอ Bulk Import) ต่างจากที่เคยเข้าใจว่า FT-033 ไม่มี user-observable interaction เลย — ต้องพิจารณาปรับ [Feature List](../02-feature-list.md)/[User Journey](../03-user-journey/)/[05-architecture.md](../05-architecture.md) ให้สะท้อนหน้าจอนี้ต่อไป (ไม่ใช่ขอบเขตของไฟล์นี้)

### BL-043 | Admin ปรับค่า Config ผ่านหน้าจอ

- **Feature:** [FT-034](../02-feature-list.md) — Admin ปรับค่า Config ผ่านหน้าจอระบบ
- **อ้างอิง:** FR-6.10 ([006](../01-spec/20260816-006-rbac-and-security-nfr.md)) — cross-ref BL-009b — resolved 20260824 (หลักการ), resolved 20260825 (ขอบเขต validation ต่อ Config Key)

**Scenario 1: Admin ปรับค่า Config ผ่านหน้าจอสำเร็จ (happy path)**
- Given Admin ต้องการปรับค่า config ที่กำหนดให้ปรับได้ เช่น Config Key "จำนวนวันแจ้งเตือนล่วงหน้าก่อนกำหนดส่งคำขอเบิกประจำเดือน" (BL-009b, ค่าปัจจุบัน = 2 วัน)
- When เข้าหน้าจอตั้งค่าระบบ ปรับค่าเป็น 3 วัน แล้วกดบันทึก
- Then ค่าใหม่ (3 วัน) มีผลทันทีกับรอบแจ้งเตือนถัดไปของ FT-007 โดยไม่ต้องแก้ไขโค้ด/รอรอบพัฒนาใหม่

**Scenario 2: ขอบเขตค่าที่ยอมรับได้กำหนดเฉพาะทีละ Config Key (edge — validation, resolved 20260825 สำหรับ BL-009b)**
- Given แต่ละ Config Key มีขอบเขตค่าที่ยอมรับได้ (min/max) เป็นของตัวเองแยกจากกัน ไม่ใช้กฎ validation เดียวกันทั้งหมด — Config Key "จำนวนวันแจ้งเตือนล่วงหน้า" (BL-009b) กำหนดขอบเขต **1 ถึง 30 วัน**
- When Admin กรอกค่าที่อยู่นอกขอบเขต min/max ของ Config Key นั้น (เช่น กรอก 0 หรือ 31 ให้ Config Key "จำนวนวันแจ้งเตือนล่วงหน้า")
- Then ระบบต้องปฏิเสธการบันทึกและแจ้งขอบเขตที่ยอมรับได้ของ Config Key นั้นโดยเฉพาะ (เช่น "กรุณากรอกค่าระหว่าง 1 ถึง 30") — **[ถือว่า]** ขอบเขต min/max ของ Config Key อื่นที่จะเพิ่มในอนาคต (นอกเหนือจาก BL-009b) ยังต้องยืนยันเป็นรายตัวเมื่อมีการเพิ่มจริง ไม่ใช้ค่า 1-30 นี้เป็นค่าเริ่มต้นตายตัว

**Scenario 3: Config Key หนึ่งผิดพลาดไม่กระทบ Config Key อื่น (edge — isolation)**
- Given Admin กำลังปรับ Config Key หนึ่งด้วยค่าที่ไม่ผ่าน validation ของ Key นั้น (Scenario 2)
- When ระบบปฏิเสธการบันทึกค่าของ Config Key นั้น
- Then ค่าปัจจุบันของ Config Key อื่นทั้งหมดยังคงเดิมไม่เปลี่ยนแปลง (การ validation ทำงานแยกเป็นรายรายการตาม Config Key)

**Scenario 4: Role อื่นพยายามเข้าถึงหน้าจอตั้งค่า (error — RBAC)**
- Given ผู้ใช้ role อื่น (ไม่ใช่ Admin) พยายามเข้าถึงหน้าจอตั้งค่า config ของระบบ
- When พยายามเข้าใช้งาน
- Then ระบบต้องปฏิเสธ/ไม่แสดงเมนูนี้ (สิทธิ์ปรับ config เป็นของ Admin เท่านั้น)

- หมายเหตุ: cross-ref BL-009b — ตัวเลขจำนวนวันแจ้งเตือนล่วงหน้า (2 วัน), ขอบเขต min/max ของ Config Key นี้ (1-30 วัน), และหลักการ validation แยกตามทีละ Config Key ยืนยันครบแล้ว 20260825 — Config Key อื่นที่จะเพิ่มในอนาคตยังต้องยืนยันขอบเขต min/max เป็นรายตัวเมื่อเพิ่มจริง — ดู [backlog.md](../backlog.md) BL-043
