## รายละเอียดต่อ Backlog Item

### Epic 1: เบิก-จ่ายยา NCD (Core)

### BL-001 | เจ้าหน้าที่ รพ.สต. เห็นยอดแนะนำเบิกอัตโนมัติ

- **Feature:** [FT-001](../02-feature-list.md) — สร้างคำขอเบิกยาประจำเดือน
- **อ้างอิง:** FR-1.1, US-1.0 ([002](../01-spec/20260816-002-ncd-drug-requisition-core.md))

**Scenario 1: แสดงยอดแนะนำเบิกอัตโนมัติ (happy path)**
- Given มีเกณฑ์ safety stock ที่คำนวณแล้วและยอดคงเหลือล่าสุดของหน่วย
- When เจ้าหน้าที่ รพ.สต. เปิดหน้าสร้างคำขอเบิกของเดือนนั้น
- Then ระบบแสดงยอดแนะนำเบิกต่อรายการยาโดยอัตโนมัติ

**Scenario 2: หน่วยยังไม่มีเกณฑ์ safety stock ที่คำนวณเสร็จ (edge)**
- Given หน่วยยังไม่มีเกณฑ์ safety stock ที่คำนวณเสร็จ (เช่น BL-011 ยังไม่เสร็จ หรือหน่วยเพิ่งเข้าร่วมเครือข่าย)
- When เจ้าหน้าที่เปิดหน้าสร้างคำขอเบิก
- Then **[ถือว่า]** ระบบต้องแจ้งให้ทราบว่ายังไม่มีค่ายอดแนะนำ ไม่ใช่แสดงค่า 0 ที่ทำให้เข้าใจผิดว่าไม่ต้องเบิก

**Scenario 3: หน่วยมีหลายรายการยาที่ต้องเบิกในเดือนนั้น**
- Given หน่วยมีรายการยาหลายรายการที่ต้องเบิกในรอบเดือนนั้น
- When เปิดหน้าสร้างคำขอ
- Then ระบบแสดงยอดแนะนำแยกต่อรายการยาทุกรายการ ไม่ใช่ยอดรวมเดียว

### BL-002 | เจ้าหน้าที่ รพ.สต. กรอกยอดคงเหลือ + ยืนยันคำขอเบิก

- **Feature:** [FT-001](../02-feature-list.md)
- **อ้างอิง:** FR-1.1a, US-1.1 ([002](../01-spec/20260816-002-ncd-drug-requisition-core.md))

**Scenario 1: กรอกยอดคงเหลือและยืนยันคำขอ (happy path)**
- Given เจ้าหน้าที่เห็นยอดแนะนำเบิกแล้ว
- When กรอกยอดคงเหลือปัจจุบันของแต่ละรายการและกดยืนยันคำขอ
- Then ระบบบันทึกคำขอสถานะ "รอการอนุมัติระดับ 1"

**Scenario 2: กรอกยอดคงเหลือเป็นค่าที่ไม่ถูกต้อง (validation error)**
- Given กำลังกรอกยอดคงเหลือของรายการยา
- When กรอกค่าที่ไม่ใช่ตัวเลข หรือค่าติดลบ
- Then **[ถือว่า]** ระบบต้องปฏิเสธการบันทึกและแจ้งให้แก้ไขก่อนยืนยันคำขอ (validation มาตรฐานของฟอร์มตัวเลข)

**Scenario 3: กรอกยอดคงเหลือไม่ครบทุกรายการ (edge)**
- Given มีรายการยาที่ยังไม่ได้กรอกยอดคงเหลือครบทุกรายการ
- When กดยืนยันคำขอ
- Then **[ถือว่า]** ระบบต้องไม่ยืนยันคำขอจนกว่าจะกรอกครบทุกรายการยา

### BL-003 | เจ้าหน้าที่ รพ.สต. กด "ขอปรึกษา"

- **Feature:** [FT-001](../02-feature-list.md)
- **อ้างอิง:** FR-1.1b, US-1.1b ([002](../01-spec/20260816-002-ncd-drug-requisition-core.md))

**Scenario 1: กด "ขอปรึกษา" แจ้งเภสัชกร (happy path)**
- Given เจ้าหน้าที่ไม่เห็นด้วยกับยอดแนะนำ
- When กดปุ่ม "ขอปรึกษา"
- Then ระบบส่ง alert ไปยังกลุ่มเภสัชกรผ่าน LINE OA ทันที และบันทึกเหตุการณ์นี้ลง audit trail (BL-008)

**Scenario 2: LINE OA ไม่พร้อมใช้งานชั่วคราว (error)**
- Given ช่องทาง LINE OA ไม่พร้อมใช้งานชั่วคราว (เช่น API ล่ม)
- When กดปุ่ม "ขอปรึกษา"
- Then **[ถือว่า]** ระบบต้องแจ้งผู้ใช้ว่าส่งแจ้งเตือนไม่สำเร็จ และยังคงบันทึกเหตุการณ์การกดขอปรึกษาไว้ใน audit trail (ไม่ปล่อยให้เงียบหายไปทั้งหมด)

**Scenario 3: กดขอปรึกษาแล้วยังแก้ไข/ยืนยันคำขอต่อได้**
- Given กดปุ่ม "ขอปรึกษา" แล้วแต่ยังไม่ได้ยืนยันคำขอ
- When เจ้าหน้าที่แก้ไขยอดคงเหลือ/ยอดแนะนำต่อ
- Then เจ้าหน้าที่ยังคงยืนยันคำขอในภายหลังได้ตามปกติ (ปุ่มขอปรึกษาไม่บล็อกการยืนยันคำขอ)

### BL-004 | เภสัชกรอนุมัติคำขอเบิกแบบสองระดับ

- **Feature:** [FT-002](../02-feature-list.md) — อนุมัติคำขอเบิกแบบสองระดับ
- **อ้างอิง:** FR-1.2, US-1.2, US-1.2b ([002](../01-spec/20260816-002-ncd-drug-requisition-core.md))

**Scenario 1: อนุมัติระดับ 1 (happy path)**
- Given คำขอสถานะ "รอการอนุมัติระดับ 1"
- When เภสัชกรระดับ 1 พิจารณาและอนุมัติ
- Then สถานะเปลี่ยนเป็น "รอการอนุมัติระดับ 2"

**Scenario 2: ปฏิเสธ/ปรับจำนวนที่ระดับ 1 (edge)**
- Given คำขอสถานะ "รอการอนุมัติระดับ 1"
- When เภสัชกรระดับ 1 ปฏิเสธคำขอ หรือปรับจำนวนก่อนอนุมัติ
- Then ระบบบันทึกจำนวนที่ปรับ (ถ้ามี) หรือสถานะ "ปฏิเสธ" พร้อมเหตุผล และบันทึกลง audit trail (BL-008)

**Scenario 3: อนุมัติระดับ 2 โดยคนละคน (happy path)**
- Given คำขอผ่านระดับ 1 แล้ว
- When เภสัชกรระดับ 2 (คนละคนกับระดับ 1) ยืนยัน
- Then สถานะเปลี่ยนเป็น "อนุมัติแล้ว"

**Scenario 4: เภสัชกรคนเดียวกันพยายามอนุมัติสองระดับ (error — RBAC)**
- Given เภสัชกรคนเดียวกันเป็นผู้อนุมัติระดับ 1
- When พยายามยืนยันระดับ 2 ของคำขอเดียวกัน
- Then ระบบต้องปฏิเสธการกระทำ (ดู DESIGN.md §4.3 — UI ควรซ่อน/disable ปุ่มระดับ 2 ด้วย ไม่พึ่ง backend validation อย่างเดียว)

### BL-005 | ระบบเปลี่ยนสถานะ "พร้อมส่งออก" / "จ่ายแล้ว"

- **Feature:** [FT-002](../02-feature-list.md)
- **อ้างอิง:** FR-1.3 ([002](../01-spec/20260816-002-ncd-drug-requisition-core.md))

**Scenario 1: เปลี่ยนสถานะเป็น "พร้อมส่งออก" (happy path)**
- Given คำขอผ่านอนุมัติครบสองระดับ
- When ระบบประมวลผล
- Then สถานะเปลี่ยนเป็น "พร้อมส่งออก" โดยอัตโนมัติ

**Scenario 2: เปลี่ยนสถานะเป็น "จ่ายแล้ว" ทันทีที่คอนเฟิร์ม (happy path)**
- Given เภสัชกรผู้อนุมัติระดับ 2 กด "คอนเฟิร์ม" (BL-020)
- When ระบบประมวลผล
- Then สถานะเปลี่ยนเป็น "จ่ายแล้ว" ทันที โดยไม่ต้องรอการยืนยันย้อนกลับจากฝ่ายคลังยาว่านำเข้า INVC สำเร็จ

**Scenario 3: คำขอที่ยังอนุมัติไม่ครบสองระดับ (edge)**
- Given คำขอผ่านการอนุมัติเพียงระดับเดียว (ยังไม่ครบ 2 ระดับ)
- When ตรวจสอบสถานะคำขอ
- Then สถานะต้องไม่ใช่ "พร้อมส่งออก" (ยังคงเป็น "รอการอนุมัติระดับ 2")

### BL-006 | เจ้าหน้าที่ รพ.สต. ยืนยันการรับยา

- **Feature:** [FT-003](../02-feature-list.md) — ยืนยันรับยาเข้าคลัง
- **อ้างอิง:** FR-1.4, US-1.3 ([002](../01-spec/20260816-002-ncd-drug-requisition-core.md))

**Scenario 1: ยืนยันรับยา (happy path)**
- Given ยาถูกจ่ายจาก รพ.แม่ข่ายแล้ว (สถานะ "จ่ายแล้ว")
- When เจ้าหน้าที่ยืนยันรับยาเข้าคลัง
- Then ยอดคงคลังของหน่วยอัปเดตทันที

**Scenario 2: เจ้าหน้าที่หน่วยอื่นพยายามยืนยันรับยา (error — RBAC)**
- Given เจ้าหน้าที่ รพ.สต. อื่นที่ไม่ใช่เจ้าของคำขอนี้
- When พยายามยืนยันรับยาแทนหน่วยอื่น
- Then ระบบต้องปฏิเสธการกระทำ เนื่องจากสิทธิ์เข้าถึงเฉพาะหน่วยตนเอง (อ้างอิง BL-024 RBAC)

**Scenario 3: พยายามยืนยันรับยาก่อนสถานะ "จ่ายแล้ว" (edge — state)**
- Given คำขอยังไม่ได้เปลี่ยนเป็นสถานะ "จ่ายแล้ว" (เช่น เภสัชกรยังไม่กดคอนเฟิร์ม)
- When เจ้าหน้าที่พยายามยืนยันรับยา
- Then ระบบต้องไม่อนุญาตให้ยืนยันรับยาก่อนสถานะ "จ่ายแล้ว"

### BL-007 | แสดงยอดคงคลังแบบ Real-time

- **Feature:** [FT-004](../02-feature-list.md) — แสดงยอดคงคลังแบบ Real-time
- **อ้างอิง:** FR-1.5 ([002](../01-spec/20260816-002-ncd-drug-requisition-core.md)); NFR Performance ([006](../01-spec/20260816-006-rbac-and-security-nfr.md))

**Scenario 1: อัปเดตยอดคงคลังภายใน 5 วินาที (happy path)**
- Given มีการบันทึกรับ/จ่ายยา
- When ระบบประมวลผล
- Then ยอดคงคลังของหน่วยที่เกี่ยวข้องอัปเดตภายใน 5 วินาที

**Scenario 2: อัปเดตเฉพาะหน่วยที่เกี่ยวข้อง (edge — RBAC scoping)**
- Given ผู้ใช้หลายคนจากหน่วยต่างกันดูยอดคงคลังพร้อมกัน (ไม่เกินหลักสิบรายตาม NFR Performance)
- When มีการบันทึกรับ/จ่ายที่หน่วยหนึ่ง
- Then เฉพาะยอดคงคลังของหน่วยที่เกี่ยวข้องเท่านั้นที่อัปเดต ไม่กระทบยอดของหน่วยอื่น

**Scenario 3: ผู้บริหารเห็นยอดอัปเดตผ่าน Dashboard**
- Given ผู้บริหาร login และดูยอดคงคลังผ่าน Dashboard
- When มีการบันทึกรับ/จ่ายที่หน่วยใดหน่วยหนึ่ง
- Then ยอดคงคลังที่ผู้บริหารเห็นในภาพรวม/drill-down อัปเดตภายในเวลาเดียวกัน (ภายใน 5 วินาที)

### BL-008 | Audit Trail ครบวงจร

- **Feature:** [FT-005](../02-feature-list.md) — Audit Trail การเบิก-จ่าย-อนุมัติ-รับ-ขอปรึกษา
- **อ้างอิง:** FR-1.6 ([002](../01-spec/20260816-002-ncd-drug-requisition-core.md))

**Scenario 1: บันทึกทุกเหตุการณ์ (happy path)**
- Given มีการเบิก/อนุมัติ/จ่าย/รับ/กด "ขอปรึกษา"
- When เหตุการณ์เกิดขึ้น
- Then ระบบบันทึกผู้กระทำ วันเวลา และรายละเอียดลง audit log ที่แก้ไขไม่ได้

**Scenario 2: พยายามแก้ไข/ลบ audit log โดยตรง (error)**
- Given มี audit log entry ที่บันทึกไว้แล้ว
- When ผู้ใช้ใดๆ (รวม Admin ในการใช้งานปกติ) พยายามแก้ไขหรือลบ entry นั้นโดยตรง
- Then ระบบต้องปฏิเสธ — กรณีแก้ไขข้อมูลธุรกิจฉุกเฉินโดย Admin (BL-025) ต้องสร้าง entry ใหม่พร้อมเหตุผล ไม่ใช่แก้ entry เดิม

**Scenario 3: บันทึกแยกผู้อนุมัติแต่ละระดับ**
- Given เภสัชกรอนุมัติระดับ 1 และระดับ 2 ของคำขอเดียวกัน (คนละคน)
- When ตรวจสอบ audit log ของคำขอนั้น
- Then เห็นบันทึกแยกของผู้อนุมัติแต่ละระดับครบถ้วน (ผู้กระทำ, วันเวลา)

### BL-009 | สร้างคำขอเบิกฉุกเฉินนอกรอบ

- **Feature:** [FT-006](../02-feature-list.md) — สร้างคำขอเบิกฉุกเฉินนอกรอบ
- **อ้างอิง:** FR-1.7, US-1.4 ([002](../01-spec/20260816-002-ncd-drug-requisition-core.md))

**Scenario 1: สร้างคำขอเบิกฉุกเฉิน (happy path)**
- Given ยาใกล้หมดกะทันหันนอกรอบเดือน
- When เจ้าหน้าที่สร้างคำขอเบิกฉุกเฉิน
- Then คำขอเข้าสู่ผังอนุมัติสองระดับเดียวกับคำขอปกติ (BL-004) พร้อมส่ง notify ทันทีให้ผู้อนุมัติทั้งสองระดับ

**Scenario 2: แยกแยะคำขอฉุกเฉินจากคำขอปกติ (edge)**
- Given มีทั้งคำขอปกติและคำขอฉุกเฉินของหน่วยเดียวกันในเดือนเดียวกัน
- When เภสัชกรเข้าดูรายการคำขอที่รอดำเนินการ
- Then **[ถือว่า]** ระบบต้องแสดง/ระบุคำขอฉุกเฉินให้แยกแยะได้จากคำขอปกติ (เช่น ป้าย/สถานะพิเศษ) เนื่องจากการ notify ทันทีบ่งชี้ความเร่งด่วนที่ควรมองเห็นได้

**Scenario 3: บันทึกประเภทคำขอลง audit trail**
- Given สร้างคำขอเบิกฉุกเฉินแล้ว
- When ตรวจสอบ audit trail
- Then บันทึกว่าคำขอนี้เป็นประเภทฉุกเฉิน (Off-cycle) แยกจากคำขอปกติ

### BL-009b | แจ้งเตือนล่วงหน้าก่อนกำหนดส่งคำขอเบิกประจำเดือน

- **Feature:** [FT-007](../02-feature-list.md) — แจ้งเตือนล่วงหน้าก่อนกำหนดส่งคำขอเบิกประจำเดือน
- **อ้างอิง:** FR-1.8, US-1.5 ([002](../01-spec/20260816-002-ncd-drug-requisition-core.md))

**Scenario 1: แจ้งเตือนล่วงหน้าก่อนกำหนด (happy path, จำนวนวัน `[รอยืนยัน]`)**
- Given ใกล้ถึงกำหนดส่งคำขอเบิกประจำเดือนของหน่วย
- When ถึงจำนวนวันที่กำหนดไว้ล่วงหน้า **`[รอยืนยัน]` จำนวนวันที่แน่นอน**
- Then ระบบส่งแจ้งเตือนไปยังเจ้าหน้าที่ รพ.สต. ของหน่วยนั้นผ่านช่องทางอีเมล + LINE OA (BL-014)

**Scenario 2: แจ้งเตือนเฉพาะหน่วยที่ถึงกำหนด (edge — RBAC scoping)**
- Given หลายหน่วย รพ.สต. มีกำหนดส่งคำขอเบิกในวันที่ต่างกัน
- When ถึงกำหนดแจ้งเตือนล่วงหน้าของหน่วยหนึ่ง
- Then ระบบแจ้งเตือนเฉพาะเจ้าหน้าที่ของหน่วยนั้น ไม่ส่งแจ้งเตือนไปยังหน่วยอื่นที่ยังไม่ถึงกำหนด

- หมายเหตุ: `[รอยืนยัน]` จำนวนวันล่วงหน้าที่ควรแจ้งเตือนยังค้างอยู่ใน backlog.md/spec 002 — ต้องยืนยันค่านี้ก่อนกำหนด test data ที่แน่นอนสำหรับทดสอบจริง

### BL-032 | กระทบยอดคงเหลือที่แจ้งเองกับยอดคงคลังที่ระบบคำนวณ

- **Feature:** [FT-008](../02-feature-list.md) — กระทบยอดคงเหลือที่แจ้งเองกับยอดคงคลังที่ระบบคำนวณ
- **อ้างอิง:** FR-1.1a, FR-1.5 ([002](../01-spec/20260816-002-ncd-drug-requisition-core.md))

**Scenario 1: พบความคลาดเคลื่อน (พฤติกรรมหลัก `[รอยืนยัน]`)**
- Given มียอดคงเหลือที่แจ้งเองและยอดคงคลังที่ระบบคำนวณของหน่วยเดียวกันในช่วงเวลาเดียวกัน
- When ระบบเปรียบเทียบสองค่านี้และพบว่าไม่ตรงกัน
- Then `[รอยืนยัน]` ต้องแจ้งเตือนหรือไม่ และมีขั้นตอนกระทบยอดอย่างไร รวมถึงเกณฑ์ความคลาดเคลื่อนที่ยอมรับได้ — ยังไม่สามารถเขียนสถานการณ์ทดสอบที่เป็นรูปธรรมเพิ่มเติมได้จนกว่าจะยืนยันจากเจ้าของข้อกำหนด (เภสัชกร)

**Scenario 2: ยอดสองค่าตรงกัน (happy path — ไม่มีความคลาดเคลื่อน)**
- Given ยอดคงเหลือที่แจ้งเองตรงกับยอดคงคลังที่ระบบคำนวณของหน่วยเดียวกันในช่วงเวลาเดียวกัน
- When ระบบเปรียบเทียบสองค่านี้
- Then ระบบต้องไม่แจ้งเตือนหรือสร้างขั้นตอนกระทบยอดใดๆ (ไม่มีความคลาดเคลื่อน)

### BL-010 | นำเข้าข้อมูลประวัติเบิก-จ่ายย้อนหลัง (Data Migration)

**Scenario 1: นำเข้าข้อมูลครบ (happy path)**
- Given ได้รับไฟล์ข้อมูลย้อนหลัง 3 ปีจากเภสัชกร/กระบวนการเดิม
- When นำเข้าสู่ระบบ
- Then ข้อมูลครบทุกหน่วย/รายการยาพร้อมสำหรับคำนวณ safety stock

**Scenario 2: ข้อมูลบางหน่วยไม่ครบ 3 ปี (edge)**
- Given ไฟล์ข้อมูลย้อนหลังของบางหน่วย/บางรายการยาไม่ครบ 3 ปีเต็ม (เช่น หน่วยเพิ่งเปิดใหม่)
- When นำเข้าสู่ระบบ
- Then **[ถือว่า]** ระบบต้องนำเข้าข้อมูลเท่าที่มีได้โดยไม่ทำให้กระบวนการนำเข้าทั้งหมดล้มเหลว และต้องมีวิธีระบุว่าหน่วย/รายการยานั้นข้อมูลย้อนหลังไม่ครบ 3 ปี

**Scenario 3: ไฟล์ข้อมูลผิดรูปแบบ (error)**
- Given ไฟล์ข้อมูลมีรูปแบบไม่ตรงตามที่ระบบคาดหวัง (เช่น คอลัมน์ขาดหาย)
- When พยายามนำเข้า
- Then ระบบต้องแจ้ง error พร้อมระบุตำแหน่ง/แถวที่ผิดพลาด แทนที่จะนำเข้าข้อมูลบางส่วนแบบเงียบๆ

### BL-011 | คำนวณเกณฑ์ Safety Stock เริ่มต้น (Year-over-year)

- **Feature:** [FT-010](../02-feature-list.md) — คำนวณและปรับปรุงเกณฑ์ Safety Stock
- **อ้างอิง:** FR-2.1, US-2.2 ([003](../01-spec/20260816-003-stock-forecast-alerts.md))

**Scenario 1: คำนวณแบบ year-over-year (happy path)**
- Given มีข้อมูลย้อนหลัง 3 ปีของหน่วย/รายการยา
- When ระบบคำนวณเกณฑ์ safety stock ของเดือน X
- Then ใช้ค่าเฉลี่ยของเดือน X ย้อนหลัง 3 ปี ไม่ใช่ rolling average ทั่วไป

**Scenario 2: ไม่ปนข้อมูลข้ามเดือน (edge)**
- Given มีข้อมูลย้อนหลังของเดือนมีนาคมและเดือนอื่นในปีเดียวกัน
- When ระบบคำนวณ safety stock ของเดือนมีนาคม
- Then ใช้เฉพาะข้อมูลของเดือนมีนาคมย้อนหลัง 3 ปีเท่านั้น ไม่ปนกับข้อมูลเดือนอื่น

**Scenario 3: ข้อมูลพอดีขั้นต่ำ 3 ปี (boundary)**
- Given มีข้อมูลย้อนหลังพอดี 3 ปีของเดือน X
- When ระบบคำนวณ safety stock
- Then คำนวณค่าเฉลี่ยจากทั้ง 3 ปีที่มีครบ (ไม่ปฏิเสธเพราะข้อมูลพอดีขั้นต่ำ)

### BL-012 | ปรับปรุง Safety Stock ต่อเนื่องอัตโนมัติ

- **Feature:** [FT-010](../02-feature-list.md)
- **อ้างอิง:** FR-2.1b ([003](../01-spec/20260816-003-stock-forecast-alerts.md))

**Scenario 1: คำนวณยอดใช้จริงตามสูตร stock-flow (happy path)**
- Given มียอดคงเหลือต้นเดือน/ปลายเดือนที่ รพ.สต. รายงานมาพร้อมคำขอเบิก และยอดรับเข้าระหว่างเดือน
- When ระบบประมวลผลสิ้นเดือน
- Then คำนวณยอดใช้จริง = ยอดคงเหลือต้นเดือน + ยอดรับเข้า − ยอดคงเหลือปลายเดือน และนำไปปรับปรุง safety stock อัตโนมัติ

**Scenario 2: ไม่มีการใช้ยาเลยในเดือนนั้น (boundary)**
- Given ยอดคงเหลือต้นเดือน + ยอดรับเข้า = ยอดคงเหลือปลายเดือน
- When ระบบคำนวณยอดใช้จริง
- Then ได้ค่ายอดใช้จริง = 0 และนำค่านี้ไปปรับปรุง safety stock ตามสูตรปกติ (ไม่ error)

**Scenario 3: ค่ายอดใช้จริงติดลบผิดปกติ (edge)**
- Given ยอดคงเหลือปลายเดือนที่รายงานมามากกว่าผลรวมของยอดคงเหลือต้นเดือน+ยอดรับเข้า (ยอดใช้จริงติดลบ)
- When ระบบคำนวณ
- Then **[ถือว่า]** ระบบต้องตรวจพบค่าที่ผิดปกตินี้และไม่นำไปปรับปรุง safety stock โดยไม่แจ้งเตือน — เกี่ยวข้องกับผลการตัดสินใจของ BL-032 (กระทบยอด) ที่ยัง `[รอยืนยัน]`

### BL-013 | แจ้งเตือนเมื่อยอดคงคลังต่ำกว่า Safety Stock

- **Feature:** [FT-011](../02-feature-list.md) — แจ้งเตือนเมื่อยาใกล้หมด
- **อ้างอิง:** FR-2.2, US-2.1 ([003](../01-spec/20260816-003-stock-forecast-alerts.md))

- When ระบบตรวจพบ

- Given ยอดคงคลังของหน่วยเท่ากับเกณฑ์ safety stock พอดี (ไม่ต่ำกว่า)
- When ระบบตรวจสอบ

**Scenario 3: แจ้งเตือนเฉพาะหน่วยตนเอง (RBAC scoping)**
- Given ยอดคงคลังของหลายหน่วยต่ำกว่าเกณฑ์พร้อมกัน
- When ระบบส่งแจ้งเตือน
- Then แต่ละหน่วยได้รับแจ้งเตือนเฉพาะของหน่วยตนเอง ไม่เห็นแจ้งเตือนของหน่วยอื่น

### BL-014 | ช่องทางแจ้งเตือนผ่านอีเมล + LINE OA

- **Feature:** [FT-012](../02-feature-list.md) — ช่องทางแจ้งเตือนผ่านอีเมลและ LINE OA
- **อ้างอิง:** FR-2.3 ([003](../01-spec/20260816-003-stock-forecast-alerts.md))

- Given ช่องทางหนึ่ง (เช่น อีเมล) ส่งไม่สำเร็จชั่วคราว
- When ระบบส่ง notify

- Given ยังไม่ได้ตั้งค่า SMTP หรือ LINE OA API/Webhook
- When ระบบพยายามส่ง notify
- Then ระบบต้องไม่ล้มเหลวแบบ silent — ควรบันทึกข้อผิดพลาดของการตั้งค่าไว้ให้ผู้ดูแลระบบตรวจสอบได้

### BL-017 | Drill-down ดูรายละเอียดรายหน่วย

- **Feature:** [FT-014](../02-feature-list.md)
- **อ้างอิง:** FR-3.5, US-3.3 ([004](../01-spec/20260816-004-management-dashboard.md))

- Given ผู้บริหารดู Dashboard ภาพรวม

- Then ไม่ต้องมีกระบวนการ DPO/Data Protection Impact Assessment (DPIA) อย่างเป็นทางการสำหรับระบบนี้

### BL-028 | System Access Log (Login/Logout + IP Address)

- **Feature:** [FT-024](../02-feature-list.md) — System Access Log และการเก็บรักษาข้อมูลตามกฎหมาย
- **อ้างอิง:** FR-6.1 ([006](../01-spec/20260816-006-rbac-and-security-nfr.md))

**Scenario 1: บันทึก login/logout พร้อม IP (happy path)**
- Given ผู้ใช้ login หรือ logout
- When เหตุการณ์เกิดขึ้น
- Then ระบบบันทึกผู้ใช้ วันเวลา และ IP Address ที่ใช้เข้าถึงลง log แยกจาก audit trail ทางธุรกิจ

**Scenario 2: Login ไม่สำเร็จ (edge)**
- Given ผู้ใช้กรอกรหัสผ่านผิด (login ไม่สำเร็จ)
- When ระบบประมวลผล
- Then **[ถือว่า]** ระบบควรบันทึกความพยายาม login ที่ไม่สำเร็จไว้ใน System Access Log ด้วย (พร้อม IP Address) เพื่อรองรับการตรวจสอบด้านความปลอดภัยตามเจตนารมณ์ของ FR-6.1

**Scenario 3: บันทึกเวลา logout แยกจากเวลา login**
- Given ผู้ใช้ logout ออกจากระบบ
- When เหตุการณ์เกิดขึ้น
- Then ระบบบันทึกเวลา logout แยกจากเวลา login ของ session เดียวกัน

### BL-029 | เก็บ Audit Trail + Access Log อย่างน้อย 90 วัน

- **Feature:** [FT-024](../02-feature-list.md)
- **อ้างอิง:** FR-6.2 ([006](../01-spec/20260816-006-rbac-and-security-nfr.md))

**Scenario 1: เก็บรักษาอย่างน้อย 90 วัน (happy path)**
- Given มี audit trail และ access log สะสม
- When ครบกำหนด
- Then ข้อมูลย้อนหลังอย่างน้อย 90 วันยังคงอยู่ครบถ้วน

**Scenario 2: ไม่ลบข้อมูลอัตโนมัติหลังพ้น 90 วัน (happy path)**
- Given ข้อมูลพ้น 90 วันไปแล้ว
- When ถึงเวลาที่ควรพิจารณาลบ
- Then ระบบไม่ลบข้อมูลอัตโนมัติ (เก็บต่อเนื่องไม่มีกำหนด)

**Scenario 3: ข้อมูลอายุครบ 90 วันพอดี (boundary)**
- Given ข้อมูล audit/access log มีอายุครบ 90 วันพอดี
- When ตรวจสอบ
- Then ข้อมูลนั้นยังคงอยู่ในระบบ (ไม่ถูกลบ ณ วันที่ครบ 90 วันพอดี)

### BL-030 | Consent Banner ตอน Login ครั้งแรก

- **Feature:** [FT-023](../02-feature-list.md)
- **อ้างอิง:** FR-6.3 ([006](../01-spec/20260816-006-rbac-and-security-nfr.md))

**Scenario 1: แสดง Consent Banner ครั้งแรก (happy path)**
- Given ผู้ใช้ login เข้าระบบครั้งแรก
- When ยังไม่เคยกดยินยอม Consent
- Then ระบบแสดง Consent Banner ก่อนเข้าใช้งาน

**Scenario 2: ไม่แสดงซ้ำหลังยินยอมแล้ว (happy path)**
- Given ผู้ใช้กดยินยอมแล้ว
- When login ครั้งถัดไป
- Then ระบบไม่แสดง Consent Banner ซ้ำอีก

**Scenario 3: เนื้อหาไม่มีข้อความ Google Analytics (content check)**
- Given ระบบแสดง Consent Banner
- When ผู้ใช้อ่านเนื้อหา
- Then เนื้อหาต้องระบุว่าระบบเก็บ IP Address แต่ต้องไม่มีข้อความเกี่ยวกับ Google Analytics หรือเครื่องมือวิเคราะห์การใช้งานเว็บใดๆ (ยืนยันแล้วว่าไม่ใช้ในเฟสนี้)

**Scenario 4: ผู้ใช้ไม่กดยินยอม (edge)**
- Given ผู้ใช้ login ครั้งแรกและเห็น Consent Banner
- When ผู้ใช้ปิดหน้าต่างโดยไม่กดยินยอม
- Then **[ถือว่า]** ระบบต้องไม่อนุญาตให้เข้าใช้งานส่วนอื่นของระบบจนกว่าจะกดยินยอม

### BL-031 | บันทึกวันเวลาที่กดยินยอม Consent

- **Feature:** [FT-023](../02-feature-list.md)
- **อ้างอิง:** FR-6.4 ([006](../01-spec/20260816-006-rbac-and-security-nfr.md)); ส่วนหนึ่งของ FR-6.1 (BL-028)

**Scenario 1: บันทึกวันเวลายินยอม (happy path)**
- Given ผู้ใช้กดยินยอม Consent
- When ระบบประมวลผล
- Then บันทึกวันเวลาที่ยินยอมลง System Access Log

**Scenario 2: ไม่สร้างบันทึกซ้ำ (edge)**
- Given ผู้ใช้เคยกดยินยอมไปแล้วในการ login ครั้งแรก
- When login ครั้งถัดไปที่ไม่แสดง Consent Banner ซ้ำ
- Then ระบบไม่สร้างบันทึกเวลายินยอมใหม่ซ้ำ (บันทึกเพียงครั้งเดียวตอนยินยอมจริง)

### BL-033 | ระบบพร้อมใช้งานเฉพาะเวลาราชการ

- **Feature:** [FT-025](../02-feature-list.md) — ระบบพร้อมใช้งานเฉพาะเวลาราชการ
- **อ้างอิง:** NFR Availability ([006](../01-spec/20260816-006-rbac-and-security-nfr.md))

**Scenario 1: พร้อมใช้งานในเวลาราชการ (happy path)**
- Given ระบบเปิดให้ใช้งานในช่วง 08:00-16:30 น. จันทร์-ศุกร์
- When ผู้ใช้เข้าใช้งานในช่วงเวลานี้
- Then ระบบพร้อมใช้งานตามปกติ

**Scenario 2: นอกเวลาราชการ (edge — ไม่บังคับ 24/7)**
- Given อยู่นอกช่วงเวลาราชการ (เช่น เย็นวันธรรมดาหรือวันหยุดสุดสัปดาห์)
- When ผู้ใช้พยายามเข้าใช้งาน
- Then ระบบไม่จำเป็นต้องพร้อมใช้งาน 24/7 (ไม่ถือเป็นข้อบกพร่องหากไม่พร้อมใช้งานนอกเวลานี้)
