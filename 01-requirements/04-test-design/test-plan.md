## 1. ภาพรวมและวัตถุประสงค์ (Overview & Objectives)

SmartSync เป็นระบบสนับสนุนการเบิก-จ่ายยากลุ่ม NCD ระหว่าง รพ.เชียงรายประชานุเคราะห์ (รพ.แม่ข่าย) และเครือข่าย รพ.สต. 29 แห่ง — เป้าหมายเชิงตัวชี้วัด (KPI) ของโครงการคือลดอัตราหมุนเวียนคงคลัง (Inventory Turnover) ของ รพ.สต. จากปัจจุบัน **3 เดือน** เหลือ **≤ 1.5 เดือน** พร้อมลดความถี่การเบิกยาด่วนนอกรอบ (ดู [spec 001](../01-spec/20260816-001-project-scope-and-problem-background.md))

**วัตถุประสงค์ของการทดสอบ:**
- ยืนยันว่า Epic 1 (เบิก-จ่ายยา NCD Core) และ Epic 2 (พยากรณ์สต็อก) ซึ่งเป็นกลไกหลักที่ตอบ KPI ทำงานถูกต้องตรงตามสูตรคำนวณเดียวกันที่ผู้เบิกและผู้คัดกรองใช้ร่วมกัน (แก้ Root Cause เรื่องเกณฑ์คำนวณคนละมาตรฐาน)
- ยืนยันว่าการควบคุมสิทธิ์ (RBAC), การอนุมัติสองระดับ, และ audit trail ทำงานถูกต้องครบถ้วนก่อนเข้าสู่การใช้งานจริง เนื่องจากเกี่ยวข้องกับการจ่ายยาจริงและข้อมูลที่เชื่อมโยงถึงผู้ป่วยทางอ้อม
- ยืนยันว่าการเชื่อมต่อกับ INVC (Epic 4) ผลิตไฟล์ที่นำเข้าได้จริงโดยไม่ต้องแก้ไขเพิ่มเติม (เป็นความเสี่ยงสูงสุดของโครงการ — ดู §5)

## 2. ขอบเขตการทดสอบ (Scope)

- **อยู่ในขอบเขต:** ทั้ง 25 Feature (FT-001–FT-025) ครอบคลุม 5 Epic ตาม [Feature List](../02-feature-list.md) — Epic 1 (เบิก-จ่าย Core), Epic 2 (พยากรณ์สต็อก/แจ้งเตือน), Epic 3 (รายงาน/Dashboard), Epic 4 (เชื่อมต่อระบบเดิม), Epic 5 (RBAC/NFR)
- **นอกขอบเขต (เฟสนี้):**
  - **FT-019 (เชื่อมต่อ JHCIS/myPCU โดยตรง, BL-023):** Priority Won't ในเฟสนี้ — มีเพียง scenario ยืนยันขอบเขตว่าไม่มี integration จริงเกิดขึ้น ไม่ใช่การทดสอบฟังก์ชันที่พัฒนาจริง
  - **FT-018 (รูปแบบไฟล์ Excel ให้ตรงกับ INVC, BL-022):** `[รอยืนยัน — บล็อกการพัฒนา]` ยังไม่มีรูปแบบคอลัมน์ INVC ที่แน่นอนจากฝ่ายดูแล INVC — **ทดสอบจริงไม่ได้จนกว่าจะได้รับการยืนยัน** (ดูความเสี่ยงใน §5) ทำให้ทั้ง Epic 4 (FT-017, FT-018) ทดสอบ end-to-end ไม่ได้ครบวงจรในเฟสนี้จนกว่าจุดนี้จะปลดล็อก
  - งบประมาณ/กรอบเวลาโครงการ, เอกสารนโยบายเบิกจ่ายยา NCD ของเขตสุขภาพ, การจัดซื้อยา (Procurement)/ระบบบัญชีการเงิน — นอกขอบเขตของ requirement เองตาม [spec 001](../01-spec/20260816-001-project-scope-and-problem-background.md)

## 3. กลยุทธ์/ประเภทการทดสอบ (Test Strategy & Types)

| ประเภท | คำอธิบาย | ครอบคลุม |
|---|---|---|
| Functional/System Testing | ทดสอบ flow หลักตาม Acceptance Criteria ของแต่ละ BL-ID — สร้างคำขอ, คำนวณยอดแนะนำ/safety stock, อนุมัติสองระดับ, รับยา, แจ้งเตือน, Dashboard | ทุก Feature (FT-001–FT-025) |
| Integration Testing | ทดสอบการส่งออกไฟล์ Excel ไปยัง INVC (นำเข้า/ส่งออกไฟล์แบบ Manual batch ไม่ใช่ API real-time) และช่องทางแจ้งเตือนอีเมล/LINE OA — **[ถือว่า]** ต้องมี sandbox/test account ของ SMTP, LINE OA API, และไฟล์ตัวอย่างที่ INVC นำเข้าได้จริงก่อนจึงจะทดสอบ integration ได้ครบ **Epic 4 (FT-017/FT-018) ถูกบล็อกโดย BL-022 `[รอยืนยัน]`** จนกว่าจะได้รูปแบบคอลัมน์ INVC จากฝ่ายดูแลระบบ | FT-012, FT-017, FT-018 |
| RBAC / Security Testing | ทดสอบว่าแต่ละ Role (เจ้าหน้าที่ รพ.สต., เภสัชกรระดับ 1/2, ผู้บริหาร, Admin) เห็น/แก้ไขได้เฉพาะข้อมูลตามสิทธิ์ที่กำหนด รวมกฎห้ามอนุมัติซ้ำสองระดับด้วยคนเดียวกัน, การปฏิเสธการเข้าถึงข้ามหน่วย, PDPA Consent, System Access Log | FT-002, FT-020, FT-021, FT-023, FT-024 |
| Performance Testing | ทดสอบว่ายอดคงคลังอัปเดตภายใน **5 วินาที** หลังบันทึกรับ/จ่าย ภายใต้จำนวนผู้ใช้งานพร้อมกันตามขนาดจริงของเครือข่าย (29 รพ.สต. + 1 รพ.แม่ข่าย รวมไม่เกินหลักสิบราย) | FT-004 |
| Usability Testing | ทดสอบว่า UI ใช้งานได้ครบถ้วนบน Desktop-first (คอมพิวเตอร์/โน้ตบุ๊ก) โดยไม่ต้องรองรับ responsive มือถือ/แท็บเล็ตเต็มรูปแบบ | FT-022 |
| UAT (User Acceptance Testing) | ให้ตัวแทนผู้ใช้จริงแต่ละ Role ทดสอบ flow ของตนเองแบบ end-to-end ตาม User Journey ของ role นั้น — เจ้าหน้าที่ รพ.สต. ([staff-hph-journey.md](../03-user-journey/staff-hph-journey.md)), เภสัชกร ([pharmacist-journey.md](../03-user-journey/pharmacist-journey.md)), ผู้บริหาร ([executive-journey.md](../03-user-journey/executive-journey.md)), ผู้ดูแลระบบ ([admin-journey.md](../03-user-journey/admin-journey.md)) | ทุก Feature ที่เกี่ยวข้องกับ role นั้นๆ |
| Regression Testing | ทดสอบซ้ำ flow หลักหลังแก้ไข/เพิ่ม feature ใหม่ในแต่ละรอบ Sprint โดยเฉพาะจุดที่มี cross-epic dependency (ดู §5) เพื่อยืนยันว่าการแก้ไข Epic หนึ่งไม่กระทบ Epic ที่ต่อเนื่องกัน | Epic 1→4 (BL-005→BL-020→BL-020b), Epic 2→1 (safety stock→ยอดแนะนำ), Epic 5→ทุก Epic (RBAC) |

## 4. Environment

- **แพลตฟอร์ม:** Web Application, Desktop-first — ทดสอบผ่านเว็บเบราว์เซอร์บนคอมพิวเตอร์/โน้ตบุ๊กเป็นหลัก ตาม NFR Usability ([006](../01-spec/20260816-006-rbac-and-security-nfr.md)) และ [DESIGN.md](../../DESIGN.md) §2.3 (container ยืดหดได้ถึง 1024px เป็นอย่างน้อย)
- **ช่วงเวลาที่ต้องพร้อมใช้งานสำหรับทดสอบ:** สอดคล้องกับ NFR Availability — ระบบต้องพร้อมใช้งานอย่างน้อยในช่วงเวลาราชการ (08:00-16:30 น. จันทร์-ศุกร์) ตาม BL-033
- **ขนาดผู้ใช้งานพร้อมกัน:** ทดสอบ performance ภายใต้สมมติฐานเครือข่าย 29 รพ.สต. + 1 รพ.แม่ข่าย ผู้ใช้งานพร้อมกันไม่เกินหลักสิบราย (ตาม NFR Performance) — ไม่ต้องออกแบบการทดสอบ load ระดับหลักร้อย/พันผู้ใช้
- **บัญชีผู้ใช้ทดสอบต่อ Role:** ต้องมีบัญชีทดสอบอย่างน้อย 1 บัญชีต่อ role ต่อไปนี้ (ดู stakeholder table ใน [spec 001](../01-spec/20260816-001-project-scope-and-problem-background.md)):
  - เจ้าหน้าที่ รพ.สต. — อย่างน้อย 2 บัญชีจากหน่วยต่างกัน (เพื่อทดสอบ RBAC ข้ามหน่วย)
  - เภสัชกรผู้อนุมัติระดับ 1/2 — อย่างน้อย 2 บัญชี (เพื่อทดสอบกฎห้ามคนเดียวกันอนุมัติซ้ำสองระดับ)
  - ผู้บริหาร รพ./สสอ. — อย่างน้อย 1 บัญชี (read-only)
  - ผู้ดูแลระบบ (Admin) — อย่างน้อย 1 บัญชี
- **ระบบภายนอกที่ต้องเตรียม sandbox/test account ก่อนทดสอบ integration:**
  - SMTP (อีเมล) และ LINE Official Account API/Webhook — ต้องตั้งค่าก่อนทดสอบ FT-012 และ feature ที่พึ่งพา (FT-001 ขอปรึกษา, FT-006 เบิกฉุกเฉิน, FT-007 แจ้งเตือนล่วงหน้า, FT-011 สต็อกต่ำ, FT-017 ส่งไฟล์)
  - ไฟล์ตัวอย่าง/รูปแบบคอลัมน์ที่ INVC รองรับการนำเข้า — **ยังไม่มี** (บล็อกการทดสอบ FT-018 ดู §5)
- **หมายเหตุข้อมูลทดสอบ (Test Data) — สำคัญ:** ข้อมูลทดสอบทั้งหมดที่ใช้ใน [acceptance-criteria.md](acceptance-criteria.md) และ [test-cases/](test-cases/) (ชื่อยา, ปริมาณ, หน่วย รพ.สต.) เป็น **placeholder ทั่วไปเท่านั้น** (เช่น "ยา A", "ยา B", "รพ.สต. ตัวอย่าง", จำนวนกลมๆ เช่น "10 หน่วย") **ไม่ใช่ข้อมูลยา NCD จริง** — ต้องแทนที่ด้วยรายการยา/ปริมาณ/หน่วยงานจริงในบัญชียาที่ รพ.แม่ข่ายจ่ายให้เครือข่ายจริง โดยเภสัชกรเจ้าของข้อกำหนด **ก่อนเริ่มการทดสอบจริง (test execution)**
- **ข้อมูลย้อนหลังสำหรับ safety stock:** การทดสอบ FT-009/FT-010 (data migration + คำนวณ year-over-year) ต้องใช้ข้อมูลย้อนหลังอย่างน้อย 3 ปีตามรูปแบบจริงที่จะนำเข้า — งานนี้เป็นงานตั้งต้นครั้งเดียว (one-off) ต้องรอไฟล์จากเจ้าของข้อกำหนดก่อน (BL-010)

## 5. การบริหารความเสี่ยง (Risk Management)

| ความเสี่ยง | ผลกระทบ | แนวทางลด/รับมือ |
|---|---|---|
| **รูปแบบคอลัมน์ไฟล์ที่ INVC รองรับยังไม่ยืนยัน (BL-022, FR-4.3)** | บล็อกการทดสอบ integration ของ Epic 4 ทั้งหมด (FT-017, FT-018) — ไม่สามารถยืนยันว่าไฟล์ Excel ที่ระบบสร้างนำเข้า INVC ได้จริงจนกว่าจะได้รูปแบบคอลัมน์ | ติดต่อฝ่ายดูแล INVC เพื่อขอรูปแบบคอลัมน์ให้เร็วที่สุดตามที่ระบุใน backlog.md "หมายเหตุ Dependency ข้ามกลุ่ม" — ระหว่างรอ ทดสอบ FT-017 (คอนเฟิร์ม/ดาวน์โหลด) ได้เฉพาะส่วนที่ไม่ต้องพึ่งรูปแบบคอลัมน์จริง (เช่น RBAC, state transition, ช่องทางส่งไฟล์) |
| **Epic 1 → Epic 4 ต้องเรียงลำดับ (BL-005 → BL-020 → BL-020b)** | หากทดสอบข้ามลำดับ (เช่น ทดสอบดาวน์โหลดก่อนคอนเฟิร์ม) อาจได้ผลลัพธ์เท็จที่บดบัง defect จริงเรื่องการบังคับลำดับ | ออกแบบ test case ของ FT-017 ให้ตรวจสอบการบังคับลำดับโดยเฉพาะ (BL-020b Scenario 1: ยังไม่คอนเฟิร์ม → ดาวน์โหลดไม่ได้) ก่อนทดสอบ happy path |
| **Epic 2 → Epic 1: BL-011/BL-012 ต้องเสร็จก่อน BL-001 จึงมีค่ายอดแนะนำจริง** | ทดสอบ FT-001 (ยอดแนะนำเบิก) ก่อน FT-010 (safety stock) เสร็จ จะได้ผลลัพธ์ที่ไม่มีความหมาย (ไม่มีค่าให้แสดง) | จัดลำดับการทดสอบให้ FT-009/FT-010 (data migration + คำนวณ safety stock) ผ่านก่อนเริ่มทดสอบ FT-001 |
| **Epic 5 (RBAC, BL-024) เป็นรากฐานของทุก Epic** | หาก RBAC มี defect จะกระทบความถูกต้องของการทดสอบทุก Feature ที่ตามมา (การเห็น/แก้ไขข้อมูลผิดสิทธิ์อาจทำให้ผลการทดสอบ Feature อื่นคลาดเคลื่อน) | ทดสอบ FT-020 (RBAC) ให้เสร็จและผ่านก่อน หรือคู่ขนานกับการเริ่มทดสอบ Epic 1-3 ตามที่ backlog.md ระบุไว้ |
| **External dependency: SMTP/LINE OA API ยังไม่ได้ตั้งค่า (BL-014)** | ทดสอบ integration ของการแจ้งเตือน (FT-012 และ feature ที่พึ่งพา) ไม่ได้จนกว่าจะตั้งค่าเสร็จ | ตั้งค่า SMTP/LINE OA sandbox ก่อนเริ่ม Sprint ที่ทดสอบ FT-001/FT-006/FT-007/FT-011/FT-017 |
| **จุด `[รอยืนยัน]` ที่ยังไม่ resolved ในหลาย BL-ID** (BL-009b จำนวนวันแจ้งเตือน, BL-019 รูปแบบไฟล์รายงาน, BL-023 ความจำเป็นเชื่อมต่อ JHCIS/myPCU, BL-032 เกณฑ์กระทบยอด) | ไม่สามารถกำหนด test data/threshold ที่แน่นอนสำหรับ scenario เหล่านี้ได้ ทำให้ test case ที่เกี่ยวข้องต้องเว้น pass/fail criteria ไว้บางส่วน | ติดตามการตัดสินใจจากเจ้าของข้อกำหนดผ่าน `/new-requirement` ก่อนเข้ารอบทดสอบจริงของ Feature ที่เกี่ยวข้อง (FT-007, FT-008, FT-016, FT-019) |
| **ข้อมูลย้อนหลัง 3 ปีสำหรับ data migration ยังไม่ได้รับจากผู้ใช้ (BL-010)** | ทดสอบ FT-009/FT-010 (คำนวณ safety stock เริ่มต้น) ไม่ได้ด้วยข้อมูลจริงจนกว่าจะได้รับไฟล์ | ใช้ข้อมูลย้อนหลังจำลอง (synthetic data ที่มีรูปแบบเดียวกัน ไม่ใช่ข้อมูลยา NCD จริง) สำหรับทดสอบ logic การคำนวณระหว่างรอไฟล์จริง แล้วทดสอบซ้ำด้วยข้อมูลจริงก่อน migrate เข้าระบบ production |

## 6. Entry Criteria

- [ ] Spec และ backlog ของ Feature ที่จะทดสอบ sync กันแล้ว (ผ่าน `/check-backlog-sync`) ไม่มี drift ที่ยังไม่แก้ไข
- [ ] Acceptance Criteria ของทุก BL-ID ที่เกี่ยวข้องเขียนเสร็จและได้รับการตรวจสอบแล้ว (ดู [acceptance-criteria.md](acceptance-criteria.md))
- [ ] สภาพแวดล้อมทดสอบพร้อมใช้งาน (บัญชีผู้ใช้ครบทุก Role ตาม §4)
- [ ] Feature ที่มี blocking dependency (เช่น FT-018 รอรูปแบบคอลัมน์ INVC) ได้รับการปลดล็อกแล้ว หรือถูกจัดเป็น "ทดสอบบางส่วน" อย่างชัดเจนตาม §5
- [ ] ข้อมูลทดสอบ (test data) เตรียมพร้อมแล้ว **[ถือว่า]** ใช้ placeholder ทั่วไปได้สำหรับการทดสอบ logic เบื้องต้น แต่ต้องใช้ข้อมูลจริง (แทน placeholder) ก่อนรอบทดสอบ UAT/ก่อนขึ้น production

## 7. Exit Criteria

- [ ] Test Case ที่วางแผนไว้ทั้งหมดของ Feature นั้นถูก execute แล้ว (ยกเว้น Feature ที่ยังบล็อกตาม §5 ซึ่งต้องระบุเหตุผลไว้ชัดเจนแทนการนับเป็น pass)
- [ ] **[ถือว่า]** อัตราผ่านของ Test Case (Pass Rate) อย่างน้อย **95%** สำหรับ Feature priority Must และอย่างน้อย **90%** สำหรับ Feature priority Should — ตัวเลขนี้เป็นค่ามาตรฐาน QA ทั่วไป ยังไม่ได้รับการยืนยันจากเจ้าของข้อกำหนดว่าเหมาะสมกับโครงการนี้หรือไม่ ควรยืนยันก่อนใช้เป็นเกณฑ์ปิดรอบทดสอบจริง
- [ ] **[ถือว่า]** ไม่มี defect ระดับ Critical/Blocker ที่ยังเปิดอยู่ (เช่น ข้อมูลข้ามหน่วยรั่วไหลผิด RBAC, สถานะคำขอเบิกเปลี่ยนผิดลำดับ, ยอดคงคลังคำนวณผิด) — defect ระดับ Major ที่เหลือต้องมีแผนแก้ไขและกำหนดเวลาที่ชัดเจนก่อนปิดรอบ
- [ ] ทุก `[รอยืนยัน]` ที่ยังค้างซึ่งกระทบ Feature ที่ทดสอบ ได้รับการตัดสินใจจากเจ้าของข้อกำหนดแล้ว หรือถูกบันทึกเป็นความเสี่ยงที่ยอมรับได้อย่างชัดเจนก่อนขึ้น production
- [ ] UAT ผ่านการยืนยันจากตัวแทนผู้ใช้จริงอย่างน้อย 1 คนต่อ Role (เจ้าหน้าที่ รพ.สต., เภสัชกร, ผู้บริหาร, Admin)

## 8. Deliverables

- [Acceptance Criteria](acceptance-criteria.md) — Given-When-Then ครบทุก BL-ID
- Test Case ต่อ Feature ใน [test-cases/](test-cases/)
- รายงานผลการทดสอบ (Test Execution Report) — Pass/Fail ต่อ TC-ID พร้อม defect log (จัดทำในรอบทดสอบจริง ไม่ใช่ส่วนหนึ่งของเอกสารชุดนี้)
- บันทึกความเสี่ยง/จุดค้างที่ยังไม่ resolved ก่อนขึ้น production (สรุปจาก §5)
