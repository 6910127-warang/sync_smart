## 1. ภาพรวมและวัตถุประสงค์ (Overview & Objectives)

SmartSync เป็นระบบสนับสนุนการเบิก-จ่ายยากลุ่ม NCD ระหว่าง รพ.เชียงรายประชานุเคราะห์ (รพ.แม่ข่าย) และเครือข่าย รพ.สต. 29 แห่ง — เป้าหมายเชิงตัวชี้วัด (KPI) ของโครงการคือลดอัตราหมุนเวียนคงคลัง (Inventory Turnover) ของ รพ.สต. จากปัจจุบัน **3 เดือน** เหลือ **≤ 1.5 เดือน** พร้อมลดความถี่การเบิกยาด่วนนอกรอบ (ดู [spec 001](../01-spec/20260816-001-project-scope-and-problem-background.md))

**วัตถุประสงค์ของการทดสอบ:**
- ยืนยันว่า Epic 1 (เบิก-จ่ายยา NCD Core) และ Epic 2 (พยากรณ์สต็อก) ซึ่งเป็นกลไกหลักที่ตอบ KPI ทำงานถูกต้องตรงตามสูตรคำนวณเดียวกันที่ผู้เบิกและผู้คัดกรองใช้ร่วมกัน (แก้ Root Cause เรื่องเกณฑ์คำนวณคนละมาตรฐาน)
- ยืนยันว่าการควบคุมสิทธิ์ (RBAC), การอนุมัติสองระดับ, และ audit trail ทำงานถูกต้องครบถ้วนก่อนเข้าสู่การใช้งานจริง เนื่องจากเกี่ยวข้องกับการจ่ายยาจริงและข้อมูลที่เชื่อมโยงถึงผู้ป่วยทางอ้อม
- ยืนยันว่าการเชื่อมต่อกับ INVC (Epic 4) ผลิตไฟล์ที่นำเข้าได้จริงโดยไม่ต้องแก้ไขเพิ่มเติม (เป็นความเสี่ยงสูงสุดของโครงการ — ดู §5)

## 2. ขอบเขตการทดสอบ (Scope)

- **อยู่ในขอบเขต:** ทั้ง 34 Feature (FT-001–FT-034) ครอบคลุม 5 Epic ตาม [Feature List](../02-feature-list.md) — Epic 1 (เบิก-จ่าย Core), Epic 2 (พยากรณ์สต็อก/แจ้งเตือน), Epic 3 (รายงาน/Dashboard), Epic 4 (เชื่อมต่อระบบเดิม), Epic 5 (RBAC/NFR รวม FT-026–FT-034 ที่เพิ่มเข้ามา 20260824 จาก NFR เพิ่มเติม 10 หมวด — Backup/Recovery, Concurrency Check, บังคับเปลี่ยนรหัสผ่าน/Session Timeout, 2FA/OTP, Data Encryption in Transit, Browser Compatibility, Scalability, Disaster Recovery, Admin Config)
  - **หมายเหตุ FT-018 (BL-022/BL-034):** ทั้งรูปแบบคอลัมน์ไฟล์ (BL-022) และตรรกะแยกไฟล์ 2 ชุด (BL-034) **ยืนยันแล้วครบทั้งคู่ 20260823** — รูปแบบคอลัมน์จากไฟล์ตัวอย่างจริง 46 ไฟล์ และฟิลด์ `WORKING_CODE`/`HOSP_CODE`/flag "หมวดบัญชีแพทย์" เป็นฟิลด์ทางการแล้วใน [06-data-model.md](../06-data-model.md) §3.3/§3.13 — ไม่มี dependency ค้างอีกต่อไป อยู่ในขอบเขตเต็มรูปแบบ ทดสอบด้วยข้อมูลจริงได้ทั้งหมด ไม่ต้องใช้ข้อมูลจำลองอีกต่อไป
  - **หมายเหตุ FT-026, FT-030, FT-031, FT-032, FT-033 (BL-035, BL-039, BL-040, BL-041, BL-042):** เป็น NFR เชิงระบบ/infrastructure ล้วนๆ (Backup, Encryption in transit, Browser Compatibility, Scalability scope, Disaster Recovery) ไม่มีหน้าจอ/ปฏิสัมพันธ์ที่ผู้ใช้ลงมือทำตาม [Feature List](../02-feature-list.md) — ทดสอบผ่าน Integration/Compatibility/Reliability Testing (§3) มากกว่า Functional flow ปกติ ยังอยู่ในขอบเขตการทดสอบเอกสารชุดนี้ แต่การทดสอบจริง (execution) บางส่วน (เช่น backup/restore, DR runbook) อาจต้องรอ infrastructure จริงพร้อมใช้งานก่อน (ดู §5 ความเสี่ยง)
- **นอกขอบเขต (เฟสนี้):**
  - **FT-019 (เชื่อมต่อ JHCIS/myPCU โดยตรง, BL-023):** Priority Won't ในเฟสนี้ — resolved 20260823 (ยืนยันไม่เชื่อมต่อโดยตรง คงตามเดิม) มีเพียง scenario ยืนยันขอบเขตว่าไม่มี integration จริงเกิดขึ้น ไม่ใช่การทดสอบฟังก์ชันที่พัฒนาจริง — หมายเหตุ: ข้อมูลย้อนหลัง 3 ปีสำหรับ FT-009/BL-010 มาจากการขอไฟล์ด้วยมือจาก รพ.สต. ทุกแห่ง (29 แห่ง) ตาม FR-4.4a ใหม่ เป็นกิจกรรมตั้งต้นครั้งเดียวของ FT-009 ไม่ใช่ scope การทดสอบของ FT-019 นี้
  - งบประมาณ/กรอบเวลาโครงการ, เอกสารนโยบายเบิกจ่ายยา NCD ของเขตสุขภาพ, การจัดซื้อยา (Procurement)/ระบบบัญชีการเงิน — นอกขอบเขตของ requirement เองตาม [spec 001](../01-spec/20260816-001-project-scope-and-problem-background.md)

## 3. กลยุทธ์/ประเภทการทดสอบ (Test Strategy & Types)

| ประเภท | คำอธิบาย | ครอบคลุม |
|---|---|---|
| Functional/System Testing | ทดสอบ flow หลักตาม Acceptance Criteria ของแต่ละ BL-ID — สร้างคำขอ, คำนวณยอดแนะนำ/safety stock, อนุมัติสองระดับ, รับยา, แจ้งเตือน, Dashboard, Admin ปรับ config ผ่านหน้าจอ (BL-043) | ทุก Feature (FT-001–FT-034) |
| Integration Testing | ทดสอบการส่งออกไฟล์ Excel ไปยัง INVC (นำเข้า/ส่งออกไฟล์แบบ Manual batch ไม่ใช่ API real-time) และช่องทางแจ้งเตือนอีเมล/LINE OA — **[ถือว่า]** ต้องมี sandbox/test account ของ SMTP และ LINE OA API ก่อนจึงจะทดสอบ integration ได้ครบ รูปแบบคอลัมน์ไฟล์ INVC (BL-022) และตรรกะแยกไฟล์ 2 ชุด (BL-034) ยืนยันแล้วครบทั้งคู่ 20260823 — ฟิลด์ `WORKING_CODE`/`HOSP_CODE`/flag "หมวดบัญชีแพทย์" เป็นฟิลด์ทางการแล้ว ไม่บล็อกอีกต่อไป | FT-012, FT-017, FT-018 |
| Concurrency / Data Integrity Testing | ทดสอบ Optimistic Concurrency Check (BL-036) เมื่อผู้ใช้มากกว่า 1 คนพยายามแก้ไข/อนุมัติคำขอเบิกเดียวกันพร้อมกัน — ต้องจำลองสถานการณ์ 2 session พร้อมกัน (เภสัชกร 2 บัญชี) เพื่อยืนยันว่าผู้ใช้คนที่สองได้รับ error ตามที่กำหนด และเชื่อมโยงกับกฎห้ามอนุมัติระดับ 1/2 ด้วยคนเดียวกัน (BL-004) — เพิ่ม 20260824 | FT-027, FT-002 |
| RBAC / Security Testing | ทดสอบว่าแต่ละ Role (เจ้าหน้าที่ รพ.สต., เภสัชกรระดับ 1/2, ผู้บริหาร, Admin) เห็น/แก้ไขได้เฉพาะข้อมูลตามสิทธิ์ที่กำหนด รวมกฎห้ามอนุมัติซ้ำสองระดับด้วยคนเดียวกัน, การปฏิเสธการเข้าถึงข้ามหน่วย, PDPA Consent, System Access Log, บังคับเปลี่ยนรหัสผ่าน login ครั้งแรก (ความยาวขั้นต่ำ 8 ตัวอักษร ไม่บังคับอักขระพิเศษ — ยืนยันแล้ว 20260825) + session timeout ~30 นาทีทุก role (BL-037), 2FA/OTP เฉพาะเภสัชกรผู้อนุมัติระดับ 1/2 (ผิดได้ไม่เกิน 3 ครั้งก่อนล็อก, หมดอายุ 5 นาที, ส่งผ่านอีเมลช่องทางเดิม — ยืนยันแล้ว 20260825, BL-038), เข้ารหัสข้อมูลระหว่างส่ง in transit (BL-039) | FT-002, FT-020, FT-021, FT-023, FT-024, FT-028, FT-029, FT-030 |
| Performance / Scalability Testing | ทดสอบว่ายอดคงคลังอัปเดตภายใน **5 วินาที** หลังบันทึกรับ/จ่าย ภายใต้จำนวนผู้ใช้งานพร้อมกันตามขนาดจริงของเครือข่าย (29 รพ.สต. + 1 รพ.แม่ข่าย รวมไม่เกินหลักสิบราย) — ขอบเขตการทดสอบ load จำกัดเฉพาะขนาดเครือข่ายปัจจุบันนี้เท่านั้น ไม่ต้องออกแบบ/ทดสอบสถานการณ์ขยายเครือข่ายในอนาคต (BL-041, เพิ่ม 20260824) | FT-004, FT-032 |
| Compatibility Testing (เบราว์เซอร์) | ทดสอบว่าระบบใช้งานได้ครบถ้วนบนเบราว์เซอร์ Evergreen 2 เวอร์ชันล่าสุดของแต่ละยี่ห้อหลัก (Chrome, Edge, Firefox, Safari) — ไม่รับประกันรุ่นเก่ากว่านั้น — เพิ่ม 20260824 | FT-031 |
| Usability Testing | ทดสอบว่า UI ใช้งานได้ครบถ้วนแบบ Responsive เต็มรูปแบบบนทั้ง 3 breakpoint — mobile (320-767px), tablet (768-1023px), desktop (1024px ขึ้นไป) ตาม [DESIGN.md](../../DESIGN.md) §2.3 — ครอบคลุมทั้ง 4 role รวมการแปลงตารางเป็น card บนจอเล็ก (§3.3) และเมนู hamburger/drawer บน tablet/mobile (§3.5) | FT-022 |
| Reliability & Disaster Recovery Testing | ทดสอบการสำรองข้อมูลรายวัน (RPO ≤ 24 ชั่วโมง, BL-035) และแผน Disaster Recovery (RTO ≤ 4 ชั่วโมงในเวลาราชการ + ขั้นตอนสำรองแบบ manual, BL-042) — เป็นการทดสอบเชิง infrastructure/operational process มากกว่า functional test ในแอปปกติ อาจต้องประสานทีมโครงสร้างพื้นฐานแยกจากทีมทดสอบฟังก์ชัน — เพิ่ม 20260824 | FT-026, FT-033 |
| UAT (User Acceptance Testing) | ให้ตัวแทนผู้ใช้จริงแต่ละ Role ทดสอบ flow ของตนเองแบบ end-to-end ตาม User Journey ของ role นั้น — เจ้าหน้าที่ รพ.สต. ([staff-hph-journey.md](../03-user-journey/staff-hph-journey.md)), เภสัชกร ([pharmacist-journey.md](../03-user-journey/pharmacist-journey.md)), ผู้บริหาร ([executive-journey.md](../03-user-journey/executive-journey.md)), ผู้ดูแลระบบ ([admin-journey.md](../03-user-journey/admin-journey.md)) | ทุก Feature ที่เกี่ยวข้องกับ role นั้นๆ |
| Regression Testing | ทดสอบซ้ำ flow หลักหลังแก้ไข/เพิ่ม feature ใหม่ในแต่ละรอบ Sprint โดยเฉพาะจุดที่มี cross-epic dependency (ดู §5) เพื่อยืนยันว่าการแก้ไข Epic หนึ่งไม่กระทบ Epic ที่ต่อเนื่องกัน | Epic 1→4 (BL-005→BL-020→BL-020b), Epic 2→1 (safety stock→ยอดแนะนำ), Epic 5→ทุก Epic (RBAC, Concurrency Check) |

## 4. Environment

- **แพลตฟอร์ม:** Web Application, Responsive เต็มรูปแบบ — ทดสอบผ่านเว็บเบราว์เซอร์ครอบคลุมอุปกรณ์ทั้ง 3 ประเภทตาม NFR Usability ([006](../01-spec/20260816-006-rbac-and-security-nfr.md) หัวข้อ "เพิ่มเติม 20260820") และ breakpoint ใน [DESIGN.md](../../DESIGN.md) §2.3: mobile (320-767px), tablet (768-1023px), desktop (1024px ขึ้นไป, container สูงสุด 1440px) — ต้องเตรียมอุปกรณ์จริงหรือ browser viewport emulation ครบทั้ง 3 breakpoint ก่อนทดสอบ FT-022
- **เมทริกซ์เบราว์เซอร์สำหรับ FT-031 (เพิ่ม 20260824):** ต้องเตรียมเบราว์เซอร์ 2 เวอร์ชันล่าสุดของแต่ละยี่ห้อหลัก (Chrome, Edge, Firefox, Safari) อย่างน้อย 1 ชุดต่อยี่ห้อก่อนทดสอบความเข้ากันได้ — ไม่ต้องเตรียมเบราว์เซอร์รุ่นเก่ากว่านั้นตามขอบเขตที่ยืนยันแล้ว (BL-040)
- **การเชื่อมต่อผ่าน HTTPS/TLS สำหรับ FT-030 (เพิ่ม 20260824):** ต้องมีใบรับรอง/การตั้งค่าการเข้ารหัสระหว่างทางในสภาพแวดล้อมทดสอบก่อนยืนยัน NFR Data Encryption in Transit (BL-039) — **[ถือว่า]** ใช้ self-signed certificate ได้สำหรับสภาพแวดล้อมทดสอบที่ไม่ใช่ production
- **ช่วงเวลาที่ต้องพร้อมใช้งานสำหรับทดสอบ:** สอดคล้องกับ NFR Availability — ระบบต้องพร้อมใช้งานอย่างน้อยในช่วงเวลาราชการ (08:00-16:30 น. จันทร์-ศุกร์) ตาม BL-033
- **ขนาดผู้ใช้งานพร้อมกัน:** ทดสอบ performance ภายใต้สมมติฐานเครือข่าย 29 รพ.สต. + 1 รพ.แม่ข่าย ผู้ใช้งานพร้อมกันไม่เกินหลักสิบราย (ตาม NFR Performance) — ไม่ต้องออกแบบการทดสอบ load ระดับหลักร้อย/พันผู้ใช้
- **บัญชีผู้ใช้ทดสอบต่อ Role:** ต้องมีบัญชีทดสอบอย่างน้อย 1 บัญชีต่อ role ต่อไปนี้ (ดู stakeholder table ใน [spec 001](../01-spec/20260816-001-project-scope-and-problem-background.md)):
  - เจ้าหน้าที่ รพ.สต. — อย่างน้อย 2 บัญชีจากหน่วยต่างกัน (เพื่อทดสอบ RBAC ข้ามหน่วย)
  - เภสัชกรผู้อนุมัติระดับ 1/2 — อย่างน้อย 2 บัญชี (เพื่อทดสอบกฎห้ามคนเดียวกันอนุมัติซ้ำสองระดับ และเพื่อทดสอบ Optimistic Concurrency Check/BL-036 ที่ต้องจำลอง 2 session พร้อมกัน — เพิ่ม 20260824) — ทั้งสองบัญชีต้องรองรับการยืนยันตัวตนด้วย OTP (2FA, BL-038) ด้วย
  - ผู้บริหาร รพ./สสอ. — อย่างน้อย 1 บัญชี (read-only)
  - ผู้ดูแลระบบ (Admin) — อย่างน้อย 1 บัญชี (ต้องเข้าถึงหน้าจอตั้งค่า config ได้เพื่อทดสอบ FT-034/BL-043)
  - **บัญชีทดสอบทุกบัญชีข้างต้น** ต้องอยู่ในสถานะ "login ครั้งแรก" ได้อย่างน้อย 1 ชุดต่อ role เพื่อทดสอบการบังคับเปลี่ยนรหัสผ่านครั้งแรก (BL-037, เพิ่ม 20260824)
- **ระบบภายนอกที่ต้องเตรียม sandbox/test account ก่อนทดสอบ integration:**
  - SMTP (อีเมล) และ LINE Official Account API/Webhook — ต้องตั้งค่าก่อนทดสอบ FT-012 และ feature ที่พึ่งพา (FT-001 ขอปรึกษา, FT-006 เบิกฉุกเฉิน, FT-007 แจ้งเตือนล่วงหน้า, FT-011 สต็อกต่ำ, FT-017 ส่งไฟล์)
  - ไฟล์ตัวอย่าง/รูปแบบคอลัมน์ที่ INVC รองรับการนำเข้า — **ยืนยันแล้ว 20260823** (ดู [005](../01-spec/20260816-005-legacy-system-integration.md) FR-4.3) ไม่บล็อกอีกต่อไป — field/flag "หมวดบัญชีแพทย์" ของรายการยาเป็นฟิลด์ทางการแล้วใน [06-data-model.md](../06-data-model.md) §3.3 เช่นกัน จึงทดสอบตรรกะแยกไฟล์ (BL-034) ด้วยข้อมูลจริงได้สมบูรณ์แล้ว ไม่ต้องเตรียมข้อมูลจำลองอีกต่อไป
  - **ช่องทางรับรหัส OTP สำหรับทดสอบ 2FA (FT-029/BL-038):** ยืนยันแล้ว 20260825 ว่าส่งผ่าน**อีเมลที่มีอยู่แล้วในระบบ** (ช่องทางเดียวกับ SMTP ของ FT-012) ไม่ใช่ช่องทางใหม่ — บัญชีทดสอบเภสัชกรผู้อนุมัติ (ดูรายการด้านบน) ต้องมีกล่องอีเมลที่เข้าถึงได้จริงระหว่างทดสอบเพื่อรับรหัส OTP (กรอกผิดได้ไม่เกิน 3 ครั้งก่อนล็อก, หมดอายุภายใน 5 นาที)
  - **สิทธิ์เข้าถึงกลไกสำรอง/กู้คืนข้อมูล (FT-026/BL-035) และแผน Disaster Recovery (FT-033/BL-042, เพิ่ม 20260824):** การทดสอบจริง (execution) ของทั้งสองรายการนี้เป็นงานเชิง infrastructure ที่อาจอยู่นอกเหนือสภาพแวดล้อมทดสอบระดับแอปพลิเคชันทั่วไป ต้องประสานทีม/สภาพแวดล้อมที่เข้าถึงกลไก backup-restore และแผน DR ได้จริงก่อนทดสอบ
- **หมายเหตุข้อมูลทดสอบ (Test Data) — สำคัญ:** ข้อมูลทดสอบทั้งหมดที่ใช้ใน [acceptance-criteria.md](acceptance-criteria.md) และ [test-cases/](test-cases/) (ชื่อยา, ปริมาณ, หน่วย รพ.สต.) เป็น **placeholder ทั่วไปเท่านั้น** (เช่น "ยา A", "ยา B", "รพ.สต. ตัวอย่าง", จำนวนกลมๆ เช่น "10 หน่วย") **ไม่ใช่ข้อมูลยา NCD จริง** — ต้องแทนที่ด้วยรายการยา/ปริมาณ/หน่วยงานจริงในบัญชียาที่ รพ.แม่ข่ายจ่ายให้เครือข่ายจริง โดยเภสัชกรเจ้าของข้อกำหนด **ก่อนเริ่มการทดสอบจริง (test execution)**
- **ข้อมูลย้อนหลังสำหรับ safety stock:** การทดสอบ FT-009/FT-010 (data migration + คำนวณ year-over-year) ต้องใช้ข้อมูลย้อนหลังอย่างน้อย 3 ปีตามรูปแบบจริงที่จะนำเข้า — งานนี้เป็นงานตั้งต้นครั้งเดียว (one-off) ต้องรอไฟล์จากเจ้าของข้อกำหนดก่อน (BL-010)

## 6. Entry Criteria

- [ ] Spec และ backlog ของ Feature ที่จะทดสอบ sync กันแล้ว (ผ่าน `/check-backlog-sync`) ไม่มี drift ที่ยังไม่แก้ไข
- [ ] Acceptance Criteria ของทุก BL-ID ที่เกี่ยวข้องเขียนเสร็จและได้รับการตรวจสอบแล้ว (ดู [acceptance-criteria.md](acceptance-criteria.md))
- [ ] สภาพแวดล้อมทดสอบพร้อมใช้งาน (บัญชีผู้ใช้ครบทุก Role ตาม §4)
- [ ] Feature ที่มี blocking/pending dependency ได้รับการปลดล็อกแล้ว หรือถูกจัดเป็น "ทดสอบบางส่วน" อย่างชัดเจนตาม §5 (ณ 20260823 ไม่มี Feature ใดถูกบล็อกลักษณะนี้อยู่ — BL-022/BL-034 ที่เคยเป็นตัวอย่างของเกณฑ์นี้ได้รับการปลดล็อกครบทั้งคู่แล้ว)
- [ ] ข้อมูลทดสอบ (test data) เตรียมพร้อมแล้ว **[ถือว่า]** ใช้ placeholder ทั่วไปได้สำหรับการทดสอบ logic เบื้องต้น แต่ต้องใช้ข้อมูลจริง (แทน placeholder) ก่อนรอบทดสอบ UAT/ก่อนขึ้น production

## 7. Exit Criteria

- [ ] Test Case ที่วางแผนไว้ทั้งหมดของ Feature นั้นถูก execute แล้ว (ยกเว้น Feature ที่ยังบล็อกตาม §5 ซึ่งต้องระบุเหตุผลไว้ชัดเจนแทนการนับเป็น pass)
- [ ] **[ถือว่า]** อัตราผ่านของ Test Case (Pass Rate) อย่างน้อย **95%** สำหรับ Feature priority Must และอย่างน้อย **90%** สำหรับ Feature priority Should — ตัวเลขนี้เป็นค่ามาตรฐาน QA ทั่วไป ยังไม่ได้รับการยืนยันจากเจ้าของข้อกำหนดว่าเหมาะสมกับโครงการนี้หรือไม่ ควรยืนยันก่อนใช้เป็นเกณฑ์ปิดรอบทดสอบจริง
- [ ] **[ถือว่า]** ไม่มี defect ระดับ Critical/Blocker ที่ยังเปิดอยู่ (เช่น ข้อมูลข้ามหน่วยรั่วไหลผิด RBAC, สถานะคำขอเบิกเปลี่ยนผิดลำดับ, ยอดคงคลังคำนวณผิด) — defect ระดับ Major ที่เหลือต้องมีแผนแก้ไขและกำหนดเวลาที่ชัดเจนก่อนปิดรอบ
- [ ] ทุก `[รอยืนยัน]` ที่ยังค้างซึ่งกระทบ Feature ที่ทดสอบ ได้รับการตัดสินใจจากเจ้าของข้อกำหนดแล้ว หรือถูกบันทึกเป็นความเสี่ยงที่ยอมรับได้อย่างชัดเจนก่อนขึ้น production
- [ ] UAT ผ่านการยืนยันจากตัวแทนผู้ใช้จริงอย่างน้อย 1 คนต่อ Role (เจ้าหน้าที่ รพ.สต., เภสัชกร, ผู้บริหาร, Admin)

## 8. Deliverables

- [Acceptance Criteria](acceptance-criteria.md) — Given-When-Then ครบทุก BL-ID
- Test Case ต่อ Feature ใน [test-cases/](test-cases/)
- รายงานผลการทดสอบ (Test Execution Report) — Pass/Fail ต่อ TC-ID พร้อม defect log (จัดทำในรอบทดสอบจริง ไม่ใช่ส่วนหนึ่งของเอกสารชุดนี้)
- บันทึกความเสี่ยง/จุดค้างที่ยังไม่ resolved ก่อนขึ้น production (สรุปจาก §5)
