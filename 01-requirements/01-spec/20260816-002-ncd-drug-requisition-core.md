## บริบท/ที่มา (Context)

Epic นี้คือแกนหลักของ SmartSync — ตอบ Root Cause ที่พบจากการสัมภาษณ์จริง (ดู [001](20260816-001-project-scope-and-problem-background.md)) ว่าผู้เบิก (เจ้าหน้าที่ รพ.สต.) และผู้คัดกรอง (เภสัชกร) ใช้เกณฑ์คำนวณยอดเบิกคนละมาตรฐานกัน โดยให้ระบบคำนวณยอดแนะนำเบิกจากสูตรเดียวกันแบบเรียลไทม์ แทนที่การใช้ดุลยพินิจแยกกัน

## ขอบเขต (Scope)

- **อยู่ในขอบเขต:** สร้างคำขอเบิก (ปกติ/ฉุกเฉิน), อนุมัติสองระดับ, ส่งออกไฟล์เพื่อจ่ายยา (เชื่อมกับ Epic 4), ยืนยันรับยา, ยอดคงคลัง real-time, audit trail, แจ้งเตือนก่อนถึงรอบเบิก
- **นอกขอบเขต:** การคำนวณเกณฑ์ safety stock เอง (ดู [003](20260816-003-stock-forecast-alerts.md)), กลไกไฟล์ Excel/INVC โดยละเอียด (ดู [005](20260816-005-legacy-system-integration.md))

## Functional Requirements

| ID | รายละเอียด |
|---|---|
| FR-1.1 | ระบบต้องคำนวณ**ยอดแนะนำสำหรับเบิก**ของแต่ละหน่วย/รายการยาในแต่ละเดือนโดยอัตโนมัติ จากเกณฑ์ safety stock (FR-2.1/FR-2.1b/FR-2.4 ใน [003](20260816-003-stock-forecast-alerts.md)) หักด้วยยอดคงเหลือปัจจุบันที่เจ้าหน้าที่ รพ.สต. รายงาน |
| FR-1.1a | ระบบต้องให้เจ้าหน้าที่ รพ.สต. กรอก**ยอดคงเหลือปัจจุบันของแต่ละรายการยา ณ วันที่สร้างคำขอ** (ใช้คำนวณ FR-1.1 และเป็นข้อมูลนำเข้าต่อเนื่องของ FR-2.1b) จากนั้นตรวจสอบ/ยืนยันยอดแนะนำที่ระบบคำนวณได้ เพื่อสร้างเป็นคำขอเบิกของเดือนนั้น |
| FR-1.1b | หากเจ้าหน้าที่ รพ.สต. ต้องการเปลี่ยนแปลงยอดแนะนำก่อนยืนยันคำขอ ระบบต้องมีปุ่ม**"ขอปรึกษา"** ซึ่งเมื่อกดแล้วต้องส่ง alert แจ้งกลุ่มเภสัชกรผ่าน LINE Official Account ที่มีอยู่แล้วทันที |
| FR-1.2 | ระบบต้องรองรับการอนุมัติคำขอเบิกแบบ **สองระดับ**: เภสัชกรผู้อนุมัติระดับ 1 พิจารณา/ปฏิเสธ/ปรับจำนวนก่อน จากนั้นเภสัชกรผู้ตรวจสอบระดับ 2 (คนละคนกับระดับ 1) ยืนยันซ้ำก่อนสถานะเปลี่ยนเป็น "อนุมัติแล้ว" |
| FR-1.3 | เมื่อคำขอได้รับการอนุมัติครบทั้งสองระดับ (FR-1.2) ระบบต้องเปลี่ยนสถานะคำขอเป็น "พร้อมส่งออก" — เภสัชกรผู้อนุมัติระดับ 2 กด **"คอนเฟิร์ม"** เพื่อสร้างไฟล์ Excel และส่งไปยังฝ่ายคลังยา รพ.แม่ข่าย (ดู [005](20260816-005-legacy-system-integration.md) FR-4.1/FR-4.1b) ทันทีที่กดคอนเฟิร์ม ระบบต้องเปลี่ยนสถานะเป็น **"จ่ายแล้ว"** โดยไม่ต้องรอการยืนยันย้อนกลับจากฝ่ายคลังยาว่านำเข้า INVC สำเร็จ — **เจ้าหน้าที่ รพ.สต. จะดาวน์โหลดไฟล์ Excel ได้ก็ต่อเมื่อเภสัชกรกดคอนเฟิร์มแล้วเท่านั้น** (ดาวน์โหลดไฟล์ล่าสุดที่ถูกคอนเฟิร์ม ไม่ใช่ก่อนหน้านั้น) |
| FR-1.4 | ระบบต้องให้เจ้าหน้าที่ รพ.สต. ยืนยันการรับยาเข้าคลังของหน่วยตนเอง |
| FR-1.5 | ระบบต้องคำนวณและแสดงยอดคงคลังของแต่ละหน่วยแบบ real-time หรือใกล้เคียง real-time หลังบันทึกรับ/จ่าย |
| FR-1.6 | ระบบต้องเก็บประวัติการเบิก-จ่าย-รับ ย้อนหลังเพื่อการตรวจสอบ (Audit trail) รวมถึงบันทึกผู้อนุมัติระดับ 1/2 ของแต่ละคำขอ และบันทึกทุกครั้งที่มีการกด "ขอปรึกษา" (FR-1.1b) |
| FR-1.7 | ระบบต้องให้เจ้าหน้าที่ รพ.สต. สร้างคำขอเบิกฉุกเฉินนอกรอบรายเดือนได้ (Off-cycle Requisition) โดยต้องผ่านการอนุมัติสองระดับเหมือนคำขอปกติ (FR-1.2) แต่กระบวนการอนุมัติควรเร็วขึ้นด้วยการแจ้งเตือนทันที (real-time notify) ไปยังผู้อนุมัติทั้งสองระดับ |
| FR-1.8 | ระบบต้องแจ้งเตือนเจ้าหน้าที่ รพ.สต. ล่วงหน้าก่อนถึงกำหนดส่งคำขอเบิกประจำเดือน เพื่อลดปัญหา**ลืมเบิกยา** ซึ่งเป็นสาเหตุหนึ่งของการเบิกด่วนนอกรอบ (ที่มา: Root Cause Analysis ใน [001](20260816-001-project-scope-and-problem-background.md)) `[ต้องยืนยัน — จำนวนวันล่วงหน้าที่ควรแจ้งเตือนก่อนถึงกำหนด]` |
| FR-1.9 | **(ยืนยันแล้ว 20260823)** ระบบต้องเปรียบเทียบยอดคงเหลือปัจจุบันที่เจ้าหน้าที่ รพ.สต. รายงานเอง (FR-1.1a) กับยอดคงคลังที่ระบบคำนวณอัตโนมัติ (FR-1.5) ของหน่วย/รายการยาเดียวกัน ณ ช่วงเวลาเดียวกัน — เมื่อพบว่า**ไม่ตรงกัน (ค่าต่างกันแม้เพียงเล็กน้อย ไม่มีเกณฑ์ความคลาดเคลื่อนที่ยอมรับได้ — เปรียบเทียบแบบตรงเป๊ะ/exact-match)** ระบบต้องแสดงข้อความแจ้งเตือนตรงตามนี้คำต่อคำ: **"ยอดคงเหลือที่เจ้าหน้าที่แจ้งกับยอดคงคลังที่ระบบคำนวณอัตโนมัติ ไม่ตรงกัน โปรดตรวจสอบ หากไม่แน่ใจให้ปรึกษา รพศ.ชร. (แม่ข่าย)"** — `[ถือว่า]` ขอบเขตของ FR นี้ครอบคลุมเฉพาะการ**ตรวจจับและแจ้งเตือน**เท่านั้น ยังไม่รวมขั้นตอนกระทบยอด/แก้ไขข้อมูลอัตโนมัติเพิ่มเติม (เช่น ใครเป็นผู้แก้ไขค่าใดให้ตรงกัน) เนื่องจาก raw requirement ที่ได้รับยืนยันเฉพาะพฤติกรรมการแจ้งเตือนเท่านั้น — ถ้าต้องการขั้นตอนกระทบยอดเพิ่มเติมต้องระบุแยกในรอบถัดไป |
| FR-1.9a | **(ยืนยันแล้ว 20260823)** เมื่อระบบแสดงข้อความแจ้งเตือนยอดไม่ตรงกัน (FR-1.9) **เภสัชกรเป็นผู้ตรวจสอบและคอนเฟิร์ม** — ไม่ใช่เจ้าหน้าที่ รพ.สต. เองที่เป็นผู้แก้ไขค่า และการปรึกษา รพศ.ชร. (แม่ข่าย) ตามข้อความแจ้งเตือนเป็นเพียง**ทางเลือกเสริมเมื่อเภสัชกรไม่แน่ใจเท่านั้น ไม่ใช่ขั้นตอนบังคับทุกครั้ง** |
| FR-1.9b | **(ยืนยันแล้ว 20260823 รอบ 4 — ปิด Open Item ของ FR-1.9/FR-1.9a)** ขั้นตอนตรวจสอบ/คอนเฟิร์มยอดไม่ตรงกัน (FR-1.9a) **เกิดขึ้นเป็นส่วนหนึ่งของขั้นตอนอนุมัติคำขอเบิกระดับ 1 เดิม** (FR-1.2/US-1.2, ดู [BL-004](../backlog.md)) ไม่ใช่ขั้นตอนหรือบันทึกแยกต่างหาก — เมื่อเภสัชกรผู้อนุมัติระดับ 1 พิจารณาคำขอที่มีข้อความแจ้งเตือนยอดไม่ตรงกัน (FR-1.9) ปรากฏอยู่ และกด**"คอนเฟิร์ม"**การกระทบยอดนี้ (ระหว่างขั้นตอนอนุมัติระดับ 1 เดียวกัน) **เภสัชกรต้องกรอกยอดคงเหลือที่ตนพิจารณาแล้วว่าถูกต้องด้วยตนเอง** — ไม่ใช่ระบบยึดยอดคงคลังที่คำนวณอัตโนมัติ (FR-1.5) เป็นค่าที่ถูกต้องเอง และไม่ใช่การรับทราบเฉยๆ โดยไม่แก้ไขค่าใด — ค่าที่เภสัชกรกรอกนี้กลายเป็น**ยอดคงเหลือที่ถูกต้อง/มีผลผูกพันต่อ (authoritative)** แทนที่ยอดคงเหลือปัจจุบันที่เจ้าหน้าที่ รพ.สต. รายงานเดิม (FR-1.1a) และนำไปใช้คำนวณต่อเนื่อง (FR-1.5, FR-2.1b ใน [003](20260816-003-stock-forecast-alerts.md)) — รายละเอียดว่าฟิลด์ข้อมูล/โครงสร้างใน data model จะถูกปรับปรุงอย่างไรอยู่**นอกขอบเขต**ของ spec นี้ ให้เป็นงานของ `/build-data-api-spec` |

## User Stories (Agile)

- **US-1.0** ในฐานะ เจ้าหน้าที่ รพ.สต. ฉันต้องการเห็นยอดแนะนำเบิกที่ระบบคำนวณให้อัตโนมัติ เพื่อไม่ต้องคำนวณจำนวนที่ต้องเบิกเองทุกเดือน

- **US-1.1** ในฐานะ เจ้าหน้าที่ รพ.สต. ฉันต้องการกรอกยอดคงเหลือปัจจุบันและยืนยันคำขอเบิกยา NCD ผ่านระบบ เพื่อลดความผิดพลาดจากการโทร/บันทึกใน Excel ด้วยมือ และเป็นข้อมูลให้ระบบคำนวณ safety stock ต่อเนื่อง
  - Acceptance Criteria:
    - [ ] Given เจ้าหน้าที่ รพ.สต. login เข้าระบบและเห็นยอดแนะนำเบิก, When กรอกยอดคงเหลือปัจจุบันของแต่ละรายการและกดยืนยันคำขอ, Then ระบบบันทึกคำขอสถานะ "รอการอนุมัติระดับ 1"

- **US-1.1b** ในฐานะ เจ้าหน้าที่ รพ.สต. ฉันต้องการกด "ขอปรึกษา" เมื่อไม่เห็นด้วยกับยอดแนะนำเบิก เพื่อให้กลุ่มเภสัชกรได้รับแจ้งเตือนผ่าน LINE OA และช่วยพิจารณาก่อนยืนยันคำขอ

- **US-1.2** ในฐานะ เภสัชกรผู้อนุมัติระดับ 1 ฉันต้องการเห็นคำขอเบิกทั้งหมดที่รอดำเนินการ เพื่อพิจารณาอนุมัติ/ปฏิเสธ/ปรับจำนวนได้อย่างรวดเร็ว

- **US-1.2b** ในฐานะ เภสัชกรผู้ตรวจสอบระดับ 2 ฉันต้องการเห็นคำขอที่ผ่านการอนุมัติระดับ 1 แล้ว เพื่อตรวจสอบซ้ำก่อนยืนยันให้จ่ายยาจริง
  - Acceptance Criteria:
    - [ ] Given คำขอผ่านการอนุมัติระดับ 1 แล้ว, When เภสัชกรระดับ 2 (คนละคนกับระดับ 1) กดยืนยัน, Then สถานะเปลี่ยนเป็น "อนุมัติแล้ว" และพร้อมบันทึกจ่าย
    - [ ] Given เภสัชกรคนเดียวกันเป็นผู้อนุมัติระดับ 1, When พยายามยืนยันระดับ 2 ของคำขอเดียวกัน, Then ระบบต้องปฏิเสธการกระทำ

- **US-1.3** ในฐานะ เจ้าหน้าที่ รพ.สต. ฉันต้องการยืนยันการรับยาในระบบ เพื่อให้ยอดคงคลังของหน่วยฉันถูกต้อง

- **US-1.4** ในฐานะ เจ้าหน้าที่ รพ.สต. ฉันต้องการสร้างคำขอเบิกฉุกเฉินนอกรอบรายเดือน เพื่อรับมือกรณียาหมดกะทันหันโดยไม่ต้องรอรอบเบิกถัดไป

- **US-1.5** ในฐานะ เจ้าหน้าที่ รพ.สต. ฉันต้องการได้รับแจ้งเตือนล่วงหน้าก่อนถึงกำหนดส่งคำขอเบิกประจำเดือน เพื่อลดปัญหาลืมเบิกยา

- **US-1.6** **(ใหม่ 20260823)** ในฐานะ เจ้าหน้าที่ รพ.สต./เภสัชกร ฉันต้องการให้ระบบแจ้งเตือนทันทีเมื่อยอดคงเหลือที่แจ้งเองกับยอดคงคลังที่ระบบคำนวณไม่ตรงกัน เพื่อให้ตรวจสอบความถูกต้องก่อนที่ความคลาดเคลื่อนจะกระทบต่อความแม่นยำของ safety stock
  - Acceptance Criteria:
    - [ ] Given มียอดคงเหลือที่แจ้งเอง (FR-1.1a) และยอดคงคลังที่ระบบคำนวณ (FR-1.5) ของหน่วย/รายการยาเดียวกัน, When ระบบเปรียบเทียบสองค่านี้และพบว่าไม่ตรงกัน (ไม่ว่าจะต่างกันเท่าใด), Then ระบบแสดงข้อความ "ยอดคงเหลือที่เจ้าหน้าที่แจ้งกับยอดคงคลังที่ระบบคำนวณอัตโนมัติ ไม่ตรงกัน โปรดตรวจสอบ หากไม่แน่ใจให้ปรึกษา รพศ.ชร. (แม่ข่าย)" ทันที
    - [ ] **(เพิ่ม 20260823 รอบ 3 — อ้างอิง FR-1.9a)** Given ระบบแสดงข้อความแจ้งเตือนยอดไม่ตรงกันแล้ว, When มีการตรวจสอบ, Then **เภสัชกร** (ไม่ใช่เจ้าหน้าที่ รพ.สต.) เป็นผู้ตรวจสอบและคอนเฟิร์ม โดยการปรึกษา รพศ.ชร. เป็นทางเลือกเสริมเมื่อไม่แน่ใจเท่านั้น ไม่ใช่ขั้นตอนบังคับ

## คำถามที่ถามและคำตอบที่ได้ (Clarifications)

- **ถาม:** การอนุมัติคำขอเบิก ควรกำหนดอย่างไร? → **ตอบ:** ต้องมีการอนุมัติสองระดับ (Double-check)

- **ถาม:** มีกรณีที่ต้องเบิกยานอกรอบรายเดือนหรือไม่? → **ตอบ:** มี ต้องรองรับการเบิกฉุกเฉินในระบบด้วย ผ่านอนุมัติสองระดับเหมือนคำขอปกติแต่เร็วขึ้นด้วย notify
- **ยืนยัน (20260823, ตอบตรงจากเภสัชกรเจ้าของระบบ ไม่ใช่การสมมติของ agent):** เมื่อยอดคงเหลือที่เจ้าหน้าที่แจ้งเอง (FR-1.1a) กับยอดคงคลังที่ระบบคำนวณอัตโนมัติ (FR-1.5) ไม่ตรงกัน ต้องมีการแจ้งเตือน โดยใช้ข้อความแจ้งเตือนตรงตามนี้คำต่อคำ: "ยอดคงเหลือที่เจ้าหน้าที่แจ้งกับยอดคงคลังที่ระบบคำนวณอัตโนมัติ ไม่ตรงกัน โปรดตรวจสอบ หากไม่แน่ใจให้ปรึกษา รพศ.ชร. (แม่ข่าย)" — raw requirement ไม่ได้ระบุเกณฑ์ความคลาดเคลื่อนที่ยอมรับได้ (tolerance) จึงตีความว่าเป็นการเปรียบเทียบแบบตรงเป๊ะ (exact-match/zero-tolerance): ไม่ตรงกันแม้เพียงเล็กน้อยก็ต้องแจ้งเตือน
- **ยืนยันบางส่วน (20260823 รอบ 3, ตอบตรงจากเภสัชกรเจ้าของระบบ):** เภสัชกรเป็นผู้ตรวจสอบและคอนเฟิร์มเมื่อระบบแจ้งเตือนยอดไม่ตรงกัน — ไม่ใช่เจ้าหน้าที่ รพ.สต. เองที่เป็นผู้แก้ไขค่า และไม่ใช่ต้องส่งเรื่องให้ รพศ.ชร. (แม่ข่าย) เสมอไป (การปรึกษา รพศ.ชร. ตามข้อความแจ้งเตือนเป็นทางเลือกเสริมเมื่อไม่แน่ใจเท่านั้น ไม่ใช่ขั้นตอนบังคับ) — ยังไม่ได้ตอบว่าผลลัพธ์ของการคอนเฟิร์มมีผลต่อค่าที่บันทึกในระบบอย่างไร และยังไม่ได้ตอบว่าขั้นตอนนี้ผูกกับการอนุมัติระดับ 1 (BL-004) เดิมหรือแยกต่างหาก
- **ยืนยันครบ (20260823 รอบ 4, ตอบตรงจากเภสัชกรเจ้าของระบบ ผ่าน AskUserQuestion — ปิด Open Item ของ FR-1.9 ทั้งหมด):** (1) เมื่อเภสัชกรคอนเฟิร์มการกระทบยอด **เภสัชกรกรอกยอดที่ถูกต้องเอง** (ไม่ใช่ระบบยึดยอดที่คำนวณอัตโนมัติเป็นค่าที่ถูกต้อง และไม่ใช่แค่การรับทราบเฉยๆ) — ค่าที่กรอกกลายเป็นยอดคงเหลือที่ถูกต้อง/มีผลผูกพันต่อ (2) ขั้นตอนนี้**รวมอยู่ในขั้นตอนอนุมัติระดับ 1 เดิม** (FR-1.2/US-1.2/BL-004) ไม่ใช่ขั้นตอนแยกใหม่ — ดู FR-1.9b

## เพิ่มเติม 20260823: ยืนยันพฤติกรรมกระทบยอด (ปิด open item BL-032)

**Raw requirement ที่ได้รับ:** เภสัชกรเจ้าของระบบยืนยันโดยตรงว่าเมื่อยอดคงเหลือที่เจ้าหน้าที่แจ้งเอง (FR-1.1a) กับยอดคงคลังที่ระบบคำนวณอัตโนมัติ (FR-1.5) ไม่ตรงกัน ต้องมีการแจ้งเตือน โดยระบุข้อความแจ้งเตือนคำต่อคำมาให้ครบถ้วน

**การตัดสินใจ:** แก้ไขไฟล์ spec 002 นี้โดยตรง (ไม่สร้างไฟล์ใหม่) เนื่องจากเป็นการปิด open item ที่มีอยู่แล้วในไฟล์นี้ (เดิมสะท้อนอยู่ใน backlog เป็น BL-032) ไม่ใช่ Epic/หัวข้อใหม่ — เพิ่ม FR-1.9 (ข้อสรุปที่ยืนยันแล้ว), เพิ่ม US-1.6 พร้อม Acceptance Criteria, ปิด Open Item เดิมเรื่องกระทบยอด และเพิ่ม Open Item ใหม่ที่แคบลง (เฉพาะขั้นตอนกระทบยอด/แก้ไขข้อมูลต่อจากการแจ้งเตือน ซึ่งยังไม่ได้ระบุมา)

**ประเด็นที่พิจารณาแล้วแต่ไม่ถามเพิ่ม:** raw requirement ไม่ได้ระบุเกณฑ์ความคลาดเคลื่อนที่ยอมรับได้ (tolerance band) — ตีความว่าเป็นการเปรียบเทียบแบบตรงเป๊ะ (exact-match/zero-tolerance) เนื่องจากข้อความแจ้งเตือนที่ยืนยันมาใช้คำว่า "ไม่ตรงกัน" ไม่มีคำใดสื่อถึงช่วงที่ยอมรับได้ และเป็นทางเลือกที่ปลอดภัยกว่าในเชิงคลินิก (ไม่ปล่อยผ่านความคลาดเคลื่อนเล็กน้อยที่อาจสะสมเป็นปัญหาที่ safety stock ในระยะยาว) — หากเจ้าของข้อกำหนดต้องการเกณฑ์ tolerance ที่ต่างจากนี้ ให้แจ้งเพิ่มเติมได้ในรอบถัดไป

**Changelog สั้น:** เพิ่ม FR-1.9, US-1.6 พร้อม AC; ปิด Open Item เดิม "กระทบยอดคงเหลือที่แจ้งเอง vs. ยอดคงคลังที่ระบบคำนวณ"; เพิ่ม Open Item ใหม่ (ขอบเขตขั้นตอนกระทบยอดจริง ยังไม่ยืนยัน)

## เพิ่มเติม 20260823 (รอบ 3): ยืนยันบางส่วน — ผู้รับผิดชอบตรวจสอบ/คอนเฟิร์มยอดไม่ตรงกัน

**Raw requirement ที่ได้รับ:** เภสัชกรเจ้าของระบบยืนยันขั้นตอนหลังจากระบบแจ้งเตือนยอดไม่ตรงกัน (FR-1.9/US-1.6) ว่า **เภสัชกรเป็นผู้ตรวจสอบและคอนเฟิร์ม** ไม่ใช่เจ้าหน้าที่ รพ.สต. เองที่แก้ไขค่า และไม่ใช่ต้องส่งเรื่องให้ รพศ.ชร. (แม่ข่าย) เสมอไป — ข้อความแจ้งเตือนที่บอกให้ปรึกษา รพศ.ชร. เป็นเพียงทางเลือกเมื่อไม่แน่ใจเท่านั้น ไม่ใช่ขั้นตอนบังคับ พร้อมตั้งข้อสังเกตว่าขั้นตอนนี้ **น่าจะ** เกิดขึ้นระหว่างขั้นตอนอนุมัติคำขอเบิกระดับ 1 ที่เภสัชกรตรวจสอบคำขออยู่แล้ว (FT-002/BL-004) แต่ไม่ให้ agent สมมติจุดผูกนี้เองโดยไม่ถามยืนยันถ้ายังกำกวม

**การตัดสินใจ:** แก้ไขไฟล์ spec 002 นี้โดยตรง (ไม่สร้างไฟล์ใหม่) เนื่องจากเป็นการต่อยอด/ตอบ Open Item ที่มีอยู่แล้วในไฟล์นี้ (FR-1.9/US-1.6, สะท้อนใน backlog เป็น BL-032) ไม่ใช่ Epic/หัวข้อใหม่ — เพิ่ม FR-1.9a (ยืนยันบางส่วน — เฉพาะ "ใครเป็นผู้ตรวจสอบ/คอนเฟิร์ม" และ "การปรึกษา รพศ.ชร. ไม่บังคับ"), เพิ่ม AC ใหม่ใน US-1.6, ปรับปรุงข้อความ Open Item เดิมให้แคบลงเหลือเฉพาะ 2 ประเด็นที่ยังไม่ตอบ

**เหตุผลที่ไม่ปิด Open Item ทั้งหมดในรอบนี้ (ทำไมยังต้องถามต่อ):** raw requirement ตอบคำถาม "ใครเป็นผู้กระทำ" (WHO) ชัดเจนแล้ว แต่ไม่ได้ตอบ 2 ประเด็นที่จำเป็นต่อการเขียน FR/AC ที่นำไปพัฒนาได้จริง:
1. **ผลลัพธ์ของ "คอนเฟิร์ม" ต่อค่าที่บันทึกในระบบ** — เป็นข้อมูลเชิงคลินิก/policy ที่เจ้าของข้อกำหนดต้องตัดสินใจเอง (ตาม CLAUDE.md ห้าม agent สมมติเกณฑ์/ขั้นตอนกระทบยอดเอง) ประโยคที่ให้มา ("ไม่ใช่เจ้าหน้าที่ รพ.สต. เองที่เป็นผู้แก้ไขค่า") บอกเป็นนัยว่ามีการ "แก้ไขค่า" เกิดขึ้นจริง แต่ไม่ได้ระบุว่าใครแก้ไขเป็นตัวเลขใหม่ หรือระบบยึดค่าใดเป็นค่าที่ถูกต้องโดยอัตโนมัติเมื่อคอนเฟิร์ม — เดาผิดจุดนี้จะกระทบความแม่นยำของ safety stock (FR-2.1b) โดยตรง จึงต้องถามแทนการเดา
2. **จุดผูกกับ flow เดิม (BL-004) หรือแยกใหม่** — raw requirement เองระบุชัดว่า "น่าจะ" เท่านั้น และสั่งห้าม agent สมมติจุดผูกนี้โดยไม่ถามยืนยันถ้ายังกำกวม จึงต้องถามแทนการเดา แม้จะมีความเป็นไปได้สูงว่าจะ reuse การอนุมัติระดับ 1

**หมายเหตุเรื่องเครื่องมือถาม:** เครื่องมือ `AskUserQuestion` ไม่อยู่ใน toolset ที่ subagent นี้เรียกใช้ได้โดยตรงในรอบนี้ — คำถามทั้ง 2 ข้อ (พร้อมตัวเลือกอย่างน้อย 3 แนวทางต่อข้อ) ถูกส่งกลับไปให้ผู้ประสาน (coordinator/main conversation) เป็นผู้ยิงคำถามให้เจ้าของข้อกำหนดยืนยันผ่าน `AskUserQuestion` จริงแทน — ยังไม่ได้รับคำตอบ ณ เวลาที่ปิดรอบนี้

**Changelog สั้น:** เพิ่ม FR-1.9a (ยืนยันบางส่วน); เพิ่ม AC ใหม่ใน US-1.6; แก้ Clarifications เพิ่มรายการ "ยืนยันบางส่วน 20260823 รอบ 3"; แก้ Open Item เดิมของ FR-1.9 ให้แคบลงเหลือ 2 ประเด็นย่อยที่ยังไม่ตอบ (ผลลัพธ์ของคอนเฟิร์มต่อค่าที่บันทึก, จุดผูกกับ BL-004 หรือแยกใหม่)

## เพิ่มเติม 20260823 (รอบ 4): ปิด Open Item สุดท้ายของ FR-1.9 — ผลลัพธ์ของ "คอนเฟิร์ม" และจุดผูกกับอนุมัติระดับ 1

**Raw requirement ที่ได้รับ:** เภสัชกรเจ้าของระบบตอบ 2 คำถามสุดท้ายที่ค้างอยู่ผ่าน `AskUserQuestion` ในการสนทนาหลัก — (1) เมื่อเภสัชกรคอนเฟิร์มยอดไม่ตรงกันแล้ว ค่าที่ถือเป็นค่าที่ถูกต้อง/บันทึกต่อคือ **เภสัชกรกรอกยอดที่ถูกต้องเอง** (ไม่ใช่ระบบยึดยอดคำนวณอัตโนมัติเป็นค่าที่ถูกต้อง และไม่ใช่การรับทราบเฉยๆ โดยไม่แก้ไขค่า) (2) ขั้นตอนตรวจสอบ/คอนเฟิร์มนี้ **รวมอยู่ในขั้นตอนอนุมัติคำขอเบิกระดับ 1 เดิม** (FR-1.2/US-1.2/BL-004) ไม่ใช่ขั้นตอนแยกใหม่

**การตัดสินใจ:** แก้ไขไฟล์ spec 002 นี้โดยตรง (ไม่สร้างไฟล์ใหม่) เนื่องจากเป็นการปิด Open Item สุดท้ายของ FR-1.9/FR-1.9a ที่มีอยู่แล้วในไฟล์นี้ ไม่ใช่ Epic/หัวข้อใหม่ — เพิ่ม **FR-1.9b** (โครงสร้างต่อยอดจาก FR-1.9a เดิม แทนที่จะแก้ทับ FR-1.9a เพื่อรักษาประวัติการยืนยันทีละส่วนไว้ให้ตรวจสอบย้อนหลังได้), อัปเดต AC ของ US-1.6 ให้ครบ, ปิด Clarifications/Open Items ที่ค้างอยู่ทั้งหมดของ FR-1.9

**หมายเหตุเรื่อง data model:** FR-1.9b ระบุเฉพาะกฎเชิงธุรกิจ (เภสัชกรกรอกค่าที่ถูกต้องเอง และค่านั้นกลายเป็นค่าที่ถูกต้อง/มีผลผูกพันต่อ แทนที่ยอดที่เจ้าหน้าที่ รพ.สต. รายงานเดิม) — **ไม่ได้ระบุ**ว่าฟิลด์ใดใน data model จะถูกเพิ่ม/แก้ไข (เช่น จะเพิ่มฟิลด์ใหม่แยกจาก "ยอดคงเหลือที่แจ้งเอง" เดิม หรือ overwrite ฟิลด์เดิม) เนื่องจากเป็นรายละเอียดระดับ data model/API ที่อยู่นอกขอบเขตของ spec requirement — ส่งต่อให้ `/build-data-api-spec` ออกแบบ
