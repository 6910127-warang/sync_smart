# ระบบและความปลอดภัย (RBAC และ Non-Functional Requirements)

**Spec ID:** 20260816-006
**สถานะ:** Migrated (ย้ายจาก `docs/requirements/REQUIREMENTS.md` ฉบับก่อนปรับโครงสร้างเอกสาร)
**วันที่สร้าง:** 20260816
**Epic:** 5 (Cross-cutting — ใช้ร่วมกับทุก Epic)

> บริบทร่วม/stakeholder table เต็มดูที่ [001 — ภาพรวมโครงการ](20260816-001-project-scope-and-problem-background.md)

## บริบท/ที่มา (Context)

เอกสารนี้รวบรวมความต้องการที่ไม่ใช่เชิงฟังก์ชัน (NFR) และการควบคุมสิทธิ์การเข้าถึง (RBAC) ที่ใช้ร่วมกันทุก Epic แทนที่จะซ้ำในแต่ละไฟล์

## ขอบเขต (Scope)

- **อยู่ในขอบเขต:** RBAC ตาม role, Usability, Performance, Availability, PDPA (รวม Consent), การเก็บ Log ตามกฎหมาย IT, Compatibility กับ INVC, ช่องทางแจ้งเตือน
- **นอกขอบเขต:** รายละเอียด business logic ของแต่ละ Epic (ดูไฟล์ Epic นั้นๆ)

## Non-Functional Requirements

| หมวด | รายละเอียด |
|---|---|
| Usability | ใช้งานผ่านเว็บเบราว์เซอร์ทั่วไป ออกแบบเป็น **Responsive เต็มรูปแบบ** รองรับ**ทุกอุปกรณ์** (คอมพิวเตอร์/โน้ตบุ๊ก, แท็บเล็ต, มือถือ) — เปลี่ยนจากมติเดิม (Desktop-first เท่านั้น ดู "เพิ่มเติม 20260820" ด้านล่าง) ครอบคลุมทั้ง 4 role (เจ้าหน้าที่ รพ.สต., เภสัชกรระดับ 1/2, ผู้บริหาร, Admin) และทุกหน้าจอของระบบ ผู้ใช้ส่วนใหญ่ไม่ใช่สายเทคนิค ควรออกแบบ UI ให้เรียบง่ายบนทุกขนาดหน้าจอ — breakpoint ที่ยืนยันแล้ว (20260820, ใช้ค่ามาตรฐานทั่วไป): **mobile 320-767px / tablet 768-1023px / desktop 1024px ขึ้นไป** เหตุผลของการเปลี่ยนมติ: เจ้าหน้าที่ รพ.สต. เริ่มใช้แท็บเล็ต/มือถือในการทำงานภาคสนามจริง |
| Security / สิทธิ์การเข้าถึง (RBAC) | ต้องแยกสิทธิ์ตาม Role อย่างชัดเจน: เจ้าหน้าที่ รพ.สต. เห็นเฉพาะหน่วยตนเอง, ผู้บริหาร Read-only + drill-down ทั้งเครือข่าย, Admin แก้ไขข้อมูลธุรกิจได้เฉพาะกรณีฉุกเฉินและต้องมี audit log ทุกครั้ง รวมถึงบังคับกฎ **ห้ามอนุมัติระดับ 1 และ 2 ด้วยเภสัชกรคนเดียวกัน** ในคำขอเดียวกัน (ดู [002](20260816-002-ncd-drug-requisition-core.md) FR-1.2) |
| Performance | เครือข่ายมี รพ.สต. 29 แห่ง + รพ.แม่ข่าย 1 แห่ง รวมผู้ใช้งานพร้อมกันคาดว่าไม่เกินหลักสิบราย ระบบต้องตอบสนองการบันทึก/ดูยอดคงคลัง**ภายใน 5 วินาที** |
| Availability | ระบบต้องพร้อมใช้งาน**เฉพาะเวลาราชการ** (เช่น 08:00-16:30 น. จันทร์-ศุกร์) เพียงพอ — สอดคล้องกับเวลาทำงานของเจ้าหน้าที่ รพ.สต./เภสัชกร ไม่ต้องรองรับ 24/7 |
| Data Privacy / PDPA | ต้องมีมาตรการป้องกันข้อมูลตาม PDPA เนื่องจากเชื่อมโยงถึงข้อมูลการใช้ยาของผู้ป่วยทางอ้อม — กำหนดเป็น**ระดับพื้นฐาน (Basic compliance)**: Consent Banner (FR-6.3) + ประกาศ Privacy Policy เท่านั้น ไม่ต้องมี DPO/Data Protection Impact Assessment (DPIA) เป็นทางการสำหรับระบบนี้โดยเฉพาะ |
| Log Retention (กฎหมาย IT) | ต้องเก็บ Audit Trail ทางธุรกิจ ([002](20260816-002-ncd-drug-requisition-core.md) FR-1.6) และ System Access Log (FR-6.1) ไว้**อย่างน้อย 90 วัน** ตาม พ.ร.บ. ว่าด้วยการกระทำความผิดเกี่ยวกับคอมพิวเตอร์ พ.ศ. 2550 (แก้ไขเพิ่มเติม) มาตรา 26 — หลังพ้น 90 วันให้**เก็บต่อเนื่องไม่มีกำหนดลบ** (ไม่ auto-delete ในเฟสนี้) เพื่อประโยชน์ด้าน audit/วิเคราะห์ย้อนหลัง — ดู FR-6.1/FR-6.2 |
| Compatibility | ไฟล์ Excel ที่ส่งออก ([005](20260816-005-legacy-system-integration.md) FR-4.1) ต้องรองรับรูปแบบคอลัมน์ที่ INVC นำเข้าได้จริง (ดู FR-4.3) — ไม่ต้องพิจารณาความเข้ากันได้กับ HOSxP เนื่องจาก รพ.แม่ข่ายไม่ได้เชื่อม HIS หลักเข้ากับ INVC — **ยืนยันแล้ว 20260823** จากไฟล์ตัวอย่างจริง 46 ไฟล์ (3 คอลัมน์ `HOSP_CODE`/`QTY_DISP`/`WORKING_CODE`) ดู [005](20260816-005-legacy-system-integration.md) FR-4.3 |
| Notification Channel | การแจ้งเตือนสต็อกต่ำ ([003](20260816-003-stock-forecast-alerts.md) FR-2.3) และการแจ้ง "ขอปรึกษา" ([002](20260816-002-ncd-drug-requisition-core.md) FR-1.1b) ต้องส่งผ่าน**ทั้งอีเมลและ LINE** (LINE Official Account ที่มีอยู่แล้ว) |
| Reliability / Backup & Recovery | ต้องมีการสำรองข้อมูล (Backup) **รายวัน** โดยกำหนดเป้าหมาย **RPO (Recovery Point Objective) ≤ 24 ชั่วโมง** — หากระบบล่ม ข้อมูลที่กู้คืนได้ต้องไม่เก่ากว่าการสำรองครั้งล่าสุดเกิน 24 ชั่วโมง (มติเพิ่มเติม 20260824, ดู FR-6.11 ไม่มี — เก็บเป็น NFR ล้วน ตามรูปแบบเดียวกับ Availability/Performance) — เมื่อรอบสำรองข้อมูลล้มเหลว ต้องแจ้งเตือน Admin ผ่าน**อีเมล + LINE OA** (ช่องทางเดียวกับการแจ้งเตือนอื่นของระบบ, ยืนยันแล้ว 20260825) |
| Data Integrity / Concurrency Control | เมื่อมีผู้ใช้มากกว่า 1 คนพยายามแก้ไข/อนุมัติคำขอเบิกเดียวกันพร้อมกัน ระบบต้องตรวจสอบสถานะล่าสุดของคำขอก่อนบันทึกทุกครั้ง (**Optimistic Concurrency Check**) และแสดง error แจ้งผู้ใช้ทันทีหากพบว่ามีผู้อื่นแก้ไข/บันทึกไปแล้ว — เกี่ยวพันโดยตรงกับกฎห้ามอนุมัติระดับ 1 และ 2 ด้วยเภสัชกรคนเดียวกัน ([002](20260816-002-ncd-drug-requisition-core.md) FR-1.2, ดู FR-6.5) |
| Security — Authentication & Session Management | (1) บังคับให้ผู้ใช้**เปลี่ยนรหัสผ่านเมื่อ login ครั้งแรก** สำหรับผู้ใช้งานทุกคน — ความยาวขั้นต่ำของรหัสผ่านใหม่ **8 ตัวอักษร** (ไม่บังคับอักขระพิเศษ/ตัวเลขเพิ่มเติม, ยืนยันแล้ว 20260825) (2) **Session timeout อัตโนมัติเมื่อไม่มีการใช้งานประมาณ 30 นาที** สำหรับผู้ใช้งานทุกคน (3) เพิ่ม**การยืนยันตัวตนสองปัจจัย (2FA/OTP) เฉพาะบัญชีเภสัชกรผู้อนุมัติระดับ 1 และ 2 เท่านั้น** เนื่องจากมีผลผูกพันทาง audit/กฎหมาย — role อื่น (เจ้าหน้าที่ รพ.สต., ผู้บริหาร, Admin) ไม่บังคับ 2FA — อนุญาตกรอก OTP ผิดได้ไม่เกิน **3 ครั้ง** ก่อนล็อกบัญชีชั่วคราว, รหัส OTP หมดอายุภายใน **5 นาที**, ส่งผ่าน**อีเมลที่มีอยู่แล้วในระบบ** (ช่องทางติดต่อสำหรับแจ้งเตือน — ไม่เพิ่มช่องทางใหม่) — หลังล็อก อนุญาตให้ขอรหัส OTP ชุดใหม่ได้**อัตโนมัติหลังผ่านไป 5 นาที** ไม่ต้องรอ Admin ปลดล็อก (ยืนยันแล้ว 20260825) (ดู FR-6.6, FR-6.7, FR-6.8) |
| Data Encryption | เข้ารหัสข้อมูลระหว่างส่งผ่านเครือข่าย (**in transit**) เป็นอย่างน้อย — **ไม่บังคับ**เข้ารหัสข้อมูลที่จัดเก็บ (at rest) เพิ่มเติมในเฟสนี้ สอดคล้องกับระดับ PDPA แบบพื้นฐานที่ยืนยันไว้แล้ว (ดู NFR Data Privacy/PDPA ด้านบน, FR-6.9) — เมื่อตรวจพบความพยายามเชื่อมต่อผ่านช่องทางที่ไม่เข้ารหัส ระบบต้อง**ปฏิเสธการเชื่อมต่อทันทีพร้อมแสดง error** ไม่ redirect ไปช่องทางที่เข้ารหัสให้อัตโนมัติ (ยืนยันแล้ว 20260825) |
| Compatibility — เบราว์เซอร์ | รองรับเบราว์เซอร์สมัยใหม่ (**Evergreen**) 2 เวอร์ชันล่าสุดของแต่ละยี่ห้อหลัก (เช่น Chrome, Edge, Firefox, Safari) — ไม่ต้องรองรับเบราว์เซอร์รุ่นเก่ากว่านั้น |
| Scalability | ออกแบบให้รองรับ**เฉพาะขนาดเครือข่ายปัจจุบัน** (รพ.สต. 29 แห่ง + รพ.แม่ข่าย 1 แห่ง) — **ไม่ต้อง**ออกแบบเผื่อขยายเครือข่ายไปยังอำเภอ/พื้นที่อื่นในอนาคต (resolved) |
| Disaster Recovery | กำหนด **RTO (Recovery Time Objective) ≤ 4 ชั่วโมงในเวลาราชการ** เมื่อระบบล่ม พร้อมต้องมี**ขั้นตอนสำรองแบบ manual (fallback process)** เช่น กลับไปบันทึกด้วยมือ/Excel ชั่วคราว ระหว่างรอระบบกลับมาใช้งานได้ — หลังระบบกลับมาใช้งานได้ ต้องมี**หน้าจอ/เครื่องมือนำเข้าเฉพาะสำหรับ Bulk Import ข้อมูลจาก Excel** เพื่อนำข้อมูลที่บันทึกด้วยมือระหว่างระบบล่มกลับเข้าสู่ระบบ ไม่ใช่การกรอกซ้ำทีละรายการผ่านหน้าจอปกติ (ยืนยันแล้ว 20260825) |
| Maintainability / Configurability | ผู้ดูแลระบบ (Admin) ต้องสามารถปรับค่า config ที่มีแนวโน้มเปลี่ยนตามนโยบายได้เองผ่านหน้าจอระบบ โดย**ไม่ต้องแก้โค้ด/รอรอบพัฒนาใหม่** — ตัวอย่าง: จำนวนวันแจ้งเตือนล่วงหน้าก่อนกำหนดส่งคำขอเบิกประจำเดือน (BL-009b — **ยืนยันแล้ว 20260825 = 2 วัน** ดู [002](20260816-002-ncd-drug-requisition-core.md) FR-1.8) — การตรวจสอบค่าที่ Admin กรอกเข้าไปกำหนดขอบเขตขั้นต่ำ/สูงสุด**เฉพาะแต่ละ Config Key** ไม่ใช้กฎทั่วไปกฎเดียว — Config Key "จำนวนวันแจ้งเตือนล่วงหน้า" (BL-009b) กำหนดขอบเขต **1 ถึง 30 วัน** (ยืนยันแล้ว 20260825) (ดู FR-6.10) |
| Accessibility | **ไม่จำเป็น**ต้องออกแบบตามมาตรฐานการเข้าถึงสำหรับผู้พิการ (WCAG) เนื่องจากเป็นระบบใช้งานภายในเครือข่าย รพ.สต./รพ.แม่ข่ายเท่านั้น ไม่ใช่เว็บไซต์สาธารณะ (resolved — เป็นการยืนยันขอบเขตที่ไม่ต้องดำเนินการ จึงไม่มี backlog item แยก) |
| กฎหมายไซเบอร์เพิ่มเติม | ปัจจุบัน**ไม่มี**ข้อกำหนดด้านความมั่นคงปลอดภัยไซเบอร์เพิ่มเติมนอกเหนือจาก พ.ร.บ. ว่าด้วยการกระทำความผิดเกี่ยวกับคอมพิวเตอร์ฯ ที่ระบุไว้แล้วในหัวข้อ Log Retention ด้านบน (เช่น ยังไม่มีการยืนยันสถานะ CII ตาม พ.ร.บ.ไซเบอร์ฯ 2562) — เจ้าของระบบจะแจ้งเพิ่มเติมภายหลังหากมีการยืนยันสถานะทางกฎหมายเพิ่ม (resolved-no-action ณ ตอนนี้ — ห้ามสมมติ/สร้างข้อกำหนดล่วงหน้าเรื่องนี้เอง จึงไม่มี backlog item แยก) |

## Functional Requirements

RBAC ราย role โดยละเอียดอยู่ในตาราง stakeholder ที่ [001](20260816-001-project-scope-and-problem-background.md) — ด้านล่างคือ FR ใหม่เฉพาะเรื่องกฎหมาย IT/PDPA ที่เพิ่มเข้ามา (20260816):

| ID | รายละเอียด |
|---|---|
| FR-6.1 | ระบบต้องบันทึก **System Access Log** แยกจาก Audit Trail ทางธุรกิจ ([002](20260816-002-ncd-drug-requisition-core.md) FR-1.6) ครอบคลุมการ login/logout ของผู้ใช้งานทุกคน พร้อม**IP Address**ที่ใช้เข้าถึงระบบในแต่ละครั้ง |
| FR-6.2 | ระบบต้องเก็บรักษา Audit Trail ทางธุรกิจ (FR-1.6) และ System Access Log (FR-6.1) ไว้**อย่างน้อย 90 วัน** ตาม พ.ร.บ. ว่าด้วยการกระทำความผิดเกี่ยวกับคอมพิวเตอร์ พ.ศ. 2550 (แก้ไขเพิ่มเติม) มาตรา 26 — หลังพ้น 90 วัน**ให้เก็บต่อเนื่องไม่มีกำหนดลบ** ระบบไม่ต้องมีกลไก auto-delete ข้อมูลตามอายุในเฟสนี้ |
| FR-6.3 | ระบบต้องแสดง **Consent Banner** ตาม PDPA ให้ผู้ใช้งานทุกคน (จนท. รพ.สต., เภสัชกร, ผู้บริหาร, Admin) ยืนยันตอน **login ครั้งแรกเท่านั้น** (One-time consent ผูกกับบัญชีผู้ใช้ ไม่ต้องแสดงซ้ำทุกครั้งที่เข้าใช้งาน) เนื้อหาต้องระบุว่าระบบเก็บ IP Address (FR-6.1) — **ไม่ต้องมีข้อความเกี่ยวกับ Google Analytics หรือเครื่องมือวิเคราะห์การใช้งานเว็บใดๆ ในเฟสนี้** เนื่องจากยืนยันแล้วว่าจะไม่ใช้เครื่องมือดังกล่าว (หากตัดสินใจใช้ในอนาคต ต้องกลับมาปรับข้อความ Consent และแจ้งผู้ใช้ที่เคยยินยอมไปแล้วให้ยินยอมใหม่) |
| FR-6.4 | ระบบต้องบันทึกไว้เป็นหลักฐานว่าผู้ใช้แต่ละคนกดยินยอม Consent (FR-6.3) เมื่อใด — เป็นส่วนหนึ่งของ System Access Log (FR-6.1) |
| FR-6.5 | ระบบต้องตรวจสอบสถานะล่าสุดของคำขอเบิกก่อนบันทึกทุกครั้งที่มีการแก้ไข/อนุมัติ (**Optimistic Concurrency Check**) และแสดง error แจ้งผู้ใช้ทันทีหากพบว่ามีผู้อื่นแก้ไข/บันทึกคำขอนั้นไปแล้ว — เกี่ยวพันโดยตรงกับกฎห้ามอนุมัติระดับ 1 และ 2 ด้วยเภสัชกรคนเดียวกัน ([002](20260816-002-ncd-drug-requisition-core.md) FR-1.2/BL-004) |
| FR-6.6 | ระบบต้องบังคับให้ผู้ใช้ทุกคนเปลี่ยนรหัสผ่านเมื่อ login ครั้งแรก ก่อนเข้าใช้งานหน้าจออื่นของระบบ — รหัสผ่านใหม่ต้องมีความยาวขั้นต่ำ **8 ตัวอักษร** (ไม่บังคับอักขระพิเศษ/ตัวเลขเพิ่มเติม, ยืนยันแล้ว 20260825) |
| FR-6.7 | ระบบต้องตัด session อัตโนมัติ (session timeout) เมื่อผู้ใช้ไม่มีการใช้งานต่อเนื่องประมาณ **30 นาที** สำหรับผู้ใช้งานทุก role |
| FR-6.8 | ระบบต้องบังคับการยืนยันตัวตนสองปัจจัย (**2FA/OTP**) เพิ่มเติมจาก username/password เฉพาะบัญชี**เภสัชกรผู้อนุมัติระดับ 1 และระดับ 2** เท่านั้น เนื่องจากมีผลผูกพันทาง audit/กฎหมาย — role อื่น (เจ้าหน้าที่ รพ.สต., ผู้บริหาร, Admin) ไม่บังคับ — อนุญาตกรอก OTP ผิดได้ไม่เกิน **3 ครั้ง** ก่อนล็อกบัญชีชั่วคราว, รหัส OTP หมดอายุภายใน **5 นาที**, ส่งผ่าน**อีเมลที่มีอยู่แล้วในระบบ** (ช่องทางติดต่อสำหรับแจ้งเตือนเดิม ไม่เพิ่มช่องทางใหม่) — หลังล็อกชั่วคราว อนุญาตให้ขอรหัส OTP ชุดใหม่ได้**อัตโนมัติหลังผ่านไป 5 นาที** ไม่ต้องรอ Admin ปลดล็อก (ยืนยันแล้ว 20260825) |
| FR-6.9 | ระบบต้องเข้ารหัสข้อมูลทุกประเภทที่รับส่งระหว่าง client และระบบระหว่างทาง (**in transit**) — ไม่ครอบคลุมการเข้ารหัสข้อมูลที่จัดเก็บ (at rest) เพิ่มเติมในเฟสนี้ |
| FR-6.10 | ผู้ดูแลระบบ (Admin) ต้องสามารถปรับค่า config ของระบบที่มีแนวโน้มเปลี่ยนตามนโยบาย (เช่น จำนวนวันแจ้งเตือนล่วงหน้าตาม BL-009b) ได้เองผ่านหน้าจอระบบ โดยไม่ต้องแก้ไขโค้ดหรือรอรอบพัฒนาใหม่ — ตัวเลขจริงของ BL-009b **ยืนยันแล้ว 20260825 = 2 วัน** ดู [002](20260816-002-ncd-drug-requisition-core.md) FR-1.8 — การตรวจสอบค่าที่กรอกกำหนดขอบเขตขั้นต่ำ/สูงสุด**เฉพาะแต่ละ Config Key** — Config Key "จำนวนวันแจ้งเตือนล่วงหน้า" (BL-009b) กำหนดขอบเขต **1 ถึง 30 วัน** (ยืนยันแล้ว 20260825) |

## คำถามที่ถามและคำตอบที่ได้ (Clarifications)

- **ถาม:** ผู้ดูแลระบบ (Admin) ควรมีสิทธิ์แก้ไขข้อมูลธุรกิจได้หรือไม่? → **ตอบ:** มีสิทธิ์แก้ไขข้อมูลธุรกิจได้ในกรณีฉุกเฉิน (ต้องบันทึก audit log ทุกครั้ง)
- **ถาม:** เจ้าหน้าที่ รพ.สต. ควรเห็นข้อมูลของหน่วยอื่นได้หรือไม่? → **ตอบ:** เห็นเฉพาะหน่วยตนเอง
- **ถาม:** อุปกรณ์ที่เจ้าหน้าที่ รพ.สต. ใช้งานหลัก? → **ตอบ (เดิม, 20260816):** คอมพิวเตอร์/โน้ตบุ๊ก (Desktop-first) ไม่ต้องรองรับ responsive เต็มรูปแบบ — **เปลี่ยนแปลงแล้วใน 20260820** ดูรายการด้านล่าง
- **ถาม (20260820):** ต้องการปรับให้เว็บ (Prototype และระบบจริงในอนาคต) ใช้งานได้สวยงามเหมาะสมในหลายอุปกรณ์หรือไม่? → **ตอบ:** ต้องการ — ยกเลิกมติ Desktop-first เดิม เปลี่ยนเป็นรองรับ **"ทุกอุปกรณ์"** ไม่ใช่แค่ desktop/laptop ถึง 1024px ตามเดิม
- **ถาม (20260820):** ขอบเขต role/หน้าจอที่ต้องปรับ responsive ครอบคลุมแค่ไหน? → **ตอบ:** ครอบคลุมทั้ง 4 role และทุกหน้าจอ prototype ทั้งหมด (ไม่ใช่บาง role/บางหน้าจอ)
- **ถาม (20260820):** breakpoint ที่แน่นอนสำหรับ mobile/tablet/desktop คือเท่าใด และเหตุผล/แรงจูงใจเบื้องหลังการเปลี่ยนใจ? → **ตอบ:** ใช้ค่ามาตรฐานทั่วไป (mobile 320-767px / tablet 768-1023px / desktop 1024px ขึ้นไป) เหตุผล: เจ้าหน้าที่ รพ.สต. เริ่มใช้แท็บเล็ต/มือถือในการทำงานภาคสนามจริง
- **ถาม (20260820):** ขอบเขตนี้ใช้กับ Prototype เท่านั้น หรือใช้กับระบบจริงในอนาคตด้วย? → **ตอบ:** ใช้กับ NFR ของระบบจริงด้วย (แก้ spec 006/001 นี้โดยตรง) — ส่วนการปรับ Prototype จริง (ไฟล์ `prototype/`) เป็นงานแยกที่ทำโดย `prototype-builder` agent ในภายหลัง ไม่ได้อยู่ในขอบเขตของ spec/backlog รอบนี้
- **ถาม (20260816):** "ผู้ใช้งานที่เป็นผู้ซื้อ" ในข้อกำหนด PDPA หมายถึงใคร? → **ตอบ:** หมายถึงผู้ใช้งานระบบทุกคน (จนท. รพ.สต., เภสัชกร, ผู้บริหาร) — เป็นคำที่ใช้ทั่วไปตามศัพท์กฎหมาย ไม่ได้หมายถึงลูกค้า/ผู้ซื้อสินค้าจริง
- **ถาม (20260816):** ต้องการใช้ Google Analytics จริงหรือไม่? → **ตอบ:** ยังไม่ตัดสินใจ แต่ต้องการเผื่อ requirement (ข้อความ Consent) ไว้ล่วงหน้า
- **ถาม (20260816):** การเก็บ log 90 วันครอบคลุม log ประเภทใด? → **ตอบ:** ทั้ง audit trail ทางธุรกิจที่มีอยู่แล้วและ system access log (login/logout, IP) ที่เพิ่มใหม่
- **ถาม (20260816):** Consent banner ควรแสดงเมื่อไร? → **ตอบ:** ตอน login ครั้งแรกเท่านั้น (ผูกกับบัญชีผู้ใช้)
- **ถาม (20260816):** เป้าหมาย response time? → **ตอบ:** ภายใน 5 วินาที
- **ถาม (20260816):** ระดับความพร้อมใช้งาน (Availability)? → **ตอบ:** เฉพาะเวลาราชการ (08:00-16:30 น. จันทร์-ศุกร์)
- **ถาม (20260816):** ระดับความเข้มงวดของ PDPA นอกเหนือจาก Consent banner? → **ตอบ:** ระดับพื้นฐาน (Basic compliance) ไม่ต้องมี DPO/DPIA เป็นทางการ
- **ถาม (20260816):** หลังพ้น 90 วัน log ควรทำอย่างไร? → **ตอบ:** เก็บต่อเนื่องไม่มีกำหนดลบ ไม่ต้อง auto-delete
- **ถาม (20260816):** ต้องการใช้ Google Analytics จริงหรือไม่ในเฟสนี้? → **ตอบ:** ไม่ใช้ในเฟสนี้ — ตัด requirement เรื่อง analytics ออกจาก FR-6.3 เหลือแค่ consent เรื่อง IP Address
- **มติ (20260824 — NFR เพิ่มเติมชุดใหญ่ 10 หมวด):** เจ้าของข้อกำหนด (เภสัชกร) ตัดสินใจแล้วนอกรอบสนทนากับผู้ใช้โดยตรง โดยผู้ใช้นำเสนอทางเลือกพร้อมข้อดี/ข้อเสียของแต่ละหมวดให้พิจารณาก่อน แล้วเลือกคำตอบสุดท้ายมาครบทั้ง 10 ข้อ (ไม่ใช่การสัมภาษณ์แบบเปิดของ requirement-writer เอง) สรุปมติ: (1) Backup/Recovery รายวัน, RPO ≤ 24 ชม. (2) Concurrency control แบบ Optimistic — ตรวจสอบสถานะซ้ำก่อนบันทึกทุกครั้ง + แจ้ง error (ผูกกับกฎห้ามอนุมัติ 1/2 คนเดียวกัน, BL-004) (3) บังคับเปลี่ยนรหัสผ่าน login ครั้งแรก + session timeout ~30 นาทีทุกคน + 2FA/OTP เฉพาะเภสัชกรผู้อนุมัติระดับ 1/2 (4) เข้ารหัสเฉพาะ in transit ไม่บังคับ at rest เพิ่มเติม (5) รองรับเบราว์เซอร์ Evergreen 2 เวอร์ชันล่าสุดต่อยี่ห้อ (6) Scalability เฉพาะขนาดเครือข่ายปัจจุบัน (29+1) ไม่เผื่อขยายอนาคต (7) DR: RTO ≤ 4 ชม. ในเวลาราชการ + ต้องมี manual fallback process (8) Admin ปรับ config ที่เปลี่ยนตามนโยบายได้เองผ่านหน้าจอ ไม่ต้องแก้โค้ด (cross-ref BL-009b — ตัวเลขวันยังคง `[รอยืนยัน]` แยกต่างหาก ไม่ได้ตอบในรอบนี้) (9) ไม่บังคับ WCAG เนื่องจากเป็นระบบใช้งานภายใน (10) ปัจจุบันไม่มีข้อกำหนดกฎหมายไซเบอร์เพิ่มเติมนอกเหนือจาก พ.ร.บ.คอมพิวเตอร์ฯ ที่มีอยู่แล้ว — จะแจ้งเพิ่มภายหลังหากมีการยืนยันสถานะทางกฎหมายใหม่ (ไม่สมมติ/สร้างข้อกำหนดล่วงหน้าเอง) — ดูรายละเอียดเต็มในตาราง NFR/FR ด้านบนและหัวข้อ "เพิ่มเติม 20260824" ท้ายไฟล์

## เพิ่มเติม 20260820: เปลี่ยนจาก Desktop-first เป็น Responsive เต็มรูปแบบ

**Raw requirement:** เจ้าของข้อกำหนดขอปรับให้เว็บ (ทั้ง Prototype และระบบจริงในอนาคต) "เปิดได้สวยๆ เหมาะสมในหลายอุปกรณ์" — เมื่อถามย้ำเพื่อยืนยันขอบเขต ยืนยันว่าต้องการรองรับ **"ทุกอุปกรณ์"** (ไม่ใช่แค่ desktop/laptop ถึง 1024px ตามมติเดิม) และต้องครอบคลุมทั้ง 4 role / ทุกหน้าจอ

**การเปลี่ยนแปลง:** ยกเลิกมติเดิมที่เคยตอบไว้ (20260816) ว่า "Desktop-first ไม่ต้องรองรับ responsive เต็มรูปแบบ" — เปลี่ยนเป็น NFR Usability ใหม่: Responsive เต็มรูปแบบ รองรับมือถือ/แท็บเล็ต/เดสก์ท็อป ครอบคลุมทุก role ทุกหน้าจอ (ดูตาราง NFR ด้านบน) มติเดิมยังคงเก็บไว้ในหัวข้อ Clarifications เพื่อรักษาประวัติการตัดสินใจ (ไม่ลบทิ้ง)

**ขอบเขตของการเปลี่ยนแปลงนี้:** ใช้กับ NFR ของ**ระบบจริง**ในอนาคต (แก้ spec 006/001 นี้โดยตรง) ไม่ใช่แค่ Prototype — ส่วนการปรับหน้าจอ Prototype ที่มีอยู่แล้วใน `prototype/` เป็นงานแยกต่างหากที่จะทำโดย `prototype-builder` agent ภายหลัง ไม่ได้อยู่ในขอบเขตของการแก้ไข spec/backlog รอบนี้

**ยืนยันเพิ่มเติม (20260820 รอบ 2):** breakpoint = mobile 320-767px / tablet 768-1023px / desktop 1024px ขึ้นไป (ค่ามาตรฐานทั่วไป) เหตุผลของการเปลี่ยนมติ = เจ้าหน้าที่ รพ.สต. เริ่มใช้แท็บเล็ต/มือถือในการทำงานภาคสนามจริง — Epic 5 ไม่มี open item ของตัวเองเหลืออยู่อีก

**ที่มา:** มติที่เจ้าของระบบ (เภสัชกร) ตัดสินใจไปแล้วในบทสนทนาก่อนหน้ากับผู้ใช้โดยตรง โดยผู้ใช้นำเสนอทางเลือกพร้อมข้อดี/ข้อเสียของแต่ละหมวดให้พิจารณาก่อนแล้วจึงเลือกคำตอบสุดท้าย — **ไม่ใช่การสัมภาษณ์แบบเปิดของ requirement-writer** ในรอบนี้ (ดูสรุปมติทั้ง 10 ข้อในหัวข้อ Clarifications ด้านบน)

**การเปลี่ยนแปลง:**
- เพิ่มแถวใหม่ 10 แถวในตาราง Non-Functional Requirements ด้านบน: Reliability/Backup & Recovery, Data Integrity/Concurrency Control, Security — Authentication & Session Management, Data Encryption, Compatibility — เบราว์เซอร์, Scalability, Disaster Recovery, Maintainability/Configurability, Accessibility, กฎหมายไซเบอร์เพิ่มเติม
- เพิ่ม FR-6.5 ถึง FR-6.10 ในตาราง Functional Requirements ด้านบน สำหรับ 6 หมวดที่มีพฤติกรรมระบบชัดเจนที่ทดสอบได้ (Concurrency Check, บังคับเปลี่ยนรหัสผ่านครั้งแรก, Session Timeout, 2FA/OTP, Data Encryption in transit, Configurability) — อีก 4 หมวด (Backup/Recovery, Browser Compatibility, Scalability, Disaster Recovery) เก็บเป็น NFR ล้วนโดยไม่มี FR แยก ตามรูปแบบเดียวกับที่ Performance/Availability ของไฟล์นี้ใช้อยู่ก่อนแล้ว (คุณสมบัติเชิงคุณภาพ/ขอบเขตของระบบ ไม่ใช่พฤติกรรมฟังก์ชันเฉพาะจุด)

**เหตุผลที่ไม่สร้าง Backlog item ให้ข้อ 9 (Accessibility) และข้อ 10 (กฎหมายไซเบอร์เพิ่มเติม):** ทั้งสองข้อเป็นมติ "ยืนยันว่าไม่ต้องทำ/ไม่มีข้อกำหนดเพิ่ม" ไม่มีพฤติกรรมระบบที่ต้อง implement หรือ test case ที่จะเขียนได้จริง (ต่างจาก BL-023 ที่เป็นการปฏิเสธ feature/integration ที่เคยถูกพิจารณาอย่างจริงจังและอาจถูกทบทวนใหม่ในอนาคต) จึงบันทึกไว้เป็นเพียงหมายเหตุ resolved-no-action ในตาราง NFR และ Clarifications ด้านบนเท่านั้น ไม่เพิ่ม BL-ID ใหม่ — ดูรายละเอียดการตัดสินใจนี้ในหัวข้อ "รายงานกลับ" ของ log/20260824-log.md

**Backlog items ใหม่ที่เพิ่มจาก 8 ข้อที่เหลือ (actionable):** BL-035 ถึง BL-043 (แยก "Security — Authentication & Session Management" ออกเป็น 2 backlog item คือ BL-037 กับ BL-038 เนื่องจากมี AC/ผู้ใช้เป้าหมายต่างกันชัดเจน — บังคับเปลี่ยนรหัสผ่าน+session timeout ใช้กับทุก role ส่วน 2FA/OTP ใช้เฉพาะเภสัชกรผู้อนุมัติ) — ดู [backlog.md](../backlog.md) Epic 5

**ข้อ 8 (Maintainability/Configurability) เชื่อมโยงกับ BL-009b:** ในรอบนี้ (20260824) ยืนยันเฉพาะ**หลักการ**ว่า Admin ต้องปรับค่า config ประเภทนี้ได้เองผ่านหน้าจอ ไม่ฝังในโค้ด — ตัวเลขจำนวนวันแจ้งเตือนล่วงหน้าที่แน่นอนของ BL-009b **ปิดแล้วในรอบถัดมา (20260825) = 2 วัน** ดู [002](20260816-002-ncd-drug-requisition-core.md) FR-1.8 และหัวข้อ "เพิ่มเติม 20260825" ด้านล่าง — ไม่มี Open Item ค้างอีกต่อไป

**Priority ที่กำหนด (MoSCoW):** อิงจากสัญญาณที่ชัดเจนในมติ — หมวดที่ระบุว่า "มีผลผูกพันทาง audit/กฎหมาย" หรือเป็นขอบเขต/ความปลอดภัยพื้นฐาน (Backup, Concurrency, Auth/Session, 2FA, Encryption, Browser Compatibility, Scalability, Disaster Recovery) กำหนดเป็น **Must**; ส่วน Configurability (BL-043) เป็นความสะดวกเชิง operation ไม่กระทบความถูกต้อง/ความปลอดภัยของระบบโดยตรง กำหนดเป็น **Should** — ไม่มีจุดที่กำกวมพอต้องถามผู้ใช้เพิ่มสำหรับการกำหนด priority รอบนี้

## เพิ่มเติม 20260825: ปิด Open Items ค่า/เกณฑ์ของรหัสผ่าน, OTP, และ Config Validation (BL-037/BL-038/BL-043)

**ที่มา:** เภสัชกรเจ้าของระบบยืนยันผ่าน `AskUserQuestion` ในการสนทนาหลัก โดยผู้ใช้นำเสนอตัวเลือกพร้อมข้อดี/ข้อเสียของแต่ละประเด็นให้พิจารณาก่อนเลือกคำตอบสุดท้าย — ประเด็นเหล่านี้เดิมถูกบันทึกเป็น `[รอยืนยัน]` ใน [07-api-spec.md](../07-api-spec.md) หัวข้อ 5 (ไม่ใช่ในไฟล์นี้โดยตรง เนื่องจากตอนเพิ่ม FR-6.6/FR-6.8/FR-6.10 เมื่อ 20260824 ยังไม่มีการยืนยันตัวเลขจริง)

**มติ:**
1. **เกณฑ์ความปลอดภัยขั้นต่ำของรหัสผ่านใหม่ (FR-6.6/BL-037):** ความยาวขั้นต่ำ 8 ตัวอักษร ไม่บังคับอักขระพิเศษ/ตัวเลขเพิ่มเติม
2. **จำนวนครั้ง/อายุ OTP (FR-6.8/BL-038):** อนุญาตกรอกผิดได้ไม่เกิน 3 ครั้งก่อนล็อก, หมดอายุภายใน 5 นาที
3. **ช่องทางส่ง OTP (FR-6.8/BL-038):** ใช้อีเมลที่มีอยู่แล้วในระบบ (ช่องทางติดต่อสำหรับแจ้งเตือนเดิม) ไม่เพิ่มช่องทางใหม่
4. **ขอบเขตค่าที่ยอมรับได้ของ Config Key (FR-6.10/BL-043):** กำหนดขั้นต่ำ/สูงสุดเฉพาะแต่ละ Config Key แทนกฎทั่วไปกฎเดียว

**การตัดสินใจ:** แก้ไขไฟล์ spec 006 นี้โดยตรง — เพิ่มค่าที่ยืนยันแล้วเข้าไปใน NFR table (Security — Authentication & Session Management) และ FR-6.6/FR-6.8/FR-6.10 ด้านบน — คู่กับการปิด open item เดิมใน [07-api-spec.md](../07-api-spec.md) หัวข้อ 5 ในรอบเดียวกัน
