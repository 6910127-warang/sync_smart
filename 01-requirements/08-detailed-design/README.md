## นโยบายรวม (Shared Conventions — ตัดสินใจโดยผู้ใช้ 20260823 ผ่าน AskUserQuestion)

ไฟล์ทั้งหมดในโฟลเดอร์นี้อ้างอิงกลับมาที่หัวข้อนี้ผ่านลิงก์ "ดูนโยบาย granularity/exception/state-diagram ที่ใช้ร่วมกันทุกไฟล์ใน README.md":

- **ขอบเขตการสร้าง:** เดิมทั้งหมด 25 Feature ในรอบเดียว (ไม่แบ่ง Epic-by-Epic) เมื่อ 20260823 — ขยายเป็น 34 Feature เมื่อ 20260825 หลัง backlog/feature-list เพิ่ม FT-026 ถึง FT-034 (Epic 5 NFR เพิ่มเติม 9 หมวด) โดยรอบ 20260825 จำกัดขอบเขตงานเฉพาะ 9 Feature ใหม่ตามคำสั่งที่ได้รับ (ไม่ใช่การสร้างใหม่ทั้งหมด) — ขยายเป็น 35 Feature เมื่อ 20260831 หลังเพิ่ม FT-035 (ใบเบิกยาแบบพิมพ์เพื่อเซ็นชื่อ, spec 007/BL-044-046) โดยรอบ 20260831 จำกัดขอบเขตงานเฉพาะ FT-035 เดียวตามคำสั่งที่ได้รับ (ไม่แตะไฟล์ FT-001–034 เดิม)
- **Granularity ของ scenario:** ระดับกลาง — หนึ่ง sequence diagram ต่อ backlog item (`BL-ID`) เป็นค่าเริ่มต้น โดยอ้าง AC scenario ที่เกี่ยวข้องทั้งหมดต่อ diagram (ไม่ใช่ 1 diagram ต่อ Feature เดียวรวมทุกอย่าง และไม่ใช่ 1 diagram ต่อทุก Given-When-Then scenario แยกกัน)
- **การแทน exception/alternate path:** ใช้ `alt`/`opt` inline ในไดอะแกรมเดียวกันเมื่อมี ≤2 branch ที่มีนัยสำคัญต่างกัน; แยกเป็นไดอะแกรมใหม่เมื่อมี 3+ branch ที่มีนัยสำคัญต่างกันอย่างชัดเจน (เช่น [two-level-requisition-approval.md](two-level-requisition-approval.md) แยก BL-004 เป็น 3 ไดอะแกรม, [confirm-export-and-download.md](confirm-export-and-download.md) แยก BL-020 เป็น 2 ไดอะแกรม)
- **Lifecycle/State diagram:** รวมเฉพาะ Feature ที่เป็น "เจ้าของ" สถานะของ entity หลักนั้นจริงๆ ไม่ซ้ำในทุกไฟล์ที่แค่อ้างอิงสถานะ — มี 2 ไฟล์ที่มี state diagram จริง: [two-level-requisition-approval.md](two-level-requisition-approval.md) §3 (สถานะคำขอเบิกยาทั้งวงจร) และ [confirm-export-and-download.md](confirm-export-and-download.md) §3 (ExportFile Download-Gate) — ไฟล์อื่นที่เกี่ยวข้องกับสถานะเดียวกันลิงก์กลับมาที่ไฟล์เจ้าของแทนการวาดซ้ำ
- **การแทน participant:** ใช้ role (`actor`) และองค์ประกอบเชิงตรรกะตามชื่อใน [05-architecture.md](../05-architecture.md) §3 ตรงตัวทุกไฟล์ (เช่น "บริการจัดการคำขอเบิกยา", "บริการคำนวณ Safety Stock และพยากรณ์") — เดิมมี 11 รายการ ขยายเป็น **12 รายการ** เมื่อ 20260831 หลังเพิ่ม "บริการสร้างเอกสารใบเบิกยาแบบพิมพ์" (FT-035) — ไม่มีการตั้งชื่อ component ใหม่ที่ไม่ปรากฏใน architecture doc
- **จุดที่ยังไม่ยืนยัน (`[รอยืนยัน]`) ในต้นทาง:** ไดอะแกรมคงเครื่องหมายนี้ไว้ตรงจุดที่ยังไม่รู้ผล แทนการสมมติขั้นตอนขึ้นเอง (ตัวอย่างเด่น: [advance-requisition-reminder.md](advance-requisition-reminder.md) — จำนวนวันแจ้งเตือนล่วงหน้ายังไม่ยืนยัน) — [invc-file-format-compatibility.md](invc-file-format-compatibility.md), [filtered-report-export.md](filtered-report-export.md) เคยอยู่ในกลุ่มนี้แต่ resolved แล้ว 20260823 และ [stock-reconciliation.md](stock-reconciliation.md) resolved ครบแล้ว 20260824 (เหลือเฉพาะ `[ถือว่า]` ระดับ validation ย่อยและ `[ส่งต่อ]` ด้าน data model ที่ไม่นับเป็น `[รอยืนยัน]` เชิงกฎธุรกิจอีกต่อไป)
- **การเชื่อมต่อระบบภายนอก (JHCIS/myPCU, INVC):** วาดเป็นขั้นตอน manual/asynchronous เสมอ ("ส่งออกไฟล์" → "นำเข้าเอง นอกระบบ") ไม่มีการวาดเป็น synchronous call ตาม [spec 005](../01-spec/20260816-005-legacy-system-integration.md)
- **ข้อยกเว้นที่ตั้งใจ:** [responsive-ui-all-devices.md](responsive-ui-all-devices.md) (FT-022), [office-hours-availability.md](office-hours-availability.md) (FT-025), [daily-backup-recovery.md](daily-backup-recovery.md) (FT-026), [data-encryption-in-transit.md](data-encryption-in-transit.md) (FT-030), [browser-compatibility.md](browser-compatibility.md) (FT-031), [network-scale-scalability.md](network-scale-scalability.md) (FT-032) เป็น NFR ล้วนๆ ที่ไม่มีความแตกต่างเชิงลำดับการโต้ตอบตาม scenario (ต่างกันแค่การนำเสนอ/ความพร้อมใช้งาน/ขอบเขตการรองรับ) จึงไม่แยกไดอะแกรมตาม AC scenario ทั้งหมดตามนโยบายข้อ "การแทน exception" — อธิบายเหตุผลไว้ในแต่ละไฟล์ (สำหรับ FT-022 แนวทาง hybrid นี้ได้รับการยืนยันจากเจ้าของข้อกำหนดแล้วเมื่อ 20260823) — [disaster-recovery.md](disaster-recovery.md) (FT-033) เป็นกรณีพิเศษแบบผสม: การกู้คืนระบบ (ทีมผู้ดูแลระบบ) และขั้นตอนสำรองแบบ manual (เจ้าหน้าที่/เภสัชกร) เกิดขึ้น**นอกระบบ SmartSync เอง** จึงแทนด้วย participant ภายนอกแบบเดียวกับระบบภายนอก (JHCIS/myPCU/INVC) — แต่ **อัปเดต 20260825 (scope change):** ขั้นตอนถัดจากนั้น (นำข้อมูล Manual Fallback กลับเข้าระบบ) ยืนยันแล้วว่ามีหน้าจอ Bulk Import จริงในแอป ดำเนินการโดย Admin จึงวาดเป็น operation ปกติกับระบบ SmartSync โดยตรง ไม่ใช่ participant ภายนอกอีกต่อไป (ดูรายละเอียดในไฟล์)
- **NFR ที่มีปฏิสัมพันธ์ผู้ใช้จริงแต่ไม่ผูกกับ Feature เดิม (เพิ่ม 20260825):** [concurrency-check.md](concurrency-check.md) (FT-027), [forced-password-change-session-timeout.md](forced-password-change-session-timeout.md) (FT-028), [pharmacist-two-factor-authentication.md](pharmacist-two-factor-authentication.md) (FT-029), [admin-system-configuration.md](admin-system-configuration.md) (FT-034) มีปฏิสัมพันธ์ผู้ใช้จริงตาม AC/user-journey จึงใช้รูปแบบ sequence diagram ปกติเหมือน Feature อื่นๆ — ทั้ง 4 ไฟล์ cross-reference กลับไปยังไฟล์ที่มีขั้นตอนก่อนหน้า/เกี่ยวข้องกัน (เช่น [access-log-retention.md](access-log-retention.md) สำหรับ login พื้นฐาน, [two-level-requisition-approval.md](two-level-requisition-approval.md) สำหรับ RBAC denial ของ BL-004) โดย**ไม่แก้ไขไฟล์ FT-001–025 เดิม** ตามขอบเขตงานที่กำหนดไว้ในรอบนี้

## Feature ที่เคยมี AC/backlog coverage บางที่สุด (ปัจจุบัน resolved ครบทั้งหมดแล้ว — เก็บหัวข้อนี้ไว้เพื่อประวัติ)

ไม่มี Feature ใดค้างอยู่ในรายการนี้อีกต่อไป ณ 20260824 — **FT-008 (stock-reconciliation.md)** เป็นรายการสุดท้ายที่ resolved ครบ: BL-032 ปิด Open Item รอบ 4 แล้วตั้งแต่ 20260823 (เภสัชกรกรอกยอดที่ถูกต้องเองระหว่างขั้นตอนอนุมัติระดับ 1, FR-1.9b) และไดอะแกรม 2.1 ของ stock-reconciliation.md ได้ขยายให้ครอบคลุมขั้นตอนคอนเฟิร์ม/กรอกยอดที่ถูกต้องนี้แล้วเมื่อ 20260824 พร้อม cross-reference กับ [two-level-requisition-approval.md](two-level-requisition-approval.md) (FT-002 ก็อัปเดตหมายเหตุเล็กน้อยพร้อมกันในรอบนี้) — เหลือเพียง `[ส่งต่อ]` ด้าน data model (ฟิลด์เก็บยอดคงเหลือ authoritative) ที่รอ `/build-data-api-spec` ออกแบบ ซึ่งเป็นรายละเอียดระดับ data model/API ไม่ใช่ประเด็นของ detailed design เอง (ไม่บล็อกสถานะ "ครบ" ของไฟล์นี้ เช่นเดียวกับหมายเหตุคล้ายกันที่ FT-017 มีอยู่แล้ว)

ก่อนหน้านี้ **FT-016 (filtered-report-export.md, BL-019 รูปแบบไฟล์)** และ **FT-018 (invc-file-format-compatibility.md)** เคยอยู่ในรายการนี้เช่นกันแต่ resolved แล้วตั้งแต่ 20260823 — FT-016 หลังเภสัชกรเจ้าของระบบยืนยันว่ารองรับทั้ง PDF และ Excel ให้เลือกได้ (ดู [004](../01-spec/20260816-004-management-dashboard.md) FR-3.3) และ FT-018 หลังฝ่ายดูแล INVC/เจ้าของข้อกำหนดยืนยันรูปแบบคอลัมน์จากไฟล์ตัวอย่างจริง (ดู [invc-file-format-compatibility.md](invc-file-format-compatibility.md))
