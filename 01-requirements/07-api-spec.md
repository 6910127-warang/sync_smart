> เอกสารนี้เป็น API spec ระดับแนวคิด (conceptual) เท่านั้น **ยังไม่ผูกมัดกับ API style/protocol (REST/GraphQL/gRPC ฯลฯ), route, format, หรือกลไก authentication ใดๆ** — ตาม CLAUDE.md เฟสปัจจุบันของโปรเจกต์คือการทำเอกสาร ยังไม่เข้าสู่เฟสพัฒนา เอกสารนี้จะถูกทบทวนอีกครั้งเมื่อเข้าสู่เฟสพัฒนาจริง
>
> อ้างอิงจาก [backlog.md](backlog.md), [Feature List](02-feature-list.md), [User Journey](03-user-journey/), [Data Model](06-data-model.md), [High-Level Architecture](05-architecture.md), และ spec ที่เกี่ยวข้องใน [01-spec/](01-spec/)

**วันที่สร้าง/อัปเดตล่าสุด:** 20260831

## 1. ภาพรวม (Overview)

เอกสารนี้จัดกลุ่ม operation แบบ**ผสม (Hybrid)**: (1) ข้อมูลอ้างอิง/ข้อมูลหลัก (หน่วยงาน, บัญชีผู้ใช้, รายการยา) ใช้การจัดกลุ่มแบบ resource-oriented (ดู/เพิ่ม/แก้ไข ต่อ entity) เพราะเป็นข้อมูลตั้งค่าที่ไม่ผูกกับ workflow เฉพาะ และ (2) กระบวนการธุรกิจหลัก (สร้างคำขอเบิก, อนุมัติ, รับยา, รายงาน, ส่งออกไฟล์, สร้างเอกสารใบเบิกยาแบบพิมพ์) ใช้การจัดกลุ่มแบบ journey-oriented —ตั้งชื่อ operation ตามการกระทำในบทบาทนั้น (เช่น "อนุมัติคำขอเบิก (ระดับ 1)") ตรงกับภาษาที่ backlog/user journey/acceptance-criteria ใช้อยู่แล้ว แทนที่จะบังคับเป็น create/read/update/delete ทั่วไปที่จะบิดเบือนความหมายของ workflow ไป — โครงสร้างกลุ่ม (หัวข้อ 3) ยึดตาม "องค์ประกอบเชิงตรรกะ/บริการ" ใน [05-architecture.md](05-architecture.md) หัวข้อ 3 เพื่อให้ทั้งสามเอกสาร (architecture/data-model/api-spec) มองภาพองค์กรของระบบตรงกัน — รวม 12 กลุ่มหลังเพิ่มกลุ่ม "เอกสารใบเบิกยาแบบพิมพ์" (3.12) เมื่อ 20260831

**หมายเหตุสำคัญเรื่องกระบวนการตัดสินใจของรอบนี้:** เช่นเดียวกับ [06-data-model.md](06-data-model.md) หัวข้อ 1 — เครื่องมือถามยืนยันแบบโต้ตอบไม่พร้อมใช้งานในรอบสร้างเอกสารครั้งแรกนี้ จึงเลือก Hybrid ตามหลักฐานข้างต้นแทนการเดาแบบเปิดกว้าง และบันทึกเป็นข้อสมมติที่ต้องยืนยันในหัวข้อ 5

## 2. สิทธิ์การเข้าถึง (Access / RBAC)

รายละเอียดกฎ RBAC เต็มอยู่ที่ [spec 006](01-spec/20260816-006-rbac-and-security-nfr.md) หัวข้อ NFR Security และ [spec 001](01-spec/20260816-001-project-scope-and-problem-background.md) ตาราง stakeholder — สรุปขอบเขตการเข้าถึงต่อบทบาทไว้ที่นี่เป็นตารางอ้างอิงเร็ว ส่วนคอลัมน์ "ผู้เรียกใช้งาน (Role)" ในตาราง operation ของหัวข้อ 3 คือรายละเอียดระดับ operation ที่ต้องอ่านคู่กับตารางนี้เสมอ

| บทบาท (Role) | ขอบเขตการเข้าถึงข้อมูล | อ้างอิง |
|---|---|---|
| เจ้าหน้าที่ รพ.สต. | อ่าน/เขียนเฉพาะข้อมูลของหน่วยงานตนเอง | BL-024 |
| เภสัชกร (ผู้อนุมัติระดับ 1/2) | อ่าน/เขียนทั้งเครือข่าย เฉพาะขอบเขตกระบวนการอนุมัติ/คอนเฟิร์ม — ห้ามเป็นผู้อนุมัติทั้งสองระดับของคำขอเดียวกัน | BL-004, BL-024 |
| ผู้บริหาร รพ./สสอ. | อ่านอย่างเดียว (Read-only) ทั้งเครือข่าย รวม drill-down รายหน่วย | BL-017, BL-024 |
| ผู้ดูแลระบบ (Admin) | สิทธิ์เต็มด้านระบบ/ผู้ใช้/สิทธิ์ + แก้ไขข้อมูลธุรกิจได้เฉพาะกรณีฉุกเฉิน (ต้องมี audit log ทุกครั้ง) | BL-024, BL-025 |

## 5. สิ่งที่ยังไม่ตัดสินใจ / Assumption ที่ต้องยืนยัน

**ตัดสินใจแล้ว (ยืนยันโดยผู้ใช้ 20260823):**

- หลักการจัดกลุ่ม operation = Hybrid (resource-oriented สำหรับข้อมูลอ้างอิง + journey-oriented สำหรับ workflow) — ดูเหตุผลในหัวข้อ 1 — **ยืนยันแล้ว**
- โครงสร้างกลุ่ม (หัวข้อ 3.1–3.11) ยึดตาม "องค์ประกอบเชิงตรรกะ/บริการ" ของ [05-architecture.md](05-architecture.md) หัวข้อ 3 เพื่อความสอดคล้องข้ามเอกสาร — **ยืนยันแล้ว**
- การนำเสนอสิทธิ์การเข้าถึง (หัวข้อ 2) = ตารางสรุปย่อ + คอลัมน์ role ต่อ operation พร้อมกัน (ไม่ใช่เลือกอย่างใดอย่างหนึ่ง) — เนื่องจากทั้งสองระดับมีประโยชน์และไม่ขัดแย้งกัน — **ยืนยันแล้ว**
- role ที่มีสิทธิ์เพิ่ม/แก้ไขรายการยา (Drug/Item Master) = **ผู้ดูแลระบบ (Admin) เท่านั้น** — ดูหัวข้อ 3.1 และหัวข้อ 4

**ตัดสินใจเพิ่มเติม 20260823:** รูปแบบข้อมูลของ "หมวดบัญชีแพทย์" บน DrugItem (ฟิลด์ Boolean เดี่ยว vs. entity หมวดยาแยก vs. join กับ Unit) — ดูการวิเคราะห์ 3 แนวทางพร้อมข้อดี/ข้อเสียเต็มรูปแบบใน [06-data-model.md](06-data-model.md) หัวข้อ 6 — เลือกแนวทาง Boolean เดี่ยวเป็นค่าเริ่มต้น (เครื่องมือ `AskUserQuestion` ไม่พร้อมใช้งานในรอบนี้) ยังต้องให้เภสัชกรเจ้าของระบบยืนยัน

**ตัดสินใจเพิ่มเติม (เพิ่ม 20260825, ยืนยันโดยผู้ใช้ผ่าน `AskUserQuestion` ในวันเดียวกัน — ดูการวิเคราะห์แนวทางแบบเต็มพร้อมข้อดี/ข้อเสียใน [06-data-model.md](06-data-model.md) หัวข้อ 6):**

- Optimistic Concurrency Check (BL-036/FR-6.5) ผูกกับ operation "พิจารณา/อนุมัติ/ปฏิเสธ/ปรับจำนวน (ระดับ 1)" และ "ตรวจสอบซ้ำและยืนยัน (ระดับ 2)" (3.4) โดยตรง — รับ/ตรวจ "เวอร์ชันของคำขอ" ทุกครั้งก่อนบันทึก แทนที่จะเป็น operation แยกต่างหาก เนื่องจากเป็น validation ที่เกิดร่วมกับการบันทึกเสมอ ไม่ใช่การกระทำที่ผู้ใช้เรียกเอง
- การบังคับเปลี่ยนรหัสผ่านครั้งแรก/2FA (BL-037/038) เพิ่มเป็น operation แยก ("เปลี่ยนรหัสผ่าน (บังคับครั้งแรก)", "ยืนยันตัวตนด้วย OTP (2FA)") ในกลุ่ม 3.2 แทนที่จะรวมเข้ากับ operation "เข้าสู่ระบบ" เดิม เนื่องจากมีข้อมูลรับ-ส่งและเงื่อนไข role ที่ต่างกันชัดเจน (การเปลี่ยนรหัสผ่านใช้กับทุก role, OTP ใช้กับเภสัชกรผู้อนุมัติเท่านั้น) — session timeout (FR-6.7) ไม่เพิ่ม operation ใหม่ เนื่องจากเป็นพฤติกรรมที่ระบบ trigger เอง ไม่ใช่การกระทำที่ผู้ใช้เรียก (สอดคล้องกับที่ user-journey ทุกไฟล์ไม่มี step แยกสำหรับเรื่องนี้)
